# 서브에이전트에 위임하기

에이전트에 일을 넘기는 것 자체가 결정이다. 잘못 위임하면 직접 하는 것보다 느려지고, 보고를
검증 없이 믿으면 안 된 일을 됐다고 듣게 된다. 같은 규율이 한 단계 위 — 사람 사이의 위임 —
에도 적용되지만, 이 스킬은 AI 서브에이전트 메커니즘에 집중한다.

## 위임할지부터 정한다

독립적으로 조사·실행 가능한 조각인가, 매 단계가 이전 결과에 의존하는가? 후자는 직접 하는 게
빠르다. **독립 도메인 간 병렬은 정상이다.** 관련 없는 실패 3개(다른 파일, 다른 원인)를 고치는
것은 한 턴에 여러 번 위임하는 것으로 보인다 — 각 에이전트는 세션 기록 없이, 좁은 범위, 명시적
제약, 구체적 산출물을 받는다. 서로 연관된 실패(하나를 고치면 다른 것도 고쳐질 수 있는)는 순차로
유지하고 나누지 않는다. **같은 파일을 두 위임이 동시에 편집하게 두지 않는다** — 도메인이 달라도
파일이 겹치면 그 파일만 빼서 순차로 처리한다. 접근 방식을 비교하려고 일부러 같은 문제를 여러
에이전트에 맡길 때는 각각 격리된 작업공간(git worktree 등)에서 돌리고, 미커밋 초안이 필요하면
명시적으로 복사해 넣는다.

"하기 싫다"는 위임의 이유가 아니다 — 컨텍스트 절약, 진짜 독립적인 도메인, 접근 비교처럼 이유가
있어야 위임한다. **역할별로 권한을 좁힌다**: 리뷰만 맡은 서브에이전트에 쓰기 권한을 주지 않는다.
**평면 구조가 기본이다** — 독립적인 여러 서브에이전트를 직접 디스패치하는 것이 기본값이고,
트리아지 → 수정 → 검증처럼 핸드오프가 필요한 다역할 작업에서만 코디네이터 하나를 둔다.

## 계층을 둘 때 / 이미 돌고 있는 에이전트에게 말 걸기

**깊이 제한 둘: 너 → 코디네이터 → 워커.** 코디네이터의 코디네이터는 없다. 코디네이터도 다른
서브에이전트와 같은 좁은 브리핑을 받고, 막힌 워커에는 명확한 재시도 한도와 실패 시 돌려줄
것을 정해준다. 보고는 기본적으로 hub-and-spoke(코디네이터가 워커 출력을 소화해 전달)로 하고,
"코디네이터가 전부 됐다"도 다른 서브에이전트 보고와 같은 검증을 거친다. 직접 여러 위임을 손으로
순서화하고 있는 걸 알아챈 순간이 코디네이터를 끼워넣을 신호다.

이름이 있는 실행 중(또는 완료된) 에이전트에 직접 말을 걸 수 있는 환경에서는 **다시 디스패치하지
말고 이어간다** — 이름으로 메시지를 보내면 그 에이전트의 전체 맥락을 가진 채로 재개된다.
**완료 신호를 구독하고 폴링하지 않는다** — "됐어?"를 반복해 묻는 것이 바로 이 방식이 대체하려는
반패턴이다. 자기 세션이 거부당한 동작을 다른 에이전트에 대신 시키지 않는다 — 권한 경계 우회다.
대신 사용자에게 가져간다.

## 브리핑하는 법

**작업 + 관련 인터페이스 + 제약**을 준다. 요약된 세션 기록을 붙여넣지 말고 파일 경로를 주어
서브에이전트가 직접 읽게 한다 — 붙여넣은 텍스트나 돌아온 요약은 그 순간부터 당신의 컨텍스트에
계속 남는다. 대상이 모호하면("이거 좀 고쳐줘") 위임하기 전에 직접 좁힌다. **디스패치 직전
기준점을 기록한다**(예: `git rev-parse HEAD`) — 작업 트리에 미커밋 변경이 있었다면 그것도
스냅샷하거나 먼저 커밋/스태시한다, 아니면 나중의 "무엇이 바뀌었나" diff가 섞여버린다. 같은
종류의 작업이 반복되면 브리핑을 재사용 템플릿으로 한 번 만들어 둔다.

## 돌아온 결과를 검증한다

**보고를 그대로 믿지 않는다** — "테스트 통과했다"는 주장일 뿐 증거가 아니다, 직접 돌리거나
diff를 읽는다(`verify-before-claiming`과 같은 원칙, 위임이 면제해주지 않는다). 보고와 리뷰는
**파일로** 받는다 — 채팅에 길게 쏟아진 답변은 압축 과정에서 사라진다. 리뷰를 요청했다면 무엇을
지적하지 말라고 미리 말하지 않는다 — finding이 그대로 드러나게 하고 나중에 직접 판단한다.
스펙 준수와 코드 품질은 **다른 축**이다. **여러 위임을 병렬로 돌린 뒤** 병합 전에: 각 요약을
따로 읽는다 → 겹친 코드가 있었는지 확인해 그 부분만 재검토 → 전체 테스트를 한 번 더 돌려 조합
문제를 잡는다.

## 막혔거나 리뷰 루프가 끝나지 않을 때

BLOCKED 보고에는 같은 지시로 재시도하지 않는다 — 구체적 피드백을 주고 재시도하거나, 더 강한
모델을 쓰거나, 작업을 쪼갠다. 리뷰에서 나온 finding은 **한 번에 한 서브에이전트**에 몰아서
고치게 한다 — finding마다 새 서브에이전트를 쓰면 매번 맥락을 처음부터 다시 쌓는다.
**수정 → 재리뷰 루프에 상한을 둔다**(예: 3회) — 넘기면 직접 판단한다: 틀렸거나 사소하면 이유를
적고 넘어가고, 실질적이면 가장 작은 수정을 직접 정하고 기록한다. **조용히 버리지 않는다** —
어느 쪽이든 판정과 이유를 남긴다.

## 얼마나 자주 끼어들지 조절한다

매 단계마다 확인을 구하지 않는다 — 일상적이고 되돌릴 수 있는 단계는 조용히 통과시키고, 정말
중요한 것에 개입을 아낀다. `weigh-tradeoffs`와 같은 기준: 되돌릴 수 있으면 → 하고 나서 결과를
보여준다, 되돌릴 수 없거나 중대하면 → 하기 전에 멈추고 묻는다. **확인 게이트는 다음 행동을
지키는 것이다, 이미 일어난 일이 아니다** — 서브에이전트가 이미 이메일을 보냈거나 커밋을
머지했다면 그 뒤에 "진행해도 될까요?"는 무의미하다.

## 장기 실행 작업과 흔한 실패

긴 시간 도는 위임은 끝날 때까지 조용히 두지 말고 짧은 이름과 한 줄 상태를 갱신한다. 브리핑에
자기 진행 상황을 파일에 쓰게 하고 그 파일을 들여다본다 — 중간 스트림을 볼 채널은 따로 없다.

흔한 실패: 여러 에이전트가 같은 파일을 동시에 편집해 서로 덮어씀 · "됐다"는 말만으로 검증 없이
다음 단계로 넘어감 · 검토하기엔 너무 큰 조각을 위임함(검토할 수 없다면 처음부터 잘못 쪼갠 것) ·
멈춘 걸 잡으려고 짧은 간격으로 계속 확인함(대기만 늘어난다, 완료 신호를 기다린다).

## 이 저장소에서

- 이 세션의 Agent 도구(새 디스패치)와 SendMessage(이름 있는 에이전트에 이어서 말 걸기)가
  "브리핑하는 법"과 "이미 돌고 있는 에이전트에게 말 걸기"를 구현한 실제 도구다.
- "같은 파일을 두 위임이 동시에 편집하지 않는다"는 정언명령 20(work item당 writing owner 한 명,
  owned path가 겹치지 않는 별도 issue·worktree에서만 병렬 허용)이 이미 강제한다.
- 완료 보고 검증 절차는 `.agents/skills/eatbid-supervised-delivery`의 "총괄: 다른 AI의 완료
  문장을 검증하기" 절이 이 저장소 기준으로 구체화해 두었다.
- 정언명령 22에 따라 `pnpm review:ai`의 finding은 결정적 gate 뒤 읽기 전용 advisory다 —
  lint·typecheck·test·contract·architecture 실패를 덮을 수 없다.
- 원본은 디스패치 점검·실행 상태 대시보드용 보조 Python 스크립트를 함께 두지만, 이 저장소는
  그 자리를 결정적 gate(`pnpm architecture:check`)와 Linear claim 상태가 대신한다 — 옮기지 않는다.

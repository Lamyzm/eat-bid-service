# 신뢰 경계 · 스케일 · 계층형 방어

## 신뢰 경계 — "외부"는 어디서 시작하는가

"내가 통제하는 것"과 "그 외 전부"의 경계를 긋는다.

- 사용자 입력, 외부 API 응답, 파일 내용을 그대로 신뢰하고 있는가? SQL, 셸 명령, 파일 경로, HTML로
  이스케이프 없이 흘러가는가?
- 비밀번호, API 키, 토큰이 코드·로그·오류 메시지에 노출되는가?
- 이 동작에 권한 검사가 필요한가? 클라이언트가 보낸 "나는 관리자다" 주장을 그대로 믿고 있는가?
- 검증이 **한 지점에서만** 강제되는가(클라이언트 측만, 또는 DB 제약만)?
- Principal 관점: 이 신뢰 경계가 서비스나 팀 경계를 넘는가? 여기서 생긴 틈은 로컬 버그가 아니라
  다른 팀이 그대로 물려받는 계약이 된다.
- Distinguished/Fellow 관점: 이 경계가 뚫리면 회사 전체 사후분석이나 외부 공개로 이어질 사고인가,
  그 대응이 이번 분기 트래픽만 버티면 되는 게 아니라 몇 년을 버텨야 하는 원칙이 되는가?
- Executive 관점(CTO/VP-Eng): 이 경계의 침해가 규제 리스크, 계약상 책임, 고객 신뢰 손상처럼
  이사회에 보고해야 할 사업 리스크로 이어지는가, 아니면 엔지니어링 안에서 정리되는 사고인가?

## 스케일 — 10배 · 1000배

지금 100건에서 잘 돈다는 사실은 아무것도 증명하지 않는다.

- 데이터가 10배, 1000배로 늘어도 이 방식이 버티는가?
- 루프 안에 DB 조회나 네트워크 호출이 있는가? (N+1)
- 모든 것을 한 번에 메모리에 올리는가? 스트리밍이나 배치로 나눌 수 있는가?
- 다만 **측정 없이 최적화하지 않는다** — 병목이 실제로 여기인지 먼저 확인한다.

## 계층형 방어

완벽한 단일 방어에 모든 것을 거는 구조보다, 한 겹이 실패하면 다음 겹이 받는 구조가 더 현실적이다.

- 이 안전장치가 실패하면 즉시 사고인가, 뒤에 다른 겹이 있는가?
- **무의식적 실수는 막고, 의식적 선택은 허용하되 흔적을 남긴다** — 이것이 좋은 안전장치의 모양이다.
  전부 막으면 사람들이 우회로를 찾고, 전부 허용하면 사고가 된다.
- 성공했을 때도 검증한다. "막혔다"에서 멈추지 말고 **왜** 막혔는지, 그 이유가 다른 조건에서도
  성립하는지 확인한다.

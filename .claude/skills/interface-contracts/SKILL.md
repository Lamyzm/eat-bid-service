# Interface 계약

## Hyrum's Law

> API 소비자가 충분히 많아지면, 계약에서 무엇을 약속했는지는 중요하지 않다 — 시스템의 **관찰 가능한 모든 동작**을 누군가는 의존하게 된다.

문서화되지 않은 특이 동작, 정확한 에러 메시지 문구, 순서, 심지어 타이밍까지 — **눈에 보이는 모든 것이 사실상의 계약이 된다.** 실무적으로는:

- 무엇을 노출할지 **의도적으로** 정한다. 관찰 가능한 동작 하나하나가 잠재적 약속이다.
- 구현 세부사항이 새어 나가게 두지 않는다. 보이면 누군가는 의존한다.
- 나중에 없애기 어려운 것은 — **설계 시점에** 없애거나 아예 노출하지 않는다.
- 테스트 통과가 안전과 같지 않다. 완벽한 계약 테스트 스위트도, 문서화되지 않은 동작에 의존한 소비자를 깨뜨리는 "안전한" 변경을 막지 못한다.
- 원리: 이것이 팀 간 파급(blast radius)이 생기는 방식이다 — 약속으로 의도하지 않은 필드·순서·에러 문구를 다른 팀의 서비스가 소비하면, "내부" 변경이 그들의 장애가 된다.

## Interface를 먼저 정의한다

구현 전에 계약을 쓴다. 계약이 스펙이고, 구현은 그 스펙을 만족시킬 뿐이다.

- 함수 시그니처, 입출력 타입, 각 메서드가 보장하는 것(idempotency, 부분 업데이트, 실패 동작)을 코드 전에 쓴다
- 에러 케이스를 명시한다: 리소스가 없을 때는? 입력이 잘못됐을 때는? 부분 실패는 어떻게 표현하는가?
- 호출자 관점에서 이 계약의 호출 지점을 먼저 써 본다 — 쓰기 편한가?

## 단일 버전 원칙

같은 의존성이나 API의 여러 버전 중 하나를 소비자가 고르게 만들지 않는다. 소비자마다 다른 버전을 원하면 다이아몬드 의존성 문제가 생긴다. 항상 정확히 하나의 버전만 존재하는 세계를 설계한다 — 포크하지 말고 확장한다.

## 체크리스트

- 이 interface가 **의도치 않게** 약속이 될 수 있는 것을 노출하는가? (에러 메시지 문구, 반환 순서, 내부 타입 이름)
- 나중에 바꾸려면 얼마나 아플까? 아프다면 지금 더 신중하게 설계한다.
- 이 경계를 넘는 데이터의 형태와 소유권이 분명한가? 오용하기 어려운가?
- 이 변경이 기존 소비자의 **문서화되지 않은** 관찰된 동작을 깨뜨리는가? 테스트 통과 여부와 무관하게 물어본다.
- 원리: 널리 쓰이는 interface에서 breaking change는 코드 diff가 아니라 하위 모든 팀에 강제하는 마이그레이션이다. deprecation 기간과 마이그레이션 경로를 사후 정리가 아니라 설계의 일부로 고려한다.
- 만약 이것이 회사 전체가 따라 하는 패턴이 된다면, 진짜 질문은 5년 뒤에도 다른 팀이 당신 없이 edge case를 올바르게 다룰 수 있는가다.
- 공개 interface에 박아 넣은 약속은 계속 지켜야 하는 지원·법적 책임 비용이다 — 지금 편하게 출시하는 것과 그 비용을 저울질한다.

## 이 저장소에서

Eatbid의 공개 endpoint·계약 topology는 개인 판단보다 소유권이 명확히 배정되어 있다. `AGENTS.md` 정언명령 19는 method·version·path·응답/Problem schema·`operationId`를 `packages/contracts`의 resource operation만 소유하게 하고, Server/Web에 canonical `/api/v1/...` literal이나 별도 `ENDPOINTS` mirror를 두지 못하게 막는다. 정언명령 15~17은 atom→value→resource→endpoint 조립 순서와 registry graph에서 codec·transform을 금지해 "관찰 가능한 동작"이 곧 계약이 되는 지점을 아예 하나로 좁힌다. 새 interface를 만들거나 바꿀 때는 `.agents/skills/eatbid-contract-change`에서 권위 지도를 먼저 확인하고, `pnpm architecture:check -- --changed`가 커밋마다 이 경계를 결정적으로 검사한다는 점을 전제로 움직인다. `design-for-the-next-reader`와 함께 본다.

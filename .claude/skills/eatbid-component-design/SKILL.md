# Eatbid 컴포넌트 설계

좋은 코드는 **변경하기 쉬운 코드**다. 새 요구가 왔을 때 고칠 자리를 빨리 찾고 옆을 안 깨뜨리면 좋은 코드다.
아래 기준은 그 목적의 수단이지 목적이 아니다.

## 0. 네 기준은 서로 상충한다

| 기준 | 변경 관점의 정의 | 주된 수단 |
| --- | --- | --- |
| 가독성 | 한 번에 담아야 할 맥락이 적고 위에서 아래로 읽힌다 | 맥락 줄이기, 구현 상세를 이름 뒤로, 조건에 이름 붙이기, 시점 이동 줄이기 |
| 예측 가능성 | 이름·인자·반환만 보고 동작을 안다 | 숨은 부수효과 드러내기, 같은 종류 함수는 반환 타입 통일 |
| 응집도 | 함께 고칠 코드가 항상 함께 고쳐진다 | 함께 바뀌는 파일을 같은 폴더에, 매직 넘버 없애기 |
| 결합도 | 고칠 때 영향 범위가 좁고 예측 가능하다 | 책임 하나씩, 중복 허용, props drilling 제거 |

**넷을 동시에 최대로 만들 수 없다.** 응집도를 위해 공통화하면 가독성이 떨어진다. 중복을 허용하면 결합도는
낮아지지만 응집도가 떨어진다. 그러니 매번 저울질한다.

- 함께 안 고치면 **버그가 나는** 관계다 → 응집도를 택한다. 공통화하고 한 곳에 둔다.
- 갈라질 가능성이 있고 안 고쳐도 위험이 낮다 → 가독성과 결합도를 택한다. **중복을 허용한다.**

DRY는 반사가 아니라 판단이다. "중복이니까 합친다"와 "선언적 컴포넌트를 썼으니 됐다"는 둘 다 기계적 적용이다.
매번 물어라. 이 선택이 변경 용이성을 높이는가, 지금 무엇을 우선해야 하는가.

## 1. 선언적 판정: 본문은 무엇을 보여주는지의 선언이다

컴포넌트 본문은 **무엇을** 보여주는지 선언한다. **어떻게**(주소 파싱, 조건 계산, 분기 기계장치, 포맷)는 이름
뒤로 숨긴다. 숨기는 것이 오히려 읽기 어려우면 숨기지 않는다.

판정은 프리미티브를 썼는지가 아니라 이것으로 한다. **한 줄씩 읽어서 무엇을 보여주는지 한 번에 이해되는가.
어떻게가 본문에 새어 나오는가.**

```tsx
// ❌ 어떻게가 본문에 샌다
function TodayScreen({ data }) {
  const region = data.search.region;
  const label = data.presentation.rows.find((row) => row.region.sido?.codeValueId === region)?.region.sido?.text;
  return <>{!data.presentation.hasSnapshotBuild ? <A /> : data.presentation.rows.length === 0 ? <B /> : <C />}</>;
}

// ✅ 본문이 무엇의 선언이다
function TodayScreen({ data }) {
  const regionText = regionTextOf(rowsOf(data.presentation), data.search.region);
  return <TodayFrame header={<TodayHeader …/>} filters={<TodayFilters …/>} list={<TodayList …/>} />;
}
```

## 2. 상태는 표시 모델의 union이고 화면은 고르기만 한다

화면이 boolean 두세 개로 상태를 다시 계산하면 같은 판정이 두 곳에 살고, 상태가 늘 때 화면이 조용히 빠뜨린다.

- 표시 모델이 `{ kind: … }` union을 돌려주고 화면은 `switch`로 갈래마다 일찍 반환한다.
- 삼항은 하나까지다. 두 단 이상 겹치면 union으로 올린다.
- 갈래 이름은 사용자가 할 일이 다른 만큼만 나눈다. "표시할 수 없음" 하나로 뭉치면 사용자가 무엇을 해야 할지 모른다.

**기존 규칙과의 관계.** 예상된 실패(없는 자원, 사라진 cursor, build 전환)는 **값**으로 돌려준다. 캐시 경계를
넘은 예외는 class 정체성을 잃기 때문이다. 예상 밖 실패만 그대로 던져 route error 경계가 받는다. 즉 union은
"무엇을 보여줄지"를, 경계는 "우리가 모르는 실패"를 맡는다. 둘은 대체재가 아니다.

## 3. 나눌 이유가 있을 때만 나눈다

분리 목적은 둘뿐이다. **복잡도를 낮추거나 재사용하거나.** 둘 다 아니면 나누지 않는다. 파일 수를 늘리는 것
자체는 개선이 아니다.

한 컴포넌트가 아래 셋 중 **둘 이상**을 하면 나눈다.

| 역할 | 사는 곳 |
| --- | --- |
| 데이터 관리 | 조회·상태·context |
| 표시 방법 결정 | JSX·포맷·클래스 |
| 사용자 상호작용 | 이벤트·폼 |

**렌더링하지 않는 모듈을 표현 폴더에 두지 않는다.** 계산은 표시 모델이나 도메인으로 간다. 확장자가 `.ts`인데
표현 폴더에 있으면 그 자체가 신호다.

**도메인 계산은 web의 층이 아니다.** 사정률·금액·시간 계산은 `packages/domain`이 소유한다(AGENTS 15).

## 4. 결합도를 낮추는 판단

- **중복을 허용한다.** 지금 비슷하다는 이유로 합치면, 화면마다 요구가 갈라질 때 공통 코드가 조건으로 부풀고
  고칠 때마다 모든 사용처를 확인해야 한다.
- **props drilling을 지운다.** 부모가 받은 값을 그대로 자식에 넘기는 사슬은 값 하나가 바뀔 때 사슬 전체를
  고치게 만든다. 합성이나 context로 끊는다.
- **boolean prop이 셋을 넘으면** 합성 컴포넌트를 검토한다. 소비자가 조합을 고르게 한다.
- **client provider에 넘기는 것은 키와 식별자이지 데이터 본문이 아니다.** 서버에서 넘긴 props는 RSC
  페이로드로 직렬화되어 HTML과 함께 두 번 실린다. 행 배열을 통째로 넘기면 그만큼 응답이 커진다.

## 5. server와 client 경계 (Eatbid)

- 기본은 server component다. 브라우저 상태·이벤트·브라우저 API가 필요한 **잎**에서만 `'use client'`를 쓴다.
- **라이브러리 때문에 client가 되지 않는다.** 표만 그리는데 headless 표 라이브러리를 들이면 그 순간 표 전체가
  브라우저로 넘어간다. 정렬·필터·가상화가 실제로 필요할 때 들인다.
- 공유 사실은 서버가 스냅샷 키와 함께 렌더하고, 개인 겹침은 그 키를 인용해 브라우저가 조회한다. 개인 자료는
  공유 캐시에 넣지 않는다(ADR 0028·0032).
- **주소 값이 질의를 바꾸면 서버 왕복, 이미 받은 것 중 무엇을 보일지만 바꾸면 클라이언트 전환이다.** 탭 전환
  같은 표시 전환을 링크로 만들면 데이터가 같은데도 페이지를 다시 받는다.

## 6. 자료형이 의도를 드러낸다

| 의도 | 자료형 |
| --- | --- |
| 순서와 중복이 의미 있다 | 배열 |
| 존재 여부만 반복해서 묻는다 | `Set` |
| 키로 자주 찾고 런타임에 키가 늘거나 준다 | `Map` |
| 키가 고정된 표다 | `as const` 객체 |

다섯 개 이하 목록은 배열 검색으로 충분하다. 반복 조회가 있으면 `Map`으로 바꾼다. 이미 있는 유틸(`es-toolkit`)을
먼저 찾고 직접 만들지 않는다.

## 7. 코드 스멜

| 신호 | 대응 |
| --- | --- |
| 삼항이 두 단 이상 겹친다 | 표시 모델 union + `switch` |
| 표현 폴더에 `.ts` 계산 파일이 있다 | 표시 모델 또는 `packages/domain`으로 |
| 한 파일이 상태 판정·조회·조립을 겸한다 | 판정을 순수 함수로 떼어 낸다 |
| 같은 표시 규칙이 두 화면에 복사돼 있다 | 함께 고쳐야 하면 한 곳으로, 갈라질 것 같으면 그대로 둔다 |
| `use client`인데 상호작용이 링크뿐이다 | server component로 되돌린다 |
| 같은 열 정의가 여러 표에 흩어져 있다 | 한 서술에서 파생한다 |
| 값 union 안에 함수가 들어 있다 | 상태는 데이터, 행동은 화면이 갖는다 |
| 비활성 조회에 빈 문자열 키를 넣는다 | 조회를 만들지 않는다(`skipToken`) |

## 8. 여기서 다루지 않는 것

- 파일 크기는 AGENTS 18이 소유한다. 300줄은 **권고**이며 분리 이유를 한 문장으로 남기면 유지할 수 있다.
- 계약·의미 값·endpoint 소유권은 AGENTS 15·16·19와 `packages/contracts`가 소유한다.
- 화면 문구·상태 표현·색 규칙과 접근성은 `apps/web/AGENTS.md`와 `docs/product/screen-system.md` §11이 소유한다.
- 모듈 경계와 import 방향은 ADR 0023이 소유한다.

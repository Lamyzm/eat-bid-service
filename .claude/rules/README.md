## 이건 우리가 못 막는다

설계 좌석이 `SPEC-SSOT.md` §6-2에 스스로 쓴 문장이 맞다:

> **"규칙 만드는 사람과 지키는 사람이 같으면 어떤 자동화도 최종적으로 자발성에 기댄다. 이 설계는 그 사실을 없애지 못한다. 비용만 올린다."**

**이 문서도 마찬가지다.** 아래는 정직하게 적어둔다.

**① 이 규칙들은 대부분 자동 검사가 없다.** 리포에 테스트 0개·CI 0개이고, 실제로 도는 건 `pre-commit → lint-staged`와 `pre-push → bun run build` 둘뿐이다. **가드로 잡을 수 있는 건 네 개뿐**이고(`ssot-guard.mjs` 축소안), 나머지는 사람이 지킨다.

**② allowlist는 언제나 수정보다 싸다.** 1인 개발 + 에이전트 팀에서 가드에 막히면 고치는 대신 예외를 넣고 간다. `until` 만료를 걸어도 **만료일을 미루는 것도 한 줄**이다.

**③ 규칙을 만든 그 회차에 같은 실수를 한다.** 실증이 둘 있다.
- 설계 좌석이 §10-27에 *"제안을 받을 때는 검증한다"*고 쓴 **바로 다음 라운드에** 내 근거를 검증 없이 받아 설계 결정을 내렸다.
- 나는 §25-3에 *"이 필드는 무엇에 대한 값인가를 물어라"*를 세운 **직후에** `MLFD_CLASS_CD`에 걸릴 뻔했다. 그 질문을 적용해서 멈췄지만, **질문이 있어서 멈춘 게 아니라 마침 그걸 방금 써서 기억하고 있었기 때문이다.**

**④ 그래서 이 문서의 실제 효용은 "혼자 지키는 체크리스트"가 아니라 "서로에게 묻는 목록"이다.** 이번 주 A급 발견 대부분이 한쪽이 다른 쪽 근거를 밟아서 나왔다. 좌석이 하나면 이 목록은 훨씬 덜 작동한다.

**⑤ 규칙이 늘어나면 안 읽힌다.** mw-auction은 27개인데 그쪽 `MODULE_MAP.md`는 스스로 stale해졌다. **넷을 넘기지 마라.** 새 규칙을 넣고 싶으면 기존 것을 지우거나 합쳐라.

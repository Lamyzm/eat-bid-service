# 비드큐 공개 FAQ에서 확인한 업계 언어와 사용자 문제

이 문서는 [비드큐 자주하는 질문 — 입/낙찰정보](https://www.bidq.co.kr/bidq/customer/faq?category=1)의
공개 내용을 요약한 경쟁 제품·도메인 evidence다. 비드큐의 표현과 계산을 eatbid의 정확한 eaT 규칙이나
제품 약속으로 채택하지 않는다. 특히 FAQ에는 나라장터·지자체 공사/용역 중심 내용이 많으므로 eaT 급식
입찰에 직접 적용하기 전에 source contract와 공식 원문을 별도로 검증해야 한다.

## 사용자 mental model

공개 FAQ의 질문 구조에서 사용자가 입찰정보를 다음 단위로 이해한다는 점을 확인할 수 있다.

- `발주처/기관`, `업종·품목`, `지역`, `가격`, `일시`로 과거 흐름과 빈도를 좁힌다.
- `투찰율`, `기초대비`, `업체별사정율`처럼 비슷해 보이는 비율의 분모와 산식 차이를 궁금해한다.
- 공고문과 개찰결과의 하한율이 다를 때 무엇을 믿어야 하는지 묻는다.
- 정정·취소·긴급·지역제한·단가·내역서·기초금액 발표 같은 공고 상태를 빠르게 식별하려 한다.
- 과거 공고를 날짜 종류와 기간으로 다시 찾고 싶어 한다.
- 누락 또는 잘못된 정보가 데이터 문제인지 검색 조건 문제인지 구분하기 어려워한다.
- 분석을 `발주처 성향`, `값의 구간 빈도`, `경쟁사 투찰 흐름`이라는 서로 다른 질문으로 나눈다.

## eatbid 기획에 채택할 것

### 1. 필터는 결과를 찾는 핵심 업무다

비드큐 FAQ는 업종·지역제한·발주처명·공고명 등 검색옵션이 source 정보와 다르면 공고가 있어도
결과에서 보이지 않을 수 있다고 안내한다. 따라서 eatbid는 `0건`을 데이터 없음으로만 표현하지 않고
다음 세 경우를 구분해야 한다.

```text
source 관측 없음
현재 필터에서 제외됨
mapping/measure가 불완전해 비교 불가
```

적용 filter, 실제 기간, 포함·제외 수와 reason을 chart·표보다 먼저 확인할 수 있어야 한다. `필터 초기화`는
사용자가 작성한 후보·결정을 지우지 않고 evidence result만 target 기본값으로 되돌린다.

### 2. 비슷한 비율은 분모를 숨기지 않는다

FAQ는 투찰율·기초대비·업체별사정율의 차이와 A값 적용 여부를 별도로 설명한다. eatbid V1은 이를
그대로 계산하지 않지만, 하나의 축에 올리는 모든 값에 다음 계약이 필요하다는 evidence로 사용한다.

- measure의 정확한 이름
- 분자·분모의 의미
- 단위와 scale·source precision
- 직접 관측인지 파생 계산인지
- 적용 공식과 computation version

`낙찰값`, `2등값`, `보통 쓰는 자리`처럼 분모와 출처가 없는 축약어를 핵심 분석 라벨로 사용하지 않는다.

### 3. 기관·빈도·경쟁사 분석은 별도 렌즈다

비드큐는 공개 FAQ에서 발주처 흐름, 구간 빈도, 경쟁사 투찰 흐름을 서로 다른 분석 메뉴로 설명한다.
eatbid도 같은 데이터가 일부 겹치더라도 세 질문을 하나의 chart나 종합점수로 합치지 않는다.

| 질문 | eatbid surface |
|---|---|
| 이 기관의 과거 회차는 시간순으로 어땠나? | exact 기관 시간 이력 |
| 비교 가능한 과거 관측은 어느 값에 얼마나 분포했나? | versioned 비교집단 분포 |
| 특정 업체가 실제로 어떤 회차에 참여했나? | 업체 사실 drill-down/복기 |

### 4. 원문 우선과 revision을 화면에서 보여 준다

비드큐 FAQ는 공고문과 개찰결과의 적용 하한이 다를 때 공고문을 우선 확인하고 정정·취소 가능성을
검토해야 한다고 안내한다. eatbid는 이 내용을 규칙으로 복사하지 않고, 서로 충돌하는 source 사실을
조용히 하나로 합치지 않아야 한다는 UX evidence로 사용한다.

- 현재 선택한 공고 revision과 최신 revision 관계
- 원문 기준과 결과 관측의 불일치
- 정정·취소·재입찰 상태
- 어떤 원본과 계산 버전을 현재 분석이 사용했는지

를 target header와 원자료에서 확인할 수 있게 한다.

### 5. 신뢰는 정확해 보이는 숫자보다 수정 경로에서 생긴다

FAQ에는 잘못된 정보·누락 공고에 대한 문의와 검수 과정 안내가 별도로 존재한다. eatbid는 전화 상담을
그대로 모방할 필요는 없지만 다음 product capability를 후속으로 검증한다.

- 각 사실의 `원문 보기`
- `자료 문제 신고`와 대상 attempt/revision 자동 첨부
- 마지막 검증 시각과 새 자료 검증 중 상태
- 신고 이후 정정 publication과 영향받은 분석 결과 추적

## 채택하지 않을 것

비드큐 FAQ의 다음 내용은 경쟁사의 제품 전략을 이해하는 자료이지 eatbid V1 요구사항이 아니다.

- 난수·등비·발주처 분석으로 복수예비가격 또는 임의 투찰금액을 산출
- 과거 빈도를 `낙찰확률구간`으로 표현
- 발주처·업체 빈도를 점수화해 확률이 높은 투찰구간을 추천
- 사용자가 고른 과거 결과를 다음 가격 산출에 바로 적용
- G2B 공사입찰의 A값·적격심사·하한율 표를 eaT에 그대로 적용

eatbid는 이 기능들의 수요 신호는 인정하되, 사전등록된 시간순 검증과 제품 경계 변경 전에는
`과거 관측`, `분포`, `사용자 후보 replay`라는 중립적 언어를 유지한다.

## 디자인 검토 질문

Claude Design 또는 내부 디자인 리뷰에서 다음을 확인한다.

1. 사용자가 현재 filter를 `기관·품목·지역·가격/하한·기간` 순서로 설명할 수 있는가?
2. 0건일 때 source 없음과 filter 제외를 구분할 수 있는가?
3. `관측 낙찰 투찰률`과 `재구성 2등 투찰률`의 출처·산식 차이를 찾을 수 있는가?
4. 정정·취소·새 revision이 분석의 어떤 부분에 영향을 주는지 이해할 수 있는가?
5. 기관 흐름·빈도·경쟁사 분석이 서로 다른 질문임을 navigation과 heading에서 알 수 있는가?
6. 잘못된 값에서 원문 확인 또는 자료 문제 신고로 이동할 수 있는가?

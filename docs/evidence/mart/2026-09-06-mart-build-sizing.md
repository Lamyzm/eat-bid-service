# mart 빌드 규모 실측 — 2026-09-06

`org_round_summary` 전량 재빌드가 얼마나 걸리는지, 그리고 ADR 0034가 적은 "60초를 넘으면 개찰 연도로
쪼갠다"는 되돌리기 조건이 언제 걸리는지를 실측으로 남긴다.

## 1. 세 번의 측정이 서로 다른 것을 쟀다

| 측정 | 규모 | `org_round_summary` 전량 빌드 | 무엇을 쟀나 |
|---|---|---:|---|
| 설계(EAT-44 설계 §6) | 74만 회차 · 2,774만 명단 행 | 6.7 s | 합성 표. **FK 제약과 trigger가 없다** |
| 1차 구현 | 4만 회차 · 100만 명단 행 | 7.75 s | 실제 `mart.org_round_summary` |
| 재측정(이 문서) | 4만 회차 · 100만 명단 행 | **7.00 s** | 실제 표, `EXPLAIN (ANALYZE, BUFFERS)` |

작은 규모가 더 오래 걸린 것이 이상해 보이지만 세 측정은 같은 것을 재지 않았다. 재측정이 그 차이를
설명한다.

## 2. 재측정 조건

- `postgres:16-alpine` (PostgreSQL 16.13) 일회용 container, `--shm-size=2g`,
  `shared_buffers=1GB work_mem=128MB maintenance_work_mem=512MB max_wal_size=4GB`. 호스트는 개발 PC다.
- 스키마는 저장소 migration 전부(`20260905223623_mart_decision_tables`까지)를 적용한 실제 스키마다.
- 합성 데이터: 회차 40,000 · 기관 12,000 · 업체 40,000 · 명단 1,000,000(회차당 25행) ·
  낙찰 40,000 · 하한율 두 종(90.000, 88.000). 명단 파티션은 2025년 하나에 들어간다.
  `core.bid_submission` 전 파티션 합계 330 MB, 결과 `mart.org_round_summary` 24 MB.
- 질의는 `apps/dataplane/src/eatbid/mart/org_round_summary.py`의 `ORG_ROUND_SUMMARY_FILL_SQL`
  그대로다. 측정 뒤 container는 삭제했다.

## 3. 병목은 집계가 아니라 행마다 도는 FK 검증이다

`EXPLAIN (ANALYZE, BUFFERS)` 실행 시간 **6,991 ms** 가운데 계획 노드가 쓴 시간은 작다.

- `core.bid_submission` 파티션 seq scan 1,000,000행 116 ms(shared hit 18,182, 디스크 읽기 없음)
- `code_value`·`award_decision`·`auction_revision_code_value` hash build 각각 9~11 ms
- 명단 집계와 `distinct on` 전체가 초 단위 아래다

시간을 쓴 것은 삽입된 40,000행마다 도는 제약 trigger다.

| trigger | 시간 | 호출 |
|---|---:|---:|
| `auction_attempt` FK | 1,043 ms | 40,000 |
| `organization` FK | 1,026 ms | 40,000 |
| `auction_revision` FK | 1,032 ms | 40,000 |
| `code_value`(지역/방식) FK | 1,025 ms | 40,000 |
| `supplier_party` FK | 1,037 ms | 40,000 |
| `mart.build` FK | 216 ms | 40,000 |
| `item_code_value` FK | 28 ms | 40,000 |
| `supersedes_attempt` FK | 19 ms | 40,000 |
| `org_round_summary_build_is_building` | 206 ms | 40,000 |
| 합계 | **약 5,632 ms** | |

같은 질의를 `session_replication_role = replica`로 두어 이 trigger들만 끄면 실행 시간이
**1,361 ms**가 된다. 즉 **전체의 80%가 행마다 도는 제약 검증**이고 집계는 100만 명단 행에서 1.4초다.

행당 제약 비용은 `(6,991 − 1,361) / 40,000 ≈ 141 µs`다.

## 4. 세 측정의 차이가 설명된다

설계 실측 6.7초는 FK 없는 합성 표에 74만 행을 넣은 시간이라 §3의 5.6초가 통째로 빠져 있다. 1차와
재측정은 같은 조건에서 7.75초·7.00초로 사실상 같은 값이며, 차이는 호스트 부하 수준이다.

**즉 전량 빌드 시간은 명단 행 수가 아니라 만들어지는 mart 행 수(=회차 수)가 지배한다.** 명단 100만
행을 한 번 통과하는 비용은 1.4초이고, 회차 4만 개를 적재하는 비용이 5.6초다.

## 5. 60초 규칙은 언제 걸리는가

행당 141 µs와 집계 상수항으로 외삽한다.

| 모집단 | 회차 수 | 예상 전량 빌드 |
|---|---:|---:|
| 현재 레이크(2026-09-04 전수 리포트) | 238,306 | 약 36 s |
| 설계의 5년 전국 환산 | 740,000 | 약 108 s |
| 60초에 닿는 지점 | 약 400,000 | 60 s |

- 지금 규모에서는 60초 아래이므로 ADR 0034의 되돌리기 조건을 아직 발동하지 않는다(AGENTS 11).
- 전수 백필로 회차가 40만을 넘으면 조건이 걸린다. 그때 `mart.build`에 개찰 연도 `partition_key`를
  더하고 활성 포인터를 `(mart_name, partition_key)`로 넓히는 것이 ADR 0034의 처방이며, **그 처방이
  듣는 이유가 이 측정에 있다**: build 하나가 삽입하는 행 수가 줄면 제약 검증 호출 수가 그만큼 준다.
  집계는 이미 상수에 가까워 쪼갠다고 크게 줄지 않는다.
- 되돌리기 조건을 발동하기 전에 먼저 확인할 것은 FK 목록이다. `mart`는 파생물이고 입력은 이미
  검증된 `core`이므로, 어떤 FK가 실제로 무엇을 막고 있는지 다시 물을 값이 있다. 다만 지금은 측정된
  병목이 아니라 예상 병목이므로 아무것도 바꾸지 않는다.

## 6. 이 측정이 답하지 않는 것

- `win_rate_distribution_monthly`는 이번에 재측정하지 않았다. 1차 실측 5.07초(같은 규모)와 설계
  실측 4.6초의 차이는 같은 원인(FK 유무)으로 설명될 것으로 보지만 확인하지 않았다.
- 합성 명단은 회차당 25행 고정이라 실제(중앙 15, 최대 413)의 분포 꼬리가 없다. 집계 시간은 행 수에
  거의 선형이므로 총 행 수가 같으면 큰 차이는 없다고 본다.
- 전수 백필 뒤 실제 값으로 이 표를 한 번 더 갱신한다.

## §0. 실측이 전제를 네 군데 뒤집었다

이 문서를 쓰기 전에 잰 것이 리더의 전제와 다르다. **설계가 통째로 바뀌는 지점이라 먼저 적는다.**

### 0-1. 🔴 레이크는 노드 안에 없다. **`F:\` 다**

전제는 *"레이크가 hostPath 라 노드가 날아가면 사라진다(재파싱으로 복구되지만 50분)"* 였다. **아니다.**

```
$ docker inspect k3d-eatbid-server-0 --format '{{json .HostConfig.Binds}}'
["F:\\Project\\eat-bid\\data:/lake","k3d-eatbid-images:/k3d/images"]

$ docker exec k3d-eatbid-server-0 df -h /lake
Filesystem  Size  Used Avail Use% Mounted on
F:\         932G  690G  243G  74% /lake
```

`/lake` 는 **`F:\Project\eat-bid\data` 를 그대로 본 것**이다. 로컬 도커 백필 3개가 쓰는 디렉터리와
CronJob 이 읽는 디렉터리가 **같은 파일**이다. `k3d cluster delete` 를 해도 raw 도 parquet 도 안 없어진다.

### 0-2. 🔴 노드와 함께 죽는 것은 **Postgres 다.** 위험이 정확히 반대로 있었다

```
$ docker exec k3d-eatbid-server-0 df -h /var/lib/rancher/k3s
/dev/sde   1007G   98G  859G  11% /var/lib/rancher/k3s
```

`local-path` PV 는 `/var/lib/rancher/k3s/storage/…` 에 있고, 그건 도커 볼륨
`5941edb8…` 다 — **`k3d cluster delete` 가 지운다.** 즉:

| | 노드 삭제 시 | 재생성 |
|---|---|---|
| raw + parquet + state sqlite | **살아남는다** (F:\) | — |
| Postgres 913만 행 | **사라진다** | 로더 재실행 **27분**(§6 실측) |

**전제와 반대다.** 그래서 §2 의 결정도 반대 방향으로 나온다.

### 0-3. 🔴 실행 환경이 **둘로 갈려 있고, 안전장치를 가진 쪽이 로더를 안 돌린다**

```

F:\Project\eat-bid -> /repo                      ← 리포 전체다. data/ 만이 아니다

$ docker exec r18a ls -ld /data
ls: cannot access '/data': No such file or directory      ← 없다
```

| | **로컬 도커 백필**(r18a·r18b·backfill-history) | **k8s CronJob** |
|---|---|---|
| 코드 출처 | `F:\Project\eat-bid` **바인드**, WD=`/repo` | 이미지 `eatbid-dataplane:dev` |
| `docs/source-fields.json` | **있다** | **없다**(`Dockerfile:15-17` 이 `docs/` 를 안 넣는다) |
| 드리프트 감지 | **작동한다** | **`inspect()` 가 항상 `[]`**(§7-1) |

**두 가지가 여기서 나온다.**

**(1) 지금 이 순간 🔴 STOP 이 서 있는데 로더가 못 본다.** `F:\…\data\source-drift.json` 실측:

**(2) ⚠ `ARCH-DELIVERY` §0-1 을 순진하게 고치면 raw 40시간이 사라진다.**

`Paths` 가 `/data` 를 `mkdir` 해 버리므로 **에러도 안 난다.** 조용히 죽는 컨테이너 안에 쌓인다.

> **`EATBID_DATA_ROOT` 를 존중하도록 고치는 커밋과 `docker run` 에 `-v …:/data` 를 붙이는 일은
> 같은 커밋이어야 한다.** 순서가 어긋나면 그 사이에 수집한 raw 를 잃는다.
> **두 좌석이 각각 절반씩 고치면 정확히 그 사고가 난다.**

## §2. 🔴 raw 아카이브의 집 — **1순위**

### 결정

**세 단계로, 이 순서로.**

| # | 언제 | 무엇 | 비용 |
|---|---|---|---|
| **1** | **오늘, 이 문서를 다 읽기 전에** | `C:\` 로 2차 사본 — 다른 볼륨 | **5분** |
| 2 | 이번 주 | **Cloudflare R2**, 샤드 단위 256개 객체 + 매니페스트 1개, 매일 | 설정 1h · 매일 5분 무인 |
| 3 | 백필 종료 후 | 월 1회 사본을 **실제로 복원해 파일 수를 대조** | 10분/월 |

목적지 R2 는 **`ARCH-DELIVERY` §7-5 의 판단과 같다.** 여기서 다시 논증하지 않는다.
**이 절이 더하는 것은 "어떤 모양으로 담느냐" 다** — 거기서는 `data/` 전체를 날짜별 tar 하나로 올린다.
그 형태는 아래 두 가지 때문에 지금 대상에 안 맞는다.

### 근거 — 통짜 tar 하나가 안 되는 이유 둘

**(a) 대상이 시간당 10,827개씩 자라는 중이다.** 통짜 tar 는 살아 있는 트리를 수 분간 걸어 다니므로
**찢어진 시점**을 담는다. 그리고 날짜별 이름이면 매번 1.8 GB 를 통째로 다시 올린다.

**(b) 샤드 단위면 두 문제가 같이 없어진다.** 샤드 하나 포장이 **312 ms** 다(§1-2).
찢어지는 창이 객체당 0.3초이고, **raw 는 append-only + 파일명 고유**라
(`config.py:51` "raw/parquet 은 파일명이 고유해 공유해도 충돌하지 않는다(검증됨)")
찢어져 봐야 **가장 최근 파일 몇 개가 빠질 뿐**이고 다음 회차가 가져간다.

### 근거 — 개별 22만 객체도 안 되는 이유

223,165개를 그대로 올리면 동기화마다 Class A 작업 223,165개이고, rclone 이 차이를 내려면
**22만 키를 LIST 해야 한다.** 초당 20 PUT 이어도 3.1시간이다. 무엇보다
**"다 왔나"를 답하기 어렵다** — `ARCH-DELIVERY` §7-6 이 지적한 그 문제다.

### 근거 — 압축은 하지 마라 (실측이 그렇게 말한다)

| 후보 | 절감 | 대가 | 판정 |
|---|---|---|---|
| tar 만 | 기준 | 312 ms/샤드 → 전체 **80초** | ✅ |
| tar + `gzip -1` | 5% | +100 ms/샤드 | 무의미 |
| 풀고 → solid `gzip -9` | **21%** (380 MB) | 22만 개 압축 해제 + 재압축 | ❌ |
| 풀고 → solid `xz -6` | **63%** (1.1 GB) | 단일 스레드 **81분** | ❌ |

21%·63% 는 진짜 이득이다 — 파일이 평균 8 KB 라 gzip 의 32 KB 창에 여러 개가 같이 들어와
**같은 스키마의 XML 끼리 서로를 압축**하기 때문이다. **그런데 살 이유가 없다.**
R2 무료 티어가 10 GB 인데 지금이 1.8 GB 다. **우리는 스토리지 값을 안 낸다.
안 내는 값을 아끼려고 CPU 를 8배 쓰지 않는다.**

> ⚠ **`tar czf` 는 특히 하지 마라.** 이미 gzip 된 것을 또 gzip 하는 것이고 실측 절감이
> **7,075,840 → 6,469,865 (8.6%)** 다. 압축 착시다.

### 형태

"복사 명령이 성공했다" 와 "다 왔다" 는 다르고, **틀렸을 때 어디가 틀렸는지까지 나와야 고칠 수 있다.**

**R2 복구 5분의 내역** (전부 실측에서 나온 수):
- 다운로드 1.7 GB — egress 무료, 100 Mbps 기준 **2.3분**
- untar 223,165 파일 → NTFS — **1,869 파일/s 실측 → 119초 ≈ 2분**
- 매니페스트 대조 — 초 단위

**R2 요금**: 스토리지 10 GB·Class A 100만/월·Class B 1000만/월 무료, **egress 무료**.
우리는 1.7 GB · 하루 256 PUT (= 월 7,680) 이다. **1년 뒤 5.0 GB(§9) 여도 무료 티어 안이다.**
초과분 $0.015/GB·월. *(가입 시점에 요금표 재확인할 것 — 이 문서가 근거가 되면 안 된다.)*

**증분을 만들지 않는다.** 해시 샤딩이라 하루 1만 개가 256 샤드에 고루 퍼져서 어차피 전 샤드가
바뀐다. 매일 전량 = **80초 포장 + 1.7 GB 업로드**이고, 대신 **모든 스냅샷이 그 자체로 완전하고
자기검증된다.** 틀릴 수 있는 증분 로직을 안 만드는 값이 절감보다 크다.
(전량 업로드가 부담이 되는 지점은 3년 뒤 약 10 GB/일이다. 그때 "닫힌 달은 불변" 으로 바꾼다. 지금은 아니다.)

### state sqlite 은 **대체 불가가 아니다** — 정정

`ARCH-DELIVERY` §7-1 은 `state*.sqlite` 를 *"❌ 잃으면 백필 처음부터"* 로 적었다. **재구성된다.**

`state.mark_done(d.auction["bid_id"])` 를 부르고, 아카이브 파일명이 `<bid_id>.xml.gz` 다.
대조: `done` 합계 221,003 vs raw 파일 223,165 — 차이 2,162 는 **받았지만 아직 parquet 에 안 쓴 것**
(batch 200, `crawl.py:23`)이고, 전체 재파싱(50분)이 그것까지 흡수한다.

```
done = { path.stem.replace('.xml','') for path in raw/internal/**/*.xml.gz }
```

**의미**: sqlite 를 정지시켜 복사하는 것이 여전히 싸지만(초 단위), **못 하더라도 잃는 것은
백필 전체가 아니라 재파싱 50분이다.** `ARCH-DELIVERY` §7-4 의 3단계 절차에서
2단계(워커 정지)가 **의무가 아니라 최적화**로 내려간다.

### 안 하면 무엇이 깨지나

**F: 디스크가 죽으면 프로젝트가 끝난다.** 지난 공고는 다시 안 열리고,

## §3. 레이크와 서빙 DB 의 자리

### 결정

| 대상 | 결정 | 이유 |
|---|---|---|
| **레이크(raw+parquet)** | **호스트 파일시스템 유지** — 이미 그렇다(§0-1) | 바꿀 것이 없다. 바인드 하나가 이식 단위다 |
| **Postgres** | **`local-path` 유지. 단, 세 군데를 정직하게 고친다** | 27분에 재생성되는 것에 스토리지 설계를 붙이지 않는다 |

### 근거 — 단일 노드 k3d 에서 PVC 가 실제로 보장하는 것

**거의 없다.** `local-path` provisioner 는:

| 사람들이 기대하는 것 | 실제 |
|---|---|
| 용량 `2Gi` 를 지킨다 | ❌ **5,478 MB 가 들어 있다**(§0-4). 강제하지 않는다 |
| 노드와 독립적이다 | ❌ 노드 컨테이너 안 도커 볼륨. `k3d cluster delete` 가 지운다 |
| 다른 노드로 옮겨간다 | ❌ 단일 노드다. `RWO` 는 옮길 곳이 없다 |
| PVC 를 지워도 데이터는 남는다 | ❌ `reclaimPolicy: Delete` — **같이 지워진다** |

**`local-path` 는 hostPath 에 절차가 더 붙은 것이다.** 그래도 유지하는 이유는
**Postgres 가 레이크의 함수**여서다 — 로더 27분이면 되돌아온다. 지키려고 애쓸 대상이 아니다.

### 그래서 고칠 셋

1. **`app.yaml:13` 의 `2Gi` → 실측 기반 값 + 근거 주석.** 지금 5,478 MB, 1년 뒤 약 13 GB(§8).
   `16Gi` 로 적고 *왜 그 숫자인지* 를 옆에 적는다. **지금 아무것도 안 자르는 거짓 숫자가
   가장 위험하다 — 다음 사람이 믿는다.**
2. **`persistentVolumeReclaimPolicy: Retain`.** `kubectl delete pvc` 한 번이 27분이 되지 않게.
3. **디스크 여유를 재고 시끄럽게 실패하기.** 지금 `/dev/sde` 859 GB 여유고 그 뒤는 C: 의 909 GB 다.
   문제가 아니라는 것이 요점이 아니라, **아무도 안 재고 있다는 것**이 요점이다.
   로더가 시작 전에 "필요 추정 vs 여유" 를 찍고 모자라면 **적재 전에** 죽는다.

### 이식 시 무엇이 따라가야 하나

**디렉터리 하나다.**

```
F:\Project\eat-bid\data\        ← raw + parquet + bidboard + state*.sqlite. 이게 전부다
```

따라가지 **않아도 되는 것**: Postgres PV(로더 27분), 이미지(§`ARCH-DELIVERY`), k3d 노드.
**`k3d cluster create` 시 `--volume <새경로>\data:/lake` 만 맞으면 새 기계에서 그대로 돈다.**
(그 명령이 두 리포 어디에도 없다는 문제는 `ARCH-DELIVERY` §0-2 가 다룬다.)

### 안 하면 무엇이 깨지나

- `2Gi` 를 믿은 누군가가 **1년 뒤 13 GB 를 보고 "PVC 초과" 라고 오진**한다. 초과가 아니라 숫자가 거짓이다
- `Delete` 정책이라 PVC 오타 한 번에 서빙 DB 가 없어진다 (복구는 되지만 27분간 서비스가 없다)
- 새 기계에서 볼륨 인자를 틀리면 CronJob 이 **빈 `/lake` 를 보고 "0건" 을 정상 종료한다** — §7 의 그 형태

## §4. 백필을 k8s 로

### 결정

**Indexed Job 이다.** CronJob 도 Deployment 도 아니다.

```yaml
spec:
  completions: <plan.json 의 작업 단위 수>
  parallelism: 3                    # 병렬 확장은 이 숫자 하나
  completionMode: Indexed
  backoffLimit: 0                   # 재시도는 재개다. 처음부터가 아니다
  template:
    spec:
      restartPolicy: Never
      containers:
        - env:
            - name: EATBID_STATE_SUFFIX
              valueFrom: { fieldRef: { fieldPath: "metadata.annotations['batch.kubernetes.io/job-completion-index']" } }
```

- **CronJob 이 틀린 이유**: 백필은 **유한**하다. 주기적인 것이 아니다. 끝나면 스케줄이 남는다
- **Deployment 가 틀린 이유**: 완료라는 개념이 없다. `restart: unless-stopped` 는 지금 실제로 해를 끼치고 있다(§5)
- **Job 이 맞는 이유**: `completions` 가 **분모**고, 성공 개수가 **분자**다. `kubectl get job` 한 줄이 진척이다

### 워커 3개와 SQLite 상태파일을 어떻게 표현하나

**이미 있는 것 두 개를 그대로 쓴다.**

1. **작업 단위 = `(시도코드, 시작일, 종료일)`.** `backfill.py:24` 가 이미 그걸 받는다
   (`code, start, end = sys.argv[1], sys.argv[2], sys.argv[3]`).
   **지금은 사람이 손으로 넣는다 — 그게 재현 불가능한 지점이다.**
   → `infra/backfill/plan.json` 에 목록으로 넣고 커밋한다. `JOB_COMPLETION_INDEX` 가 그 배열의 첨자다
2. **상태 = 인덱스별 sqlite.** `config.py:49-54` 의 `EATBID_STATE_SUFFIX` 가 이미 파일을 갈라준다.
   인덱스를 suffix 로 쓰면 **워커 간 조율이 아예 필요 없다**

### 워커별 파일이면 병렬 확장이 어떻게 되나

**`parallelism` 숫자 하나다.** 상태가 안 겹치므로 잠금도 리스도 없다.
**단, 올리기 전에 반드시 막아야 할 것이 하나 있다:**

> 🔴 **`archive.py:39` 의 임시 파일 이름이 프로세스별이 아니다.**
> ```python
> tmp = path.with_suffix(".tmp")     # 5610615.xml.gz → 5610615.xml.tmp
> ```
> 같은 `bid_id` 를 두 워커가 동시에 받으면 **한 임시 파일에 섞여 쓰고, 잘린 gzip 이
> `replace()` 로 아카이브에 들어간다.** 지금은 사람이 기간을 겹치지 않게 나눠서 안 터진다.
> `plan.json` + `parallelism` 이 되는 순간 **겹침은 설정 오타 하나 거리**다.
> `.tmp.{os.getpid()}` — 한 줄이다. **`parallelism` 을 3 위로 올리기 전에.**

그리고 `drift.py:124-138` 은 공유 JSON 한 개를 read-modify-write 한다. 잠금이 없고
`:139-140` 이 `except Exception: pass` 라 **동시 쓰기 손실이 소리 없이 난다**(§7 에서 같이 고친다).

### 🔴 끝났는지 누가 아나 — **지금은 아무도 모른다**

**오늘 실제로 일어난 일:**

```
$ docker ps -a | grep r18c
r18c    Exited (0) 2 hours ago
$ sqlite3 state-18c.sqlite "select max(at) from done"
2026-08-28 10:32:25
```

**워커 하나가 두 시간 전에 종료 0 으로 끝났고 아무도 몰랐다.** 그리고 더 나쁜 것은,
**종료 0 은 성공의 증거가 아니다.** `internal.py:326-333` 의 `_extract_bid_ids` 는
`Dataset id="ds_list"` 가 없는 XML 을 받으면 **조용히 `[]` 를 반환**하고,
`backfill.py:28` 이 `백필 완료 code=18: {listed:0, ...}` 을 찍고 **0 으로 끝난다.**
**소프트 차단과 "그 기간에 데이터가 없음" 이 구별되지 않는다.**

### 그래서 — **분모를 파싱하라. 이 문서에서 줄당 값이 가장 큰 변경이다**

`TOT_CNT`("질의 전체 건수", `SOURCE-FIELDS.md:55`)가 **모든 목록 응답에 들어 있다.**
`_extract_bid_ids` 가 `ETN_BID_ID` 만 뽑고 **나머지 37개 컬럼과 함께 버린다**(`internal.py:326-333`).

한 필드를 살리면 **세 가지가 한꺼번에 답해진다:**

| 질문 | 지금 | `TOT_CNT` 를 읽으면 |
|---|---|---|
| 이 작업 단위가 끝났나 | 알 수 없다 | `done_count >= TOT_CNT` |
| 전체 백필이 얼마나 남았나 | 손으로 4개 sqlite 를 세고 분모가 없다 | `Σdone / ΣTOT_CNT` |
| 이 종료 0 이 진짜인가 | 구별 불가 | **`listed==0 && TOT_CNT>0` = 경성 실패** |

`CrawlState.done_count()`(`crawlstate.py:43`)와 `.failed()`(`:46`)는 **이미 존재하고
프로덕션 코드에서 한 번도 안 불린다.** 부를 상대(분모)가 없어서다.

**작업 순서**: `TOT_CNT` 파싱 → 종료 코드 정직하게 → 그 다음에 Argo 로 올린다.
**분모 없이 Argo 로 올리면 "성공한 Job" 이라는 거짓말이 하나 더 는다.**

(Argo Application·`automated` 끔·동기화 정책은 `ARCH-DELIVERY` §8 참조.)

### 비용 / 안 하면

`TOT_CNT` 파싱 + 종료 코드 **반나절** · `plan.json` + Indexed Job **반나절** · tmp 이름 **10분**.
안 하면 — **백필이 언제 끝나는지 영원히 모르고, 차단당한 날과 다 끝난 날이 같은 로그를 남긴다.**

- **부하가 줄지 않는다. 부하를 보는 눈만 줄어든다.** `_g_mult` 는 프로세스별이고 어디서도 합쳐지지 않는다.
  기계를 나누면 각 가드가 **자기 몫의 신호만** 보므로, 소스가 더 힘들어지는데 트립은 더 늦게 걸린다
- **§5 가 방금 내린 결정과 정면으로 부딪힌다.** 소스가 느려지고 있다는 신호를 받은 시점에
  IP 를 늘려 더 보내는 것은 **거절 신호를 우회하는 것**이다. 그 결과가 경성 차단이면
  잃는 것은 한 시간이 아니라 **raw 전부**다
- 그리고 지금은 **정지 장치 자체가 무효화돼 있다**(결함 1). **못 멈추는 상태에서 속도를 올리지 않는다**

**정직한 답: 기계를 늘려도 수집은 못 늘린다.** 늘릴 수 있게 되려면 결함 1·2·3(§5)을 먼저 고쳐야 하고,
고친 뒤에도 늘릴지는 **한 IP 에서 워커를 3→4 로 올려 보고 `p90` 이 어떻게 되는지**로 정한다 —
기계 대수가 아니라 소스의 반응이 정하는 숫자다.

**그런데 여분의 기계가 값하는 자리는 따로 있다 — §10-2 에 적었다.**

### 안 하면 무엇이 깨지나 — 전제를 하나 뒤집는다

리더의 원칙은 *"🔴 는 적재를 멈춘다(수집은 안 멈춘다 — 수집을 멈추면 raw 를 잃는다)"* 다.
**드리프트에는 맞고 차단에는 반대다.**

- 드리프트 = 원본이 **모양**을 바꿨다 → 계속 받아라. 받은 것은 나중에 다시 파싱된다

  그러면 raw 를 **한 시간이 아니라 영구히** 못 모은다

**진짜 차단에 멈추는 것이 raw 를 지키는 방법이지 잃는 방법이 아니다.**
`internal.py:264` 의 주석("정지 신호는 재시도로 삼키지 않는다")을 쓴 사람은 이미 이걸 알고 있었다.
**한 층 위에서 그 의도가 무효화됐을 뿐이다.**

*"오늘 실제로 첫 학교에서 죽어 7개 테이블이 빈 채로 남을 뻔했다"* — **남을 뻔하지 않았다.**

`load_postgres.py` 전량 경로에 **`commit()` 이 552행 한 곳뿐**이고, 모든 DELETE·INSERT·COPY 뒤에 있다.
`psycopg.connect()` 는 기본이 `autocommit=False` 다. **어디서 죽든 전량 롤백되고 어제 데이터가 남는다.**
`app.yaml:207` 이 이미 그렇게 적어 뒀다. **오늘 롤백된 것은 운이 아니라 구조다.**

**그리고 읽기가 막히지도 않는다.** `TRUNCATE` 가 아니라 `delete from` 이다(`:215-216`) —
`ROW EXCLUSIVE` 락은 **`SELECT` 를 막지 않는다.** MVCC 라 **27분 내내 독자는 직전 스냅샷을 본다.**

> **스테이징+스왑이 사줄 성질을 우리는 이미 공짜로 갖고 있다.**
> 대가로 적재 중 디스크 2배(9 GB→18 GB)와 **반쯤 실패할 수 있는 rename 단계**가 는다.

**증분 upsert 는 더 나쁘다.** upsert 는 키를 믿어야 하는데 우리 키를 못 믿는다 —
`load_postgres.py:283` 은 `(sido, sgg, inst)` 로 묶고 `:314` 는 `sid = f"{sgg}|{inst}"` 로 **sido 를 버린다.**
그리고 `:359` 의 `on conflict (id) do nothing` 이 충돌을 **조용히 버리면서**
그 학교의 `school_auctions` 행은 살아남은 학교 밑에 붙는다.
**전량 재구축이야말로 키 버그를 "다시 돌리면 고쳐지는 것" 으로 만들어 주는 성질이다.**

### 🔴 그래서 진짜 구멍은 다른 셋이다

**(1) 오늘 만든 드리프트 정지 장치가 클러스터에는 존재하지 않는다.**

```python
drift.py:19-20   _BASELINE_PATH = _BASE / "docs" / "source-fields.json"
Dockerfile:15-17 COPY src/ ./src/ ; COPY scripts/ ./scripts/ ; COPY tools/ ./tools/
```
**`docs/` 가 이미지에 없다.** `.dockerignore` 도 없다. 그러면:
```python
drift.py:36-43   except Exception:  _baseline = {"blocks": [], "keys": {}, …}
drift.py:48-49   if not b.get("keys"): return []
```
**`inspect()` 가 모든 공고에 대해 `[]` 를 돌려준다.** STOP 이 기록될 수 없고,
`load_postgres.py:197-207` 의 중단 게이트는 **항상 0건을 보고 통과한다.**
🔴 로 적재를 멈추게 만든 장치가 **한 번도 무장된 적이 없다.**
→ `COPY docs/ ./docs/` **한 줄 + 기준선이 실제로 로드됐는지 단언.**
**기준선을 못 읽으면 그것 자체가 STOP 이어야 한다.** 지금은 통과 사유다.

**(2) `--open-only` 는 게이트를 통째로 건너뛴다.**
`:183-195` 에서 반환하고 게이트는 `:200` 에 있다. **그런데 `:157` 의
`delete from open_auctions` 는 그대로 실행한다.** 이 경로가 **평일 하루 최대 22회** 돈다.

**(3) 🔴 급감 가드가 daily-refresh 에서 한 번도 무장된 적이 없다 — 실측 증거 있음**

```python
fetch_open.py:140-145   prev_n = None
                        try:  prev_n = len(json.load(open(OUT)))
                        except Exception:  prev_n = None
fetch_open.py:155       if FULL and prev_n and prev_n > 0 and len(open_aucs) < prev_n * 0.5:
```
**`None` 은 falsy 다.** 직전 파일을 못 읽으면 가드가 **실패하는 게 아니라 꺼진다.**

**2026-08-27 22:00 UTC, 무인으로 실제로 일어난 일** (`kubectl logs daily-refresh-29797800-chlpc`):
```
김해 진행중 1건 → /app/data/bidboard/open_auctions.json
  open_auctions: 1
```
**111건 → 1건이 통과했다.** 직전 파일 경로가 어긋나 있었고(→ `ARCH-DELIVERY` §0-1),
그래서 `prev_n = None` 이 됐고, 그래서 50% 급감 가드가 **스스로 꺼졌다.**

`failing-loudly.md` 가 정확히 이 경우를 적어 뒀다:
> *"위험한 건 0이 아니라 3이다."* · *"두 겹이면 한쪽만 고쳐선 안 잡힌다."*

로더의 0건 방어(`load_postgres.py:152-155`)도 **0 에만 걸리므로 1 은 통과한다.**
**두 겹이 다 뚫렸고, 뚫은 것은 같은 원인 하나다.**

→ **`prev_n is None` 은 우회가 아니라 `problems` 여야 한다.**
전량 모드에서 직전값을 못 읽는다는 것은 "판정할 수 없다" 이고,
**"판정할 수 없다" 는 "괜찮다" 가 아니다.**

**(4) `crawl-guard.json` 을 로더가 읽지 않는다.** `load_postgres.py` 에 `guard` 검색 0건.
4번 후퇴하고 절반만 받아온 크롤도 **정상으로 적재된다.**

**(5) 레이크 parquet 쓰기가 원자적이지 않다.** `lake.py:76` 은 `.tmp` 도 `os.replace` 도 없이
최종 경로에 바로 쓴다. 죽으면 **잘린 parquet 이 남고**, `connect()` 가 `**/*.parquet` 를
무조건 glob 하므로(`lake.py:124`) **그 테이블의 모든 조회가 영구히 깨진다.**
같은 리포의 `fetch_open.py:170-178` 은 **JSON 에 대해 이미 tmp+rename 을 한다** — 레이크에만 없다.

## §8. 관측 — 무인 운영에서 사람이 어떻게 아나

### 결정

**GitHub Actions 스케줄 워크플로가 R2 의 `status.json` 을 읽고 GitHub Issue 하나를 여닫는다.
새 인프라는 없다.** 그런데 **그 전에 두 가지가 먼저다.**

### 근거 — 문제는 "파일로만 남는다" 가 아니다. **아무도 안 읽는 경로에 쓰고 있다**

| 산출물 | 실제 경로 | 결과 |
|---|---|---|
| `source-drift.json` | `drift.py:21` → `_BASE/data/…` = **`/app/data`**. `EATBID_DRIFT_LOG` 는 어느 매니페스트에도 없다 | **파드가 끝나면 지워진다.** 폴링 파드와 daily-refresh 파드는 서로의 기록을 본 적이 없다 |
| `crawl-guard.json` | `internal.py:218` → 기본값 **상대경로** `data/crawl-guard.json` | CWD 에 달려 있다 |
| 드리프트 기준선 | `docs/source-fields.json` | **이미지에 없다**(§7-1) |

**누적 기록이 애초에 누적되지 않는다.** 알림 설계를 하기 전에 **기록이 파드보다 오래 살아야 한다.**

### 단계 — 순서가 중요하다

**1단계 (비용 0, 반드시 먼저): 신호 파일을 `/lake` 로 보낸다.**
`EATBID_DRIFT_LOG=/lake/source-drift.json` · `EATBID_GUARD_LOG=/lake/crawl-guard.json`.
**환경변수 두 개다.** 기록이 파드보다 오래 못 살면 그 뒤 설계는 전부 무의미하다.

**2단계 (거의 0): Job 이 실제로 실패하게 만든다.**
쿠버네티스는 **Job 실패를 이미 알려준다.** 문제는 지금 거의 아무것도 실패하지 않는다는 것이다 —
소프트 차단은 종료 0(§4), 가드 정지는 삼켜지고(§5), 드리프트는 기준선을 못 읽고(§7-1),
급감은 가드가 스스로 꺼진다(§7-3). **종료 코드를 정직하게 만들면 `kubectl get jobs` 가 공짜로 1차 신호가 된다.**

**3단계: 스케줄 워크플로 + Issue 하나.**
- **GitHub Actions 인 이유**: 스택 안이고, **호스트가 죽어도 돈다.** 호스트에 붙은 알림은
  호스트가 죽는 그 순간을 못 알린다
- **Issue 인 이유**: 알림은 흘러가고 Issue 는 **상태를 갖는다.** 조건이 풀리면 닫히고,
  이력이 남는다. **하나만 쓴다** — 매일 새 Issue 는 곧 안 읽는 Issue 다

### `status.json` 이 담아야 하는 것 — **이게 이 절의 전부다**

**분자만 적지 마라. 분모를 같이 적어라.** `thresholds-we-invented.md` T1 —
*"자르지 말고 세어서 같이 내려보내라."*

```json
{ "at": "...",
  "backfill":  { "done": 221003, "total": 371000, "units_done": 12, "units": 47 },
  "open":      { "now": 111, "prev": 111, "guard_armed": true },
  "raw":       { "files": 223165, "prev": 212338 },
  "lake":      { "auctions": 221003, "prev": 210441 },
  "pg":        { "firm_bids": 9147891, "prev": 9147891, "loaded_at": "..." },
  "guard":     { "trips_24h": 4, "max_backoff": 4.0 },
  "drift":     { "stops": 0, "baseline_loaded": true } }
```

두 필드가 특히 중요하다:
- **`guard_armed` / `baseline_loaded`** — *"문제 없음"* 과 *"검사가 안 돌았음"* 을 가른다.
  §7-1·§7-3 두 사고가 정확히 이 구별이 없어서 났다. **꺼진 검사는 통과가 아니다**
- **모든 `prev`** — 아래의 단조성 단언이 여기서 나온다

### 그리고 단언 하나 — **감소는 언제나 결함이다**

raw 는 append-only 고 Postgres 는 레이크에서 전량 재구축된다.
**따라서 모든 계수는 단조 증가여야 한다.** 어떤 것이든 줄면 **정상 종료여도 실패다.**

**한 줄이 111→1 부류를 모든 저장소에 대해 한꺼번에 잡는다.** 임계값이 아니라 방향이라서
`thresholds-we-invented.md` 가 경고하는 "우리가 세운 숫자" 를 하나도 안 만든다.

### 안 하는 것

**Cloudflare 는 여기 답이 아니다.** 상태 페이지를 띄울 수는 있지만 **상태 페이지는
사람이 보러 가야 하는 것**이고, `.claude/rules` 가 이미 *"사람 기억에 의존하는 절차가
우리를 물었다"* 고 적어 뒀다. **Issue 는 찾아온다.**

**Prometheus·Grafana·Alertmanager 를 넣지 마라.** 1인 프로젝트다.
오늘 잰 사고 전부가 *"값이 틀렸는데 아무 소리도 안 났다"* 형태다 —
그건 **종료 코드 하나와 Issue 하나**지 시계열 DB 가 아니다.
(Kafka·Airflow 는 더 말할 것도 없다. 우리 처리량은 **3 req/s** 고 작업 그래프는 **3단계 직선**이다.)

### 비용 / 안 하면

환경변수 **10분** · 종료 코드(§4·§5 와 겹침) · `status.json` + 워크플로 **반나절**.
안 하면 — **오늘처럼 워커가 두 시간 전에 죽어도, 111건이 1건이 되어도 아무도 모른다.**
둘 다 오늘 실제로 일어났고 사람이 손으로 뒤져서 찾았다.

## §9. 보존 정책 — 커지는 속도와 1년 뒤

### 결정

**raw 는 영구 보존. parquet 은 자산이 아니라 캐시다 — 압축(compaction)하고, `parquet_v2` 는 정리한다.
보존 정책을 만들지 말고, 지켜지는지 검사되는 숫자를 만들어라.**

### 성장률 — 계산식과 함께

**공통 분모**(§1-6, **실측 갱신**): 정상 상태 **월 12,254건**(007) → 전체 상태로 넓히면
**÷0.9251 = 월 13,246건**. **백필 잔량 약 183,000건**은 1회성으로 더해진다.
*(초판은 월 12,100 · 잔량 15만이었다. 부산 보유율 34.5% 실측으로 잔량이 22% 늘었다.)*

| 저장소 | 단가 (실측) | 오늘 | +백필 18.3만 | +12개월 15.9만 | **1년 뒤** |
|---|---|---|---|---|---|
| **raw** | 8,170 B/파일 | 2.2 GB / 223k 파일 | +1.50 GB / +183k | +1.30 GB / +159k | **약 5.0 GB / 565,000 파일** |
| **parquet** | 1,760 B/공고 | 553 MB / 1,272 파일 | +322 MB | +280 MB | **약 1.16 GB / 약 6,400 파일** |
| **Postgres** | 492 B/행 · 41.4행/공고 | 5,478 MB / 915만 행 | +7.5 GB | +6.5 GB | **약 14 GB / 2,330만 행** |

**여유**: F: 243 GB · 노드 볼륨 859 GB(그 아래는 C: 909 GB). **디스크는 몇 년간 문제가 아니다.**

### 그런데 두 가지가 조용히 커진다

**(1) 파일 수 — raw 의 진짜 비용은 용량이 아니라 개수다.**
223k → **565k**. 매 백업 동기화·매 재파싱·매 `find` 가 그 트리를 다 걷는다.
§2 의 샤드 tar 가 이걸 미리 흡수한다(**256개는 늘어도 256개**) — 늘어난 잔량 추정이
이 결정을 더 굳힌다.

**(2) 재파싱 시간 — 복구 시간이 두 배 이상이 된다.**
**84.1 파일/s 실측**이므로 565,000 / 84.1 = 6,718초 = **112분 + 파케이 쓰기 → 약 2시간 10분.**
오늘의 "50분" 이 1년 뒤 "2시간 10분" 이다. **여전히 감당 가능하고, 그게 요점이다 —
가정하지 말고 숫자를 말해 두면 놀랄 일이 없다.** (그리고 §10-2 의 두 번째 기계가
정확히 이 작업을 가져갈 수 있다.)

### 그래서 — 지우지 않는다. 두 개를 압축하고, 숫자 하나를 단언한다

**(a) raw: 아무것도 안 지운다.** 대체 불가고 1년에 1.3 GB 다. **논의가 필요 없다.**

**(b) parquet 을 월 1회 compaction 한다 — 닫힌 달을 테이블당 파일 하나로.**
지금 1,272개, auctions 의 median 이 **31.7 KB** 다. 공고 200건마다 파일 하나가 생기기 때문이다
(`crawl.py:23`).

**안전한 이유가 이미 코드에 있다**: 중복 제거가 **읽기 시점의 "파일명이 큰 것이 이긴다"**
(`lake.py:130-139`)이고 파일명이 `part-{time_ns:020d}-…`(`lake.py:72-76`)다.
**더 새 이름으로 쓴 compaction 결과가 자기 입력들을 자동으로 덮는다.**
→ **compaction 은 지우기가 아니라 append 다.** 입력 파일 삭제는 행 수 대조 후에 별도로 한다.

**(c) `parquet_v2`(161 MB) 를 정리한다.** 지금 `parquet`(389 MB) 과 나란히 있고
**둘의 관계가 어디에도 적혀 있지 않다.** 로더는 `parquet` 을 읽는다(`load_postgres.py:209`).
**관계가 안 적힌 레이크 두 개는 누군가 틀린 쪽을 읽는 조건이다.** 승격하거나 지우거나, 둘 중 하나.

**(d) 단조성 단언**(§8) — **이게 보존 정책을 대신한다.**
계수가 줄면 실패. 방향만 보므로 **우리가 만든 임계값이 하나도 안 생긴다.**

### 비용 / 안 하면

compaction 스크립트 **반나절** · `parquet_v2` 판정 **1시간** · 단언은 §8 에 포함.
안 하면 — 파일 수가 조용히 자라 **복구 시간과 백업 시간만 늘고 아무도 그 곡선을 안 본다.**
그리고 **레이크가 두 개인 채로 남는다.**

## §10. 인스턴스 둘 · 여분의 기계

### 10-1. 동시 수집은 하지 않는다 — 판정만 남긴다

**요구가 아니라 아이디어였다. 다음 사람이 다시 묻지 않게 판정만 적어 둔다.**

**두 클러스터가 각자 수집하면 넷이 깨진다:** eaT 에 가는 요청이 두 배가 되고(§5 가
지금도 여유가 없다고 말한다), **raw 아카이브가 갈라져 어느 쪽도 전체가 아니게 되며**,
상태 sqlite 이 두 벌이 되어 같은 `bid_id` 를 양쪽이 각각 받고,
로더가 `delete` 로 시작하므로 둘이 같은 DB 를 보면 서로를 지운다.

**막으려면 리더 선출이나 공유 스토리지가 필요하다.** 그런데 두 클러스터는 **서로 다른 apiserver** 라
k8s Lease 로는 안 되고, 밖에 락을 둘 곳(공유 Postgres·Redis·객체 스토리지의 조건부 쓰기)을
새로 만들어야 한다. **1인 프로젝트 · 3 req/s · 3단계 직선 파이프라인에 분산 락은 값하지 않는다.**

**그리고 값을 사지도 못한다** — 수집을 두 배로 늘리는 것이 §5 에서 **하면 안 되는 일**로 판정됐으므로,
동시 수집이 성공해도 얻을 것이 없다.

> **서빙(웹·서버)은 다르다.** 무상태고 DB 만 읽으므로 **둘이 떠도 아무 문제 없다.**
> 다른 곳에서 화면만 보고 싶은 것이면 **서빙만 띄우고 수집 CronJob 을 끄면 된다** —
> 그건 `ARCH-DELIVERY` 축(어느 매니페스트를 동기화하나)이지 이 문서 축이 아니다.

### 10-2. 그런데 여분의 기계가 값하는 자리는 있다 — **수집이 아니라 나머지 전부다**

리더가 원한 것은 *"기계를 놀리지 않는 것"* 이다. **수집은 못 주지만 셋을 줄 수 있고,
셋 다 지금 아무도 안 하고 있는 일이다.**

| # | 일 | 왜 두 번째 기계여야 하나 | 값 |
|---|---|---|---|
| **1** | **raw 2차 사본을 들고 있는다** — R2 에서 당겨서 | **다른 기계에 있는 사본이 진짜 백업이다.** 이 PC 의 C:\ 사본(§2-1)은 디스크 고장만 막는다 | **§2 가 통째로 닫힌다** |
| **2** | **월 1회 복원 드릴** — R2 에서 받아 풀고 매니페스트 대조 | 사람이 손으로 절대 안 하는 일이고, **안 해본 백업은 백업이 아니다**(§2-3) | 10분/월 |
| **3** | **재파싱·compaction 을 여기서 돌린다** | 순수 로컬 CPU다. **소스에 요청을 하나도 안 보낸다.** 1년 뒤 2시간짜리 작업(§9)이고, 본 기계는 그동안 서빙한다 | 본 기계 부하 0 |

**1번이 핵심이다.** 리더는 *"복제본이 백업이 된다는 손쉬운 답이 사라졌다"* 고 했는데 — **안 사라졌다.**
**복제본을 만드는 방법이 "각자 수집" 에서 "R2 에서 당기기" 로 바뀌었을 뿐이고, 그 편이 낫다:**
수집 복제본은 서로 다른 부분집합이라 **둘 다 불완전**하지만, R2 를 당긴 사본은 **정의상 동일**하다.

**필요한 것**: R2 읽기 토큰 하나와 `rclone` 하나. **클러스터도 ArgoCD 도 필요 없다.**
스케줄 한 줄이면 된다. **§2 의 R2 결정이 이 답까지 같이 사 준다 — 두 요구가 한 답으로 풀린다.**

## §11. 파이썬이 살 곳 — 로그·진행상황의 수명

> ⚠ `architect` 좌석이 `SPEC-LOGGING.md` 에서 **"무엇을 어떤 모양으로 남기나"** 를 쓴다.
> 여기서는 **저장·수명·용량**만 본다. 결론이 갈리면 리더가 조정한다.

### 결정

**(c) 를 고르되 좁힌다.** 리더의 초안과 갈리는 지점이 하나 있고, 그게 이 절의 요점이다.

| | 리더 초안 | **이 문서** |
|---|---|---|
| 로그 | → Postgres | **`/lake` 에 append-only JSONL 이 1차. Postgres 는 배송된 사본** |
| **진행상황** | → Postgres | **옮기지 마라. 이미 durable 하다. 없는 건 저장소가 아니라 독자다** |
| 백필 상태 sqlite | 옮기는 게 맞나? | **아니다.** §11-5 |

### 11-0. 먼저 — **전제 하나가 틀렸다. "상태를 들고 있을 데가 없다" 는 사실이 아니다**

> *"상태를 들고 있을 데가 없다 — 백필 SQLite 가 hostPath 에 얹혀 있다"*

**그 hostPath 가 `F:\Project\eat-bid\data` 다**(§0-1). raw 가 사는 바로 그 파일시스템이고,
**노드를 지워도 안 없어진다**(§0-2). `state.sqlite` 에는 **221,003행이 `at` 타임스탬프와 함께** 들어 있다.
**진행 기록은 이미 있고, 이미 영속적이고, 이미 시각까지 붙어 있다.**

그 증거가 이 세션이다 — *"지금 백필 어디까지 갔어?"* 를 나는 **sqlite 한 줄로** 답했다:
```
state.sqlite    done=183789 failed=2  ('2026-08-25 15:46:31', '2026-08-28 12:36:06')
state-18a…c     done=10753 / 16904 / 9557
```
**리더가 `find -newermt` 로 파일을 세야 했던 것은 저장이 없어서가 아니라 창구가 없어서다.**

> **없는 것은 저장소가 아니라 독자다. 그리고 분모다**(§4 의 `TOT_CNT`).
> **저장소를 옮겨도 그 둘은 안 생긴다.** 우리 규칙이 경고하는 형태 그대로다 —
> 이미 있는 사실의 두 번째 사본을 만드는 것.

### 11-1. 무엇을 남기나 — **요청 단위는 불가능하다. 계산해 보면 나온다**

| 입도 | 하루 행 | 연간 | 판정 |
|---|---|---|---|
| **요청당 1행** | 10,827 × 24 ≈ **260,000** | 약 9,500만 행 · **≈ 17 GB** | ❌ **서빙 DB 전체(5.5 GB)보다 3배 크다** |
| 공고당 1행 | 위와 사실상 같다 | | ❌ |
| **실행(run)당 1행** | CronJob 4 + 폴링 22 ≈ **30** | **약 11,000행 · 수 MB** | ✅ |

**실행 단위로 충분한지**를 이 세션의 사고 셋으로 검증하면:

| 오늘 겪은 것 | 실행 단위 기록으로 답해지나 |
|---|---|
| 워커가 두 시간 전에 종료 0 으로 죽었다 | ✅ 마지막 실행의 `ended_at`·`exit_code` |
| 111건 → 1건이 통과했다 | ✅ 실행마다 `open_now` + `open_prev` |
| 가드가 4번 트립했다 | ✅ `crawl-guard.json` 이 이미 200건 상한(`internal.py`) |
| 드리프트 STOP 이 서 있다 | ✅ `source-drift.json` 이 이미 500건 상한(`drift.py:127-134`) |

**넷 다 실행 단위로 답해진다.** 요청 단위 기록이 필요했던 사고가 **하나도 없다.**
`thresholds-we-invented.md` 를 거꾸로 적용한 것이다 — **자를 근거가 있으면 세지도 마라.**
(요청 단위가 필요해지면 그때는 로그가 아니라 `state.sqlite` 의 `failed` 테이블이 답이다. 이미 있다.)

### 11-2. 로더의 `delete` 와 어떻게 격리하나 — **스키마 경계로**

`load_postgres.py` 의 DELETE 는 **이름을 하나씩 적은 8개**다
(`:157`, `:215`, `:216`×2, `:393`, `:457`×2, `:510`). 전량 삭제가 아니다.
**그래서 오늘 새 테이블을 추가해도 안전하다 — 그런데 그건 "우연히" 안전한 것이다.**

**`ops` 스키마를 따로 판다.** 로더는 `public.*` 만 만지고 마이그레이션이 `ops.*` 를 만든다.
*"로그 테이블은 로더 목록에 넣지 마라"* 는 **사람이 기억해야 하는 규칙**이고,
`.claude/rules` 는 그런 절차가 이미 우리를 물었다고 적어 뒀다.
**스키마 경계는 기억이 아니라 코드 경로가 지킨다.**

### 11-3. 로깅 실패가 작업을 죽이면 안 되는데 `|| true` 는 금지 — **버리지 말고 미뤄라**

**원칙은 "실패해도 계속하지 마라" 가 아니라 "실패를 안 보이게 하지 마라" 다.**
`|| true` 가 금지된 이유는 **사실을 지우기 때문**이다. 그래서:

```
작업  →  /lake/ops/runs.jsonl 에 한 줄 append   (여기가 1차 싱크다)
        ↓  (별도 shipper CronJob)
        ops.run_log  로 옮기고 커서를 전진시킨다
```

- **DB 쓰기가 실패하면** — 줄은 `/lake` 에 그대로 있고 다음 회차가 가져간다. **아무것도 안 사라진다**
- **shipper 가 계속 실패하면** — `runs.jsonl` 과 `ops.run_log` 의 차이가 벌어진다.
  그 **격차 자체가 `status.json` 의 필드**(§8)다. **조용히 실패할 수가 없다 — 격차가 자란다**
- **`/lake` append 가 실패하면** — 디스크가 없다는 뜻이고, **그때는 작업이 죽어야 맞다. 시끄럽게.**

**`|| true` 와의 차이**: `|| true` 는 **버린다**. 이건 **미룬다.** 사실이 살아남는다.

### 11-4. 부트스트랩 — **이 설계에서는 질문이 사라진다**

1차 싱크가 파일이라 **DB 가 아직 없는 순간에도 쓸 곳이 항상 있다.**
첫 적재든 마이그레이션 실패든 `runs.jsonl` 은 그대로 쌓이고, DB 가 생기면 shipper 가 밀어 넣는다.
**"로그를 쓰려면 DB 가 먼저 있어야 한다" 는 순환이 애초에 안 생긴다.**
리더 초안(로그 → Postgres 직행)에서는 이게 실제 문제가 되고, **파일 1차가 그걸 없앤다.**

### 11-5. 백필 상태를 DB 로 옮기나 — **아니다**

| | SQLite on `/lake` (지금) | Postgres |
|---|---|---|
| 내구성 | **raw 와 동일**. 노드 삭제로도 안 죽는다(§0-1) | PVC — **노드와 함께 죽는다**(§0-2) |
| 수집의 의존성 | 파일 하나 | **네트워크 + DB 가용성** |
| `mark_done` | 로컬 fsync (`crawlstate.py:32-35`, 행마다 commit) | flush 당 왕복 200회, 시간당 10,827건 |
| 워커별 분리 | `EATBID_STATE_SUFFIX` 로 이미 됨 | 잠금·리스를 새로 만들어야 |

**결정적인 것은 두 번째 줄이다.** 옮기면 **Postgres 가 *수집*의 의존성이 된다.**
지금은 DB 가 죽어도 백필이 계속 돈다. 옮기면 DB 가 죽을 때 **수집이 멈춘다** —
그리고 이 문서 전체가 *"수집을 멈추면 raw 를 잃는다"* 위에 서 있다.
**더 약한 것에 더 중요한 것을 매달지 않는다.**

**그리고 옮겨도 창구 문제가 안 풀린다.** 창구를 막는 것은 저장 위치가 아니라
**분모가 없다는 것**(§4)이다. `TOT_CNT` 없이 Postgres 로 옮기면
**질의는 되는데 답이 여전히 "221,003 / 모름" 이다.**

### 11-6. (b) 긴 수명 파이썬 서버를 안 쓰는 이유 — 저장 축에서 하나 더

리더의 근거(*"크론 4개가 한 프로세스가 되고, 우리는 그 하나가 죽어서 며칠 몰랐던 전력이 있다"*)에 동의한다.
**저장 축에서 하나를 더한다:**

**긴 수명이 로그를 durable 하게 만들지 않는다.** 긴 수명 프로세스의 로그도 `kubectl logs` 고,
**재시작하면 똑같이 사라진다.** (b) 는 로그 문제를 **푸는 게 아니라 미룬다.**
그리고 SQLite 핸들을 재시작 너머로 들고 있게 되어 **CronJob 에는 없는 손상 표면**이 하나 는다.

**로그를 오래 살게 하는 것은 프로세스 수명이 아니라 파드 밖 싱크다.** §11-3 이 그것이고,
그건 **(a) CronJob 그대로에 붙는다.**

### 11-7. 그래서 창구는 — **§8 의 `status.json` 이 그대로 답이다**

새 서버를 띄우지 않는다. 이미 있는 것 두 개를 쓴다:

```
CronJob → /lake/ops/runs.jsonl  +  /lake/status.json     (파일. 파드보다 오래 산다)
   ↓ shipper                          ↓ R2
ops.run_log (SQL 질의)          GitHub Actions → Issue (§8)
                                     ↓
                          server 가 /api/ops/status 로 그대로 내려보낸다
```

**서버는 이미 떠 있고 이미 노출돼 있다**(`app.yaml` 에 `/api` Ingress, `@Get` 40여 개).
**엔드포인트 하나면 *"지금 백필 어디까지 갔어?"* 가 브라우저에서 답해진다.**

### 비용 / 안 하면

`runs.jsonl` append **1시간** · shipper CronJob **반나절** · `ops` 스키마 **30분** ·
`/api/ops/status` **1시간**. **(b) 를 안 만들어서 아낀 시간이 이보다 크다.**

안 하면 — **오늘과 같다.** 워커가 언제 죽었는지 `docker ps` 로, 진행률을 `sqlite3` 로,
STOP 이 서 있는지 JSON 을 열어서 확인한다. **전부 사람이 기억해서 찾아가야 하는 절차다.**

**~~취소선~~ 은 이 문서를 쓴 뒤 실제로 재서 닫은 항목이다.
둘 중 하나는 내 가정이 틀렸음이 드러났다 — 그래서 재는 것이다.**

### 🔴 이 절이 존재하는 진짜 이유 — **"있다"와 "돈다"는 다른 사실이다**

**다섯이 전부 같은 형태다: 코드에 존재하고, 리뷰를 통과했고, 아무 일도 안 하고 있었다.**
그리고 다섯 중 **어느 것도 예외나 경고를 내지 않았다** —
`thresholds-we-invented.md` 가 임계값에 대해 적은 문장이 **장치에도 그대로 적용된다.**

> **규칙**: 안전장치를 설계에 근거로 인용할 때는 **그것이 실제로 발동한 기록**을 같이 대라.
> 없으면 *"있다"* 가 아니라 *"있는데 발동 기록이 없다"* 라고 적어라.
> 이 문서 초판이 §5 를 쓸 때 정지 장치가 동작한다고 전제했고, **틀렸다.**
> `crawl-guard.json` 을 열어 `stopped` 를 세어 보는 데 10초 걸렸다.

**§8 의 `status.json` 에 `guard_armed`·`baseline_loaded` 를 넣자고 한 이유가 이것이다** —
*"문제 없음"* 과 *"검사가 안 돌았음"* 을 화면에서 가르지 못하면 이 표는 계속 길어진다.

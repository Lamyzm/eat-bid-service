# SPEC — 알림 1종: "내 자격 지역 새 공고 N건"

근거: `docs/SIM-USERFLOW.md` 실측 — 3주 21일 중 열 이유가 있는 날 8일, 김해 축산은 월 9~10일 클러스터 발주,
앞 11일 연속 빈 화면. **최대 위험은 이탈이 아니라 망각**이고, 알림 없는 "3주 연속 자발 사용" 게이트는
아버지 기억력 테스트다. 따라서 알림은 v2 백로그가 아니라 **G1 생존 조건**이다.

## 0. 배치 #6("미리 정해두기")과의 경계 — 변호하지 않고 판정

**두 기능은 같은 문제("공고 없는 날")를 두 번 풀고 있다.** sim이 옳다.

| | 미리 정해두기(#6) | 알림(#7) |
|---|---|---|
| 전제 | 공고 없는 날에도 **사용자가 화면을 연다** | 공고 없는 날엔 **안 연다** |
| 해결 방식 | 빈 날에 할 일을 준다 | 빈 날을 없애준다(뜬 날만 부른다) |
| sim 판정 | F3 "아무도 안 정한다" = 닭·달걀 | 리듬(월 클러스터)에 정확히 대응 |

**판정: #6을 뒤로 미룬다.** #6의 F3(사산 위험)은 "공고 없는 날 접속"을 전제로 하는데, sim은 그 전제 자체를
부정했다. 순서를 뒤집는다 — 알림이 사람을 데려오고(뜬 날), 그 사람이 화면에서 값을 정하게 된 뒤에야
"미리 정해두기"가 살 자리가 생긴다.

**#6 축소안**: 화면 1장 + 빈날 블록 + 배지 전부 보류. **분석판 산출기 버튼 1개(값 저장)만** 남겨
알림 문구에 `미리 정해둔 값 90.05`를 실을 재료로 쓴다. 화면은 저장이 3건 이상 쌓인 뒤 만든다.

## 1. 채널 — 텔레그램 채택

유일한 기준: **아버지가 실제로 보는가.**

| 채널 | 판정 |
|---|---|
| **텔레그램** | ✅ 채택 — 이 세션에 MCP가 붙어 있어 오늘 발송 가능, 비용 0, 봇 승인만 1회. 유일 약점: 아버지가 평소 안 쓰는 앱 → **G1은 관찰 실험이지 대중 출시가 아니다.** 첫 사용자 1명이 설치·승인 1회 하면 끝 |
| 카카오 알림톡 | ❌ 지금은 — 사업자 채널·템플릿 심사·발송비. 아버지가 보는 채널이라는 점에서 **최종 정답이지만 G1 속도를 죽인다**. G2 이후 전환 |
| 문자(SMS) | △ 도달률 최고·설치 불필요, 건당 과금 + 발신번호 등록. 텔레그램 실패 시 대안 |
| 이메일 | ❌ 60대 사장이 안 본다 |

**결론**: G1 = 텔레그램 1인 실험 → G2 진입 시 알림톡/문자로 채널 교체(문구·트리거는 그대로 재사용).

## 2. 트리거 — 하루 1회 09:00, 있을 때만

실측 리듬: 클러스터 날엔 15~20건이 한꺼번에 뜬다. **건당 발송은 소음이고 즉시 차단 사유다.**

- **정시 요약 1회/일 · 09:00 KST**, 새 공고 0건이면 **아무것도 보내지 않는다**(빈 알림 금지 = 신뢰의 핵심)
- 발송 기준 = "지난 발송 이후 처음 본 bidNo" (open_auctions diff, 상태 테이블로 중복 방지)
- 예외 1건만: **마감 3시간 전인데 투찰함 표시가 없는 공고**가 있으면 그 시각에 1회(하루 최대 1건, 마감 사고 방지)
- 상한: 하루 최대 2건(정시 1 + 마감 1). 그 이상 어떤 이유로도 발송 없음
- 일요일·공휴일도 동일(개찰은 평일이지만 공고 등록은 주말에도 있음 — 없으면 어차피 안 감)

## 3. 내용 — 한 줄 + 최대 3줄 목록

```
김해시 새 공고 4건 (축산 2 · 공산 1 · 수산 1)
· 장유고 축산 · 기초 1,639만 · 하한 90 · 마감 8/30 10:00
· 주촌초 공산 · 기초 932만 · 하한 90 · 마감 8/30 10:00
· 외 2건
오늘 화면에서 보기 → https://<도메인>/dashboard/today
```
- 헌법: 예측·추천가·해석 라벨 0. 전부 공고 원문 사실(기초가·하한·마감). n은 "4건"이 곧 표본 수
- 4건 이상이면 상위 3건(마감 임박순) + "외 N건"
- **링크는 오늘 화면 1개**(공고별 링크 나열은 소음, 오늘 화면이 이미 목록)
- 마감 경고는 별도 형식: `주촌초 공산 마감 3시간 전 · 투찰함 표시 없음 → <링크>`
- 금지: "지금이 기회", "낙찰 유력", 이모지, 인사말

## 4. 끄기·조절 — 최소 3개 스위치

`[나] > 알림` 화면(신규 컨트롤 3개 상한):
1. **전체 끄기** (기본 켜짐, 텔레그램 연결 시)
2. **품목 선택** (자격 지역은 이미 설정값 재사용 — 지역 스위치 신설 안 함)
3. **마감 경고 끄기**
그 외 시각·빈도 설정은 만들지 않는다(설정 증식이 곧 이탈). 텔레그램 `/stop` 으로도 즉시 중단 가능.

## 5. 구독 모델 — 로그인 없이, 코드 연결

G1이 1인 실험이므로 **로그인 필수화 금지**.

1. [나]>알림 에서 `연결 코드` 6자리 발급(5분 만료) → 사용자가 봇에게 `/link 483920` 전송
2. 서버가 `user_alert(userId|sessionKey, chatId, categories, enabled)` 저장 — 게스트는 브라우저 워크스페이스 키로,
   Clerk 도입 후 userId로 자동 승격(userBiz 병합 규칙 재사용)
3. 자격 지역·사업자는 기존 설정을 그대로 읽는다(알림 전용 설정 신설 없음)
4. 해제: 화면 버튼 또는 `/stop`

스키마 — `packages/shared/src/db/schema/user-data.ts`(재적재 보존):
```ts
export const userAlert = pgTable("user_alert", {
  ownerKey: varchar("owner_key", { length: 64 }).primaryKey(), // userId 또는 workspaceId
  chatId: varchar("chat_id", { length: 32 }).notNull(),
  categories: jsonb("categories").$type<string[]>(),           // null = 전체
  deadlineWarn: boolean("deadline_warn").notNull().default(true),
  enabled: boolean("enabled").notNull().default(true),
  lastSentAt: timestamp("last_sent_at"),
});
export const alertSent = pgTable("alert_sent", {               // 중복 발송 방지
  ownerKey: varchar("owner_key", { length: 64 }).notNull(),
  bidNo: varchar("bid_no", { length: 32 }).notNull(),
  sentAt: timestamp("sent_at").notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.ownerKey, t.bidNo] })]);
```

## 6. 서버 구조 — 신규 인프라 0

- **기존 daily-refresh CronJob의 꼬리에 붙인다**(07:00 KST 수집·재적재 완료 후 09:00 발송 스텝).
  새 CronJob 1개만 추가하거나, 아예 daily-refresh 스크립트 마지막 단계로 편입 → 신규 인프라 없음
- 발송 주체: dataplane 컨테이너에서 텔레그램 Bot API `sendMessage` 직접 호출(HTTP 1건). 봇 토큰은 k8s Secret
- 마감 경고는 별도 CronJob 1개(매시 정각, 마감 3h 이내 & 투찰함 미표시 스캔) — 정시 요약과 상태 테이블 공유
- 서버 API 3개: `POST /api/alert/link`(코드 발급) · `POST /api/alert/verify`(봇 웹훅에서 코드 검증) · `PATCH /api/alert`(설정)
- 봇 수신(`/link`, `/stop`)은 폴링(getUpdates) 1분 주기로 충분 — 웹훅용 공개 URL 불필요(cloudflared 의존 제거)

## 7. 실패 시나리오 3

**F1. 오탐 = 늑대소년 (치명, sim S-2가 실증)**
발주 예정 "도래"가 방학 공백을 몰라 주촌초를 8/23부터 몇 주째 걸어둔다. 이걸 알림으로 쏘면 첫 오탐에 신뢰가 죽는다.
→ 방어: **알림은 예보를 절대 보내지 않는다.** 발송 대상은 `open_auctions`에 실재하는 공고뿐 — "뜰 것 같다"가 아니라
"떴다"만. 예보는 화면 안에 머문다. (이 한 줄이 이 스펙에서 가장 중요한 제약이다.)

**F2. 소음 → 차단**
클러스터 날 15~20건을 건당 발송하거나, 새 공고 0건인 날에도 "오늘은 없습니다"를 보내면 즉시 음소거된다.
→ 방어: 하루 1회·있을 때만·상한 2건. 빈 알림 영구 금지. 첫 주 발송량을 로그로 확인 후 상한 재조정.

**F3. 링크만 보고 안 들어온다 (사업적 실패)**
알림 한 줄에 기초가·하한·마감이 다 있어서 그것만 읽고 NeaT로 직행한다 → 서비스는 안 열림, 게이트 미달.
→ 방어: 알림에는 **공고의 사실만** 담고 우리 재료(구간·몰림·리허설·내 기록)는 담지 않는다.
"판단 재료는 화면에" 원칙 — 알림은 초대장이지 요약본이 아니다. 측정: `alert_click` 이벤트로 유입 전환율 추적,
2주간 클릭률 30% 미만이면 문구에서 정보를 더 덜어낸다.

## 10. sim이 지목한 "버려도 되는 것" — 판단

- **①분석판 렌즈 확장(더보기 4개 심화·호버 리플레이 고도화·인쇄 리포트)** → **백로그에서 내린다(동의).**
  현재 렌즈 3개로 이미 결정이 가능하고, 심화는 "아직 오지도 않은 파워유저"를 위한 것. G3 이후 재검토.
  단 예외 1건: 인쇄 리포트는 G2(남 사장에게 보여줄 물건)에서 다시 필요해질 수 있으니 **폐기가 아니라 보류**.
- **②시장 지도 v2 지오코딩** → **내린다(동의).** 학교 단위 좌표는 "있어 보이는" 가치뿐이고, 확장 검토(2호 사무소)는
  연 1회 의사결정이라 재방문·결제 어디에도 안 닿는다. 현 시군구 버블로 충분.
- 대신 그 자리에 들어갈 것: 알림(#7) → 납품(#E 이미 라이브) → G1 관찰 → 그 결과로 다음 순위 결정.

## 갱신 (배치 #9) — "마감 3시간 전" 트리거는 폴링 없이 성립하지 않는다

**문제**: 현재 크롤은 일 1회 03시. 공고 수명 최소 0일(당일 게시·당일 마감)이라
03시 스냅샷에 없는 공고는 마감 경고 대상이 될 수 없고, 있던 공고도 마감 시각 변경·취소를 반영하지 못한다.
즉 §2의 마감 경고는 **장중 폴링(≥1시간)이 붙기 전까지 설계상 불완전**하다.

**폴링 도입 전 대체안 (순서대로)**
1. **범위 한정 발송**: 03시 스냅샷에 존재하고 마감이 당일인 공고에 한해서만 경고. 문구에 근거 명시 —
   `03시 기준 목록입니다. 이후 올라온 공고는 포함되지 않습니다.`
2. **정시 요약에 마감 목록 병합**: 별도 시각 발송 대신 09:00 알림 하단에 `오늘 마감 N건`을 붙여
   하루 1회로 유지(발송 상한 2건 → 1건으로 감소, 소음 위험도 감소)
3. **일괄 표와 연동**(배치 #9): 표의 `NeaT에 입력함` 미체크 수를 09:00 알림에 포함 —
   `어제 적어둔 29칸이 아직 NeaT 미확인입니다`. 폴링 없이도 미투찰 사고를 잡는 유일한 경로
4. 폴링 도입 후: 원안(마감 3시간 전 개별 발송, 하루 상한 2건)으로 복귀

**F1(늑대소년) 재확인**: 위 대체안 어디에도 예보는 실리지 않는다. 발송 대상은 여전히 실재 공고뿐.

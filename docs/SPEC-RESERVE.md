# SPEC — 미리 정해두기 (예약 투찰안 재명명)

목적: **공고 없는 날의 할 일**을 만든다. 지금 서비스는 공고가 뜬 날에만 쓸 일이 있어 습관이 안 붙는다.
아직 안 뜬 학교에 대해 사장이 스스로 값을 적어두고, 공고가 뜨면 그 카드가 대기 상태로 올라온다.

## 0. 이름 판정 — "예약 투찰"은 쓰지 않는다

"예약"은 **자동 제출로 읽힌다**. 우리는 eaT에 대신 넣지 않는다. 오해는 곧 사고(투찰 누락)다.

| 후보 | 판정 |
|---|---|
| 예약 투찰 | ❌ 자동 제출 오독 |
| 자동 투찰안 | ❌ 최악 |
| **미리 정해두기** (기능명) / **미리 정해둔 값** (데이터명) | ✅ 채택 — 행위 주체가 사장, 자동화 암시 0 |
| 투찰 초안 | △ 문서 뉘앙스, 보조어로만 |

canon 어휘 유지: 투찰·개찰·하한·기초가·밀림·잘 나온 구간. 신조어는 "미리 정해둔 값" 하나뿐.

## 1. 모델

### 저장 단위: **학교 × 품목**
- 학교만: 장유고는 축산·수산·공산이 각각 별개 공고(하한·경쟁 다름) → 한 값으로 못 덮는다
- 지역×품목: 너무 성기다 — 학교마다 구간이 다르다는 게 우리 상품의 전제
- 결론: `(userId, schoolId, category)` 유일. 같은 학교의 다른 품목은 별개 행

### 스키마 — `packages/shared/src/db/schema/user-data.ts` (재적재 보존 대상)
```ts
/** 미리 정해둔 값 — 공고가 뜨기 전에 사장이 적어두는 투찰률. 우리가 제안한 값이 아니다 */
export const userPlan = pgTable("user_plan", {
  userId: varchar("user_id", { length: 64 }).notNull(),
  schoolId: varchar("school_id", { length: 200 }).notNull(),   // "김해시|장유고등학교"
  category: varchar("category", { length: 20 }).notNull(),      // 축산/수산/공산/농산/김치/기타
  rate: doublePrecision("rate").notNull(),                      // 사장이 정한 투찰률
  floorRate: doublePrecision("floor_rate"),                     // 정할 때 기준 하한(하한 바뀌면 경고용)
  memo: varchar("memo", { length: 200 }),                       // 근거 메모 ("지난 3회 90.03에 몰림")
  updatedAt: timestamp("updated_at").notNull().defaultNow(),
  expiresAt: date("expires_at"),                                // 기본 updatedAt+120일
}, (t) => [primaryKey({ columns: [t.userId, t.schoolId, t.category] })]);
```

### user_mark와의 관계 — **다른 층, 단방향 승격**
| | user_mark | user_plan |
|---|---|---|
| 대상 | 공고(bidNo) — 이미 뜬 것 | 학교×품목 — 아직 안 뜬 것 |
| 수명 | 개찰까지 | 120일(갱신 시 연장) |
| 의미 | 관심/투찰함(사실 기록) | 계획(의도) |

**승격 규칙**: 공고가 떠서 매칭되면 plan은 *복사되지 않는다*. 오늘 카드에 "미리 정해둔 값 90.05"로 표시되고,
사장이 [이 값으로 바구니에] 누르는 순간에만 `user_mark(status='watch', rate)`가 생성된다.
→ **한 번의 사람 확인**을 반드시 거친다(자동 제출 아님의 UI적 증거).

**충돌 규칙**: mark가 항상 이긴다. 공고 뜬 뒤 값을 바꾸면 mark만 바뀌고 plan은 그대로(다음 회차용).
카드에는 `미리 정해둔 값 90.05 · 지금 값 90.07` 둘 다 사실로 표시.

**유효기간**: 기본 120일(발주 주기 30~35일 × 3~4회). 만료 임박 30일 전부터 목록에 `기한 D-30` 표시,
만료분은 삭제하지 않고 회색 처리 + [되살리기]. 하한이 바뀐 학교는 `하한 88→90, 값 확인 필요` 경고 뱃지(사실 표시, 값 변경 제안 아님).

## 2. 트리거 — 매칭

공고(open_auctions)에는 `schoolName`, `sigungu`, `category`가 있고 plan은 `schoolId="시군구|학교명"`.

1. **1순위 정확 매칭**: `sigungu|schoolName === schoolId && category === category`
2. **2순위 학교만 일치(품목 불일치)**: 카드에 표시하지 않는다. 대신 [나]>미리 정해둔 값 목록에
   `장유고 공고 떴습니다 — 수산(정해둔 것은 축산)` 안내 행 1줄. 잘못된 값이 다른 품목에 붙는 사고 방지
3. **매칭 실패(학교명 표기 변형)**: 공백·괄호 제거 후 재시도 1회. 그래도 실패면 조용히 없음 처리
   (거짓 매칭 > 미매칭 — 후자가 안전)
4. 매칭은 **클라이언트에서** 수행(오늘 화면이 이미 open 목록과 plan 목록을 모두 가짐) — 서버 조인 불필요

## 3. 화면 — 컨트롤 예산

### U28 교훈 준수: 오늘 화면에 **새 블록을 만들지 않는다**
- 오늘 화면 변경분 = **기존 공고 카드 안 배지 1개 + 버튼 1개**뿐
  - 배지: `미리 정해둔 값 90.05` (카드 우상단, 회색)
  - 버튼: 기존 `+ 바구니` → 정해둔 값이 있으면 `이 값으로 바구니(90.05)`로 라벨만 바뀜
  - **신규 컨트롤 0개, 신규 섹션 0개** (라벨 치환 + 배지)
- 빈 상태(공고 0건)일 때만 오늘 화면 하단에 1블록 노출 → §4

### 본거지: `[나] > 미리 정해둔 값` (신규 화면 1장)
```
미리 정해둔 값                                    [CSV]
학교마다 미리 적어둔 투찰률입니다. 공고가 뜨면 오늘 화면에 함께 표시됩니다.
─────────────────────────────────────────────────────────
학교        품목   내가 정한 값  기준 하한  메모        상태
장유고      축산   90.05        90        3회 90.03몰림 D-88
주촌초      공산   88.03        88        —           공고 떴습니다 →
관동중      축산   90.02        90        —           하한 88→90 확인 필요
─────────────────────────────────────────────────────────
빈 상태: "미리 정해둔 값이 없습니다. 분석판에서 값을 정하고 [이 학교에 미리 정해두기]를 누르세요."
```

### 입력 지점: 분석판 산출기 하단 버튼 1개
`[이 학교에 미리 정해두기]` — 현재 산출기 값·하한·품목을 그대로 저장, 메모 입력은 선택(1줄).
저장 후 `저장됨 · 이 학교 축산 90.05` 인라인 확인. **분석판 신규 컨트롤 1개**.

## 4. 공고 없는 날의 할 일 (핵심 목적)

오늘 화면 공고 0건일 때 현재는 "진행 중인 공고가 없습니다" 한 줄로 끝난다 → 여기를 바꾼다:

```
진행 중인 공고가 없습니다. 다음 발주를 준비해 두세요.

다음에 뜰 학교                                   [미리 정해두기]
주촌초등학교 · 공산 · 예상 D-3 · 지난 낙찰 88.03      정해둔 값 없음  →
경운초등학교 · 축산 · 예상 D-9 · 지난 낙찰 90.04      90.02 정해둠
월산초등학교 · 수산 · 예상 D-12 · 지난 낙찰 90.01     정해둔 값 없음  →
                                          (예보 근거: 최근 발주 간격)
```
- 행 클릭 = 분석판(그 학교) → 값 정하고 돌아옴. **"할 일"이 목록으로 존재**하는 게 핵심
- 예보 데이터는 이미 있다(schools/forecast). 신규 API 0개
- 이 블록은 **공고 0건일 때만** 렌더 → 평소 오늘 화면은 부풀지 않음

## 5. 알림 v2와의 관계 — 중복 설계 금지

알림 v2 스펙(PLANNING-LOG #6)의 4종 중 **1번 "새 공고"의 필터 조건으로만** 참여한다.
- 새 규칙 신설 없음: 새 공고 알림의 우선순위에 `미리 정해둔 학교면 상단 고정 + 문구에 값 포함` 한 줄만 추가
- 알림 문구: `주촌초 공산 공고가 떴습니다. 미리 정해둔 값 88.03 (마감 8/30 10:00)`
- plan 자체는 알림 채널을 갖지 않는다(설정 항목 증식 방지)

## 7. 실패 시나리오 3

**F1. 자동 제출 오해 → 투찰 누락 (치명)**
사장이 "미리 정해뒀으니 들어갔겠지" 하고 NeaT에 안 넣는다. 개찰 후 참여조차 안 된 걸 발견 → 신뢰 즉사.
→ 방어: 이름에서 "예약" 제거, 화면 하단 경계 문구 고정, 바구니 승격에 사람 클릭 강제,
**투찰함 표시가 없는 채로 마감 3시간 전이면 오늘 카드에 `아직 투찰함 표시가 없습니다` 경고**(알림 2번과 동일 규칙 재사용).

**F2. 낡은 값이 그대로 쓰인다 (중대)**
3개월 전 값이 기초금액·하한·경쟁 상황이 바뀐 뒤에도 배지로 뜬다 → 그대로 넣고 무효/밀림.
→ 방어: 120일 만료, 하한 변경 경고 뱃지, 카드에 `정한 날짜 06-12` 병기(사실 표시로 스스로 판단하게).

**F3. 아무도 미리 안 정한다 (기능 사산)**
공고 없는 날엔 애초에 서비스를 안 열기 때문에, "공고 없는 날의 할 일"을 만들어도 볼 사람이 없다 — 닭·달걀.
→ 방어: 진입점을 **공고 있는 날**에도 심는다(분석판 산출기 버튼은 상시 노출). 개찰 결과를 보러 온 날
"다음 회차도 이 값으로?" 인라인 제안(값 제안 아님 — *저장 행위* 제안). 3주 내 저장 0건이면 기능 철수 판정.

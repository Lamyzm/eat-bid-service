# SPEC-SSOT — 중복 선언을 구조적으로 불가능하게 (2026-08-28 · architect)

사용자 원문: *"지역이나 축산 등 정규식이 적용된 부분을 정합하게 + 프론트 서버쪽으로 코드를 안 흩고,
SSOT로 중복선언 안 할 수 있나."*

**질문은 "SSOT를 선언할 수 있나"가 아니라 "중복 선언이 불가능하게 만들 수 있나"다.**
문서는 안 지켜진다. 우리는 네 번 안 지켰다. 그래서 이 문서는 **메커니즘**만 다룬다.

**한 문장 답:**
> **경계를 넘는 것은 "어휘"뿐이고, 어휘는 한 곳에서 선언해 나머지를 생성한다.
> 알고리즘은 경계를 넘지 않는다 — 층에 못박고, 층을 어기면 빌드가 깨진다.**

이 한 문장이 왜 성립하는지가 §1이고, 나머지는 그 적용이다.

## 1. (c) 메커니즘 — 중복 선언이 불가능하게

### 1-0. SSOT의 단위는 "값"이 아니라 **(값, 출처)** 다

critic 지적의 구조적 답. 어휘를 아무리 잘 봉인해도 **그 값이 어디서 왔는지**를 안 들고 다니면
101,043건의 추정이 59,437건의 사실과 구별되지 않는다. 그래서 규칙을 바꾼다:

> **출처 없는 값은 계약 위반이다. 값만 담은 컬럼·필드·타입은 만들지 않는다.**

세 사고가 이 하나로 덮인다. critic이 요구한 형식 그대로:

| 사고 | SSOT는 무엇인가 | 지금 값이 그것과 다르다는 걸 **화면이 어떻게 아는가** |
|---|---|---|
| ① 품목 | 원본 `MAIN_ITEMS` / `ds_mainItemlist` | 응답 타입이 `Sourced<Category>`다. **출처를 안 만지면 렌더가 컴파일 안 된다.** 문구가 갈린다: `축산 (발주처 지정)` vs `축산 (공고명 추정)` vs `품목 미상` |
| ② 지역 | `SIDO_CD` · `SIGUNGU_CD` | 코드가 없는 행은 `sigungu: null`. **규칙으로 메우지 않는다** — 화면은 "지역 미상"으로 말한다 |
| ③ 학교 | `PURR_CD` | 키 생성 실패를 **카운트해서 적재 요약에 싣는다.** 조용한 `continue` 금지 |

공통 모양 두 가지다.
**(가) "모른다"를 표현할 수 있는 타입.** 지금은 모른다를 표현할 자리가 없어서 규칙으로 메웠다.
**(나) 적재가 자기 품질을 숫자로 신고한다.** 지금은 신고하지 않아서 62%를 아무도 몰랐다.

**타입으로 강제하는 법 (tsc, 비용 0):**
```ts
type Provenance = 'original' | 'rule' | 'none';
type Sourced<T> = { readonly v: T; readonly src: Provenance };
```
API 응답이 `category: Sourced<Category>` 면 JSX의 `{o.category}` 는 **객체라서 React가 못 렌더하고
컴파일이 깨진다.** 값을 쓰려면 `stated(o.category)` 를 거쳐야 하고, 그 헬퍼가 출처 문구를 함께 돌려준다.
새 인프라 0, 런타임 비용 0, 이미 도는 tsc가 잡는다.
(`.v` 직접 접근이라는 탈출구는 남는다 — `stated()` 밖의 `.v` 를 가드가 grep 한다. §1-5)

**커버리지 예산 (게이트):** 로더가 적재 후 출처 분포를 찍고 **직전 적재보다 `original` 비율이 떨어지면 실패**한다.
`scripts/coverage-baseline.json` 에 **지금 숫자(36.6%)를 그대로 커밋한다.**
나쁜 상태를 숫자로 박아두면 화면이 "발주처 지정"이라고 거짓말할 수 없고, 개선은 baseline 상승으로만 기록된다.

> **어휘 대조(§1-4)는 값이 목록 안인지만 본다. 출처 예산은 값이 어디서 왔는지를 본다.
> 사고 ①을 잡는 건 후자뿐이다.**

**분모까지 오염됐다는 사실도 실어야 한다.** 62.3%가 추정이면 `by_cat_floor` 의 품목별 분모도
그만큼 추정 위에 서 있다. "축산 34회 기준"이 사실이 아니게 된다.
처방은 최소로 한다 — `catCounts` 옆에 **출처 혼합비 하나**(`srcMix: {original: 9, rule: 25}`)만 싣는다.
회차별 전개는 과설계다. 화면은 `축산 34회 (발주처 지정 9 · 추정 25)`까지 말할 수 있으면 된다.

### 1-1. 먼저 증명: 경계를 넘어야 하는 것은 **셋뿐**이다

"파이썬과 TS가 같은 지식을 갖는다"가 문제로 보이지만, 실제로 **공유해야 하는 지식은 거의 없다.**
값이 태어나는 층을 성격으로 못박으면 대부분의 알고리즘은 **한쪽에만 있어도 된다.**

| 지식 | 성격 | 사는 층 | 경계를 넘나? |
|---|---|---|---|
| 품목 분류 절차 | 회차 고정값 | 로더(py) | ❌ 서버·웹은 DB 컬럼을 읽는다 |
| 지역 파싱/정제 | 회차 고정값 | 로더(py) | ❌ 코드북 적용 후엔 절차 자체가 사라진다 |
| 유효/무효 | 회차 고정값 | **원본 → 로더가 싣기만** | ❌ |
| 적격심사 플래그 | 회차 고정값 | 로더(py) | ❌ |
| 학교/시장 집계 | 회차 고정값 | 로더(py) | ❌ |
| 자격 판정 | 사용자 의존 | 서버(ts) | ❌ 로더는 사용자를 모른다 |
| 판정 3분류·리허설 | 사용자 의존 | 서버(ts) | ❌ |
| 금액 파생(하한금액·실효하한) | 사용자 의존 | 서버(ts) | ❌ |
| 발주 예보 | 파생 | 서버(ts) | ❌ **웹이 베낀 것이 0-1** |
| 포맷·색·정렬·접기 | 표시 | 웹(ts) | ❌ |
| **① 품목 어휘 + 표기 변이표** | **데이터** | ? | ✅ **넘는다** |
| **② 시군구·시도 코드북** | **데이터** | ? | ✅ **넘는다** |
| **③ 학교키 형식** | **형식** | ? | ✅ **넘는다**(로더가 만들고 서버가 읽는다) |

**결론: 언어 경계를 넘는 건 알고리즘이 아니라 어휘 두 개와 형식 하나다.**
셋은 전부 **데이터**다. 데이터는 생성할 수 있다. 알고리즘 공유는 애초에 필요 없다.

이 표가 이 설계의 전부다. 나머지는 이걸 지키게 만드는 장치다.

### 1-2. 어휘 — 한 곳에서 선언하고 파이썬을 생성한다

```
packages/shared/src/domain/vocab/
  category.ts     ← 품목 6종 + 표시 순서 + 표기 변이표(_ATOM 이관)
  region.ts       ← 시도/시군구 코드북 (측정 통과 시)
  school-id.ts    ← 키 형식 1곳: schoolId() / parseSchoolId()
        │
        │  pnpm gen:contract   (node, ~40줄)
        ▼
tools/serve/_contract.py       ← # GENERATED — DO NOT EDIT
                                 # source-sha256: <해시>
```

**봉인 방식 (양방향으로 잡는다):**
- `gen:contract`를 `turbo build`에 물린다. 생성 결과가 커밋된 파일과 다르면 **빌드 실패**.
  → TS만 고치고 파이썬을 안 고치는 경우가 죽는다.
- `_contract.py` 상단에 원본 해시를 박는다. 로더가 시작할 때 **자기 해시를 검증**하고 불일치면 **적재 거부**.
  → 파이썬만 손으로 고치는 경우가 죽는다. (그리고 낡은 계약으로 630만 행을 덮어쓰는 사고가 막힌다.)

**선언과 절차를 나눈다.** 어휘("농공산품 = 농산+공산")는 TS 선언, 적용("이름 문자열을 훑는 절차")은 파이썬.
층 원칙과 충돌하지 않는다 — 로더는 여전히 분류의 주인이고, **무엇이 어떤 품목인지의 목록만** 위에서 받는다.

**왜 TS가 원본인가:**
- TS 쪽 소비자가 둘(웹·서버), 파이썬 소비자는 하나(로더). 소비자가 많은 쪽이 원본이다.
- `tsc`가 **이미 도는 게이트**다(pre-push `bun run build`). 파이썬은 이 리포에서 아무 게이트도 안 통과한다.
- `category.ts`는 이미 파생(`NAMED_CATEGORIES`·`categoryOrder`·타입)을 갖고 있다. JSON으로 내리면 그게 다 없어진다.
- 생성 방향이 TS→py여야 "빌드가 깨진다"가 성립한다. py→TS면 tsc가 **나중에** 안다.

> ⚠ **약점**: `_ATOM`이 측정 후 거의 비면(원본 통제 어휘가 깨끗하면) 40줄 생성기가 표시 순서 6개를 나르게 된다.
> **생성기의 값어치는 측정 결과에 반비례한다.** 그래도 ②③을 같은 파이프로 나르므로 한 번은 만든다.

### 1-3. 알고리즘 — 층에 못박고, 어기면 컴파일이 안 된다

**브랜디드 타입** — 0-2의 학교키 조립을 문법 수준에서 불가능하게.

```ts
declare const brand: unique symbol;
export type SchoolId = string & { readonly [brand]: 'SchoolId' };
export function schoolId(sigungu: string, institution: string): SchoolId
export function parseSchoolId(id: SchoolId): { sigungu: string; institution: string }
```

`` `${sigungu}|${name}` `` 을 `SchoolId` 자리에 넣으면 **타입 에러**다.
웹 4곳(`delivery:185,269` · `record:211,261`)과 서버 1곳(`app.module.ts:144`)이 컴파일에서 죽는다.
리뷰도 문서도 필요 없다. `BizNo`·`BidId`·`BidNo`도 같은 처리(A4의 bidId/bidNo 혼용이 이걸로 잡힌다).

**이게 라이브 결함 하나를 바로 고친다**: `fetch_open.py:45`는 `institution`을 원본 그대로 저장하고
로더는 `clean_inst()`로 괄호를 자른다. 그래서 괄호 붙은 기관명 공고는 `OpenController.enrich`의
학교 조회가 조용히 빗나가 `band`·`recent3`·`usualN`이 전부 null이 된다. 화면엔 "자료 없음"으로 보인다.
`schoolId()` 하나를 거치게 하면 두 경로가 같은 절차를 탄다.

**응답 타입 강제** — 컨트롤러에 shared 반환 타입을 명시하고, 웹이 로컬 타입 23개를 버린다.
런타임 zod 검증은 **넣지 않는다**(630만 행 위 응답에 파싱 비용을 얹을 이유가 없다). tsc만으로 충분하다.

### 1-4. DB가 어휘를 배신하면 적재가 실패한다 (원본 변경도 여기서 잡힌다)

생성은 "파이썬과 TS가 같은 목록을 본다"를 보장한다. **DB에 그 목록 밖 값이 들어가는 건 못 막는다.**
그리고 **원본이 바뀌는 것**(eaT가 품목을 하나 추가하는 것)도 못 막는다. 이 둘을 같은 장치로 잡는다.

> ⚠ **한계 명시(critic 지적 수용)**: 이 검사는 **값이 목록 안인지만 본다.**
> `name_rule`로 만든 "축산"도 목록 안이라 101,043건이 전부 통과한다.
> **사고 ①은 여기서 안 잡힌다. §1-0의 출처 예산이 잡는다.** 두 장치는 대체재가 아니라 짝이다.

로더 적재 직후 자기검사. 어긋나면 비영 종료:
```sql
select distinct category from school_auctions            -- ⊆ 생성된 어휘
select count(*) from firm_bids where valid is null        -- 0
select count(*) from school_auctions where category_src is null  -- 0  (출처 없는 값 금지)
select category_src, count(*) from school_auctions group by 1     -- baseline 대비 퇴행 시 실패
```
그리고 **적재 요약(load report)** 을 매 실행 남긴다. 지금 아무 데도 안 남는 것들:
출처 분포 · 키 생성 실패로 **건너뛴 회차 수**(0-0 ③) · 시군구 코드 결측 수 · 신규 어휘 값.
**"안 되는 건 안 도는 거다"의 올바른 구현은 조용한 `continue`가 아니라 카운트된 실패다.**

그리고 **관측 어휘 보고서**: 저카디널리티 컬럼마다 `distinct` 집합을 뽑아 지난 실행과 diff.
새 값이 나타나면 경고하고 기록한다.

> 우리가 두 번 실패한 이유는 "원본을 안 봐서"였다. 세 번째는 **"원본이 바뀐 걸 몰라서"** 날 수 있다.
> 이 장치가 그 방향을 막는 유일한 것이다.

### 1-5. 게이트 — 실제로 도는 것에만 얹는다

**현실 확인: 이 리포에 테스트 0개, CI 0개, 루트 lint 설정 없음.** 실제로 도는 건 둘뿐이다.
- `apps/web/.husky/pre-commit` → `lint-staged`
- `apps/web/.husky/pre-push` → `bun run build`

**그래서 계약 테스트를 CI에 넣자는 안은 이 프로젝트에서 작동하지 않는다.** 없는 인프라 위엔 강제가 안 선다.

| 층 | 장치 | 붙는 곳 | 비용 |
|---|---|---|---|
| 어휘 | `gen:contract` 재생성 diff | `turbo build` | 40줄 |
| 어휘 | `_contract.py` 해시 검증 | 로더 시작 | 5줄 |
| 알고리즘(TS) | 브랜디드 타입 | tsc (이미 돎) | **0** |
| 알고리즘(TS) | shared 응답 타입 | tsc (이미 돎) | **0** |

| DB | postflight 어휘 대조 | 로더 종료 | 10줄 |

`ssot-guard.mjs`가 잡는 것 (타입으로 못 잡는 것들만):

| 검사 대상 | 잡는 사고 |
|---|---|

### 1-6. 기각한 대안 (왜 안 하는지)

| 대안 | 기각 이유 |

## 6. 이 설계가 실패하는 시나리오 3개

### 실패 1 — 코드북이 원본에서 흔들린다 (§2의 삭제 열한 개가 전부 무효)

척추가 "원본 코드가 문자열 파싱보다 낫다"인데, 그게 틀릴 수 있다.
`SIGUNGU_CD`가 시점에 따라 다른 이름을 가리키면(2010 마산·진해→창원, 2023 강원·전북 특별자치도 개명),
"코드가 진실"은 파싱보다 나은 게 아니라 **다른 종류의 거짓**이 된다.
그 순간 우리는 `_SGG_CANON` 34줄을 **이미 지운 뒤**다 — 되돌릴 규칙이 없다.
`PURR_CD`도 같다. 통폐합·재발급되면 학교 정체성이 시간축에서 쪼개진다.

- 조기 신호: `_cb2.py`의 코드당 이름 다수결 일관성
- **폐기선: 일관성 99% 미만이면 §5-3 전체 폐기, 1·2단계에서 멈춘다** (그래도 0-1·0-3은 고쳐진다)
- 완화: 코드북을 `코드→이름`이 아니라 **`(코드,연도)→이름`**으로. 비용이 오른다
- 남는 위험: 완화해도 "지금 이름"을 골라야 하는 화면(지역 칩)에선 결국 하나를 고른다

### 실패 2 — 가드가 잔소리가 되어 죽는다 (§1-5 무력화)

1인 개발 + 에이전트 팀에서 **allowlist 추가는 언제나 수정보다 싸다.**
에이전트가 급할 때 가드에 막히면 고치는 대신 allowlist에 넣고 간다. 3개월 뒤 40줄이면 가드는 죽은 것이다.
`until` 만료를 걸었지만 **만료일을 미루는 것도 한 줄**이다.

- 조기 신호: allowlist 항목 수, 그리고 **연장 횟수**
- 완화: 연장 1회 제한 + `# why:` 필수. 2회째부터 빌드 실패
- 남는 위험: 규칙 만드는 사람과 지키는 사람이 같으면 어떤 자동화도 최종적으로 자발성에 기댄다.
  **이 설계는 그 사실을 없애지 못한다. 비용만 올린다.**

### 실패 3 — 생성이 오히려 새 이중성을 만든다 (§1-2 역효과)

`_contract.py`는 **커밋된 생성물**이다. 생성물을 리포에 두는 순간 "원본과 생성물" 두 파일이 생긴다.
지금 없던 이중성이다. 봉인(빌드 diff + 로더 해시)이 그걸 막지만, **봉인이 불편해지는 순간이 온다**:
파이썬 쪽에서 급히 값 하나를 고쳐야 하는데 노드를 못 돌리는 환경(수집 서버, 컨테이너 안)이면
사람은 생성물을 직접 고치고 해시 검증을 끄는 쪽을 고른다. 그러면 이 설계는 **거꾸로** 작동한다 —
전에는 파일이 하나였는데 이제 어긋난 파일이 둘이다.

- 조기 신호: 로더 실행 환경에 노드가 없는가. 해시 검증을 우회한 흔적(환경변수·주석)
- 완화: 생성물을 리포에 두지 않고 **로더 시작 시 DB에서 어휘를 읽는다**(서빙 DB에 `vocab` 테이블 1개).
  그러면 파일이 하나도 안 늘고 런타임에 항상 일치한다. 대신 로더가 DB 없이는 못 돈다
- 남는 위험: 완화안은 "어휘의 진실이 DB"가 되어 §1-6에서 기각한 안("오타가 진실이 된다")에 가까워진다.
  **이 트레이드오프를 나는 아직 못 골랐다. critic 좌석의 판단을 받고 싶은 1순위 항목이다**

   불일치할 수 있다. 고르는 건 data 좌석. 설계는 "하나여야 한다"까지만
3. **브랜디드 타입은 서버 SQL 문자열을 못 막는다.** `split_part(school_id,'|',1)`은 그냥 문자열이라 tsc가 못 본다.

4. **`_contract.py` 생성 대 DB 어휘 테이블 — 실패3의 트레이드오프를 못 골랐다.** 이게 가장 약하다
5. **`schools.id`를 영구 별칭으로 남기면 A3의 절반만 해결된다.** 코드와 문자열키가 공존하는 동안
   "어느 것이 진실인가"가 다시 둘이 된다. §5-3-15의 폴백이 그 이중성이다.
   **의도한 부채이고, 갚을 날짜를 나는 못 정했다**
6. **A12(카피)·A19(내 값 vs 실제)는 강제 수단이 없다.** 사람이 지킨다고 썼다.
   그건 지금까지의 방식이고, 지금까지 여섯 번 실패했다
7. **비용 추정을 안 붙였다.** 1·2단계는 며칠로 보이지만 3단계(코드북 전환)는 규모를 모른다.
   5-0 측정 전엔 추정 자체가 허구라서 뺐다

# SPEC-SSOT — 중복 선언을 구조적으로 불가능하게 (2026-08-28 · architect)

사용자 원문: *"지역이나 축산 등 정규식이 적용된 부분을 정합하게 + 프론트 서버쪽으로 코드를 안 흩고,
SSOT로 중복선언 안 할 수 있나."*

**질문은 "SSOT를 선언할 수 있나"가 아니라 "중복 선언이 불가능하게 만들 수 있나"다.**
문서는 안 지켜진다. 우리는 네 번 안 지켰다. 그래서 이 문서는 **메커니즘**만 다룬다.

**세 문장 답:**
> **① SSOT의 단위는 값이 아니라 (값, 출처)다. 출처 없는 값은 계약 위반이고, 적재는 자기 품질을 숫자로 신고한다.**
> **② 경계를 넘는 것은 "어휘"뿐이고, 어휘는 한 곳에서 선언해 나머지를 생성한다.**
> **③ 알고리즘은 경계를 넘지 않는다 — 층에 못박고, 층을 어기면 빌드가 깨진다.**

②만 있던 게 1차 설계였고, critic 측정치가 그걸 무효화했다(§0-0).
**목록이 같은지만 보는 검사는 "축산"이 원본에서 왔는지 이름 추정인지 구별하지 못한다.** ①이 그래서 1순위다.

## 1. (c) 메커니즘 — 중복 선언이 불가능하게

### 1-0. SSOT의 단위는 "값"이 아니라 **(값, 출처)** 다

critic 지적의 구조적 답. 어휘를 아무리 잘 봉인해도 **그 값이 어디서 왔는지**를 안 들고 다니면
101,043건의 추정이 59,437건의 사실과 구별되지 않는다. 그래서 규칙을 바꾼다:

> **출처 없는 값은 계약 위반이다. 값만 담은 컬럼·필드·타입은 만들지 않는다.**

세 사고가 이 하나로 덮인다. critic이 요구한 형식 그대로:

| 사고 | SSOT는 무엇인가 | 지금 값이 그것과 다르다는 걸 **화면이 어떻게 아는가** |
|---|---|---|
| ① 품목 | 원본 `MAIN_ITEMS` / `ds_mainItemlist` | 응답 타입이 `Sourced<Category>`다. **출처를 안 만지면 렌더가 컴파일 안 된다.** 문구가 갈린다: `축산 (발주처 지정)` vs `축산 (공고명 추정)` vs `품목 미상` |
| ② 지역 | `SIDO_CD` · `SIGUNGU_CD` | 코드가 없는 행은 `sigungu: null`. **규칙으로 메우지 않는다** — 화면은 "지역 미상"으로 말한다 |
| ③ 학교 | `PURR_CD` | 키 생성 실패를 **카운트해서 적재 요약에 싣는다.** 조용한 `continue` 금지 |

공통 모양 두 가지다.
**(가) "모른다"를 표현할 수 있는 타입.** 지금은 모른다를 표현할 자리가 없어서 규칙으로 메웠다.
**(나) 적재가 자기 품질을 숫자로 신고한다.** 지금은 신고하지 않아서 62%를 아무도 몰랐다.

**타입으로 강제하는 법 (tsc, 비용 0):**
```ts
type Provenance = 'original' | 'rule' | 'none';
type Sourced<T> = { readonly unsafeValue: T; readonly src: Provenance };
```
**필드명은 `unsafeValue`다. `.v`가 아니다 (critic 지적).** `.v`는 두 글자라 가드 grep에서
`e.v`·`event.v`·`rev.v` 같은 오탐이 폭발한다. **한 글자 결정이 가드의 생사를 가른다** —
`unsafeValue`는 오탐이 0에 수렴하고, 이름 자체가 "그냥 쓰면 안 되는 값"이라고 말한다.
API 응답이 `category: Sourced<Category>` 면 JSX의 `{o.category}` 는 **객체라서 React가 못 렌더하고
컴파일이 깨진다.** 값을 쓰려면 `stated(o.category)` 를 거쳐야 하고, 그 헬퍼가 출처 문구를 함께 돌려준다.
새 인프라 0, 런타임 비용 0, 이미 도는 tsc가 잡는다.
(`.v` 직접 접근이라는 탈출구는 남는다 — `stated()` 밖의 `.v` 를 가드가 grep 한다. §1-5)

**커버리지 — 게이트가 아니라 적재 요약의 한 줄로 (critic 수정 수용).**
1차안은 *"직전보다 `original` 비율이 떨어지면 적재 실패"* 였다. **틀렸다.**

### 1-0b. 표본이 적다는 사실은 **화면이 말한다. 로더는 지우지 않는다**

§1-0의 "(가) 모른다를 표현할 수 있는 타입"의 쌍둥이 원칙이다. 그리고 이건 이미 결재된 적이 있다 —
`by_floor`의 `len(wrs)<3` 폐기 로직을 걷어내며 로더 주석에 이렇게 썼다:

> *"표본이 적은 구간도 버리지 않는다 — n을 그대로 실어 보내고, 적다는 사실은 화면이 말한다.
> 작은 n을 숨기는 것과 다른 품목을 섞는 것은 같은 죄다"* (`load_postgres.py:230-232`)

**그 원칙을 쓴 파일이 그 바로 위에서 학교를 통째로 지운다**(`:217`).
구간을 지우는 건 죄라고 결재해놓고 **학교를 지우는 건 통과했다.** 더 큰 판본이다.

> **원칙(못박는다): "안정성을 위해 버리기"와 "n을 표기하기"는 같은 목적의 두 수단이고,
> 후자가 우리 헌법이다.** 전자는 사실을 감추고 후자는 사실을 말한다.
> **문턱으로 거른 것은 "없는 것"이 아니라 "우리가 안 보여주기로 한 것"이다.**

예외는 하나뿐이다: **파생값을 계산할 수 없어서 `null`을 내는 것**은 버리는 게 아니라 모른다고 말하는 것이다
(`:228`의 `len(pprs) >= 5 else None`이 그 예 — 행을 지우지 않고 그 값만 비운다). **행을 지우는 것과 값을 비우는 것은 다르다.**

**분모까지 오염됐다는 사실도 실어야 한다.** 62.3%가 추정이면 `by_cat_floor` 의 품목별 분모도
그만큼 추정 위에 서 있다. "축산 34회 기준"이 사실이 아니게 된다.
처방은 최소로 한다 — `catCounts` 옆에 **출처 혼합비 하나**(`srcMix: {original: 9, rule: 25}`)만 싣는다.
회차별 전개는 과설계다. 화면은 `축산 34회 (발주처 지정 9 · 추정 25)`까지 말할 수 있으면 된다.

### 1-1. 먼저 증명: 경계를 넘어야 하는 것은 **셋뿐**이다

"파이썬과 TS가 같은 지식을 갖는다"가 문제로 보이지만, 실제로 **공유해야 하는 지식은 거의 없다.**
값이 태어나는 층을 성격으로 못박으면 대부분의 알고리즘은 **한쪽에만 있어도 된다.**

| 지식 | 성격 | 사는 층 | 경계를 넘나? |
|---|---|---|---|
| 품목 분류 절차 | 회차 고정값 | 로더(py) | ❌ 서버·웹은 DB 컬럼을 읽는다 |
| 지역 파싱/정제 | 회차 고정값 | 로더(py) | ❌ 코드북 적용 후엔 절차 자체가 사라진다 |
| 유효/무효 | 회차 고정값 | **원본 → 로더가 싣기만** | ❌ |
| 적격심사 플래그 | 회차 고정값 | 로더(py) | ❌ |
| 학교/시장 집계 | 회차 고정값 | 로더(py) | ❌ |
| 자격 판정 | 사용자 의존 | 서버(ts) | ❌ 로더는 사용자를 모른다 |
| 판정 3분류·리허설 | 사용자 의존 | 서버(ts) | ❌ |
| 금액 파생(하한금액·실효하한) | 사용자 의존 | 서버(ts) | ❌ |
| 발주 예보 | 파생 | 서버(ts) | ❌ **웹이 베낀 것이 0-1** |
| 포맷·색·정렬·접기 | 표시 | 웹(ts) | ❌ |
| **① 품목 어휘 + 표기 변이표** | **데이터** | ? | ✅ **넘는다** |

**결론: 언어 경계를 넘는 건 알고리즘이 아니라 어휘 두 개와 형식 하나다.**
셋은 전부 **데이터**다. 데이터는 생성할 수 있다. 알고리즘 공유는 애초에 필요 없다.

이 표가 이 설계의 전부다. 나머지는 이걸 지키게 만드는 장치다.

### 1-2. 어휘 — **생성기를 만들지 않는다** (critic 결정 수용, 내 1차안 폐기)

내 1차안은 `vocab/*.ts` → `_contract.py` **생성 + 해시 봉인**이었다.
§6 실패3에서 내가 "못 골랐다"고 남긴 트레이드오프에 critic이 답했고, **그 답이 맞다.**

**폐기 근거 (critic 논증을 그대로 받는다):**
- 이 파이프가 실제로 나르는 건 `_ATOM` 25줄 + 표시 순서 6개다. **측정 후엔 더 줄어든다**(§0-0 재파싱 뒤 원본 통제 어휘가 답하는 비율이 오른다). 그걸 위해 생성기 40줄 + 빌드 훅 + 해시검증 5줄 + **새 실패 모드** + **커밋된 생성물이라는 지금 없는 이중성**을 산다.
- **§1-4의 postflight 어휘 대조 10줄이 같은 사고를 이미 막는다.** 어휘가 갈리면 → 로더가 목록 밖 값을 씀 → 적재 실패.
- 결정적으로: **갈렸는데 DB에 안 들어가는 불일치는 사용자에게 도달할 수 없다.** 생성기는 도달 불가능한 불일치를 막으려고 110줄을 낸다.
- 완화안(DB 어휘 테이블)은 §1-6이 이미 기각한 안("오타가 진실이 된다")으로 되돌아간다 — **설계가 원을 그렸다.**

**대신 이렇게 한다:**

| 무엇 | 어디 | 왜 |
|---|---|---|
| 품목 **목록**(6종·순서·타입) | `domain/category.ts` (TS) | 소비자가 웹·서버 둘. tsc가 지킨다 |
| 표기 **변이표**(`_ATOM`) | `load_postgres.py` (파이썬) | **분류 절차의 일부**다. 절차가 사는 층에 산다 |
| 정합 | **§1-4 postflight** | 갈리면 적재가 죽는다 |

> **목록과 변이표는 성격이 다르고, 성격이 다른 두 파일은 중복 선언이 아니다.**
> "농공산품 → 농산+공산"은 어휘가 아니라 **파서의 사전**이다. `CATEGORIES`는 계약이고 `_ATOM`은 구현이다.

**이 폐기가 §1-1의 결론을 바꾸지 않는다.** 경계를 넘는 셋 중 ①(어휘)은 **넘지 않아도 됐던 것**으로 판명났다.
남는 건 ②(코드북 — 데이터라 DB 테이블로 간다)와 ③(학교키 형식 — §1-3 브랜디드 타입).
**즉 언어 경계를 넘는 코드는 0이다.** 1차안보다 단순해졌다.

declare const brand: unique symbol;

### 1-4. DB가 어휘를 배신하면 적재가 실패한다 (원본 변경도 여기서 잡힌다)

생성은 "파이썬과 TS가 같은 목록을 본다"를 보장한다. **DB에 그 목록 밖 값이 들어가는 건 못 막는다.**
그리고 **원본이 바뀌는 것**(eaT가 품목을 하나 추가하는 것)도 못 막는다. 이 둘을 같은 장치로 잡는다.

> ⚠ **한계 명시(critic 지적 수용)**: 이 검사는 **값이 목록 안인지만 본다.**
> `name_rule`로 만든 "축산"도 목록 안이라 101,043건이 전부 통과한다.
> **사고 ①은 여기서 안 잡힌다. §1-0의 출처 예산이 잡는다.** 두 장치는 대체재가 아니라 짝이다.

로더 적재 직후 자기검사. 어긋나면 비영 종료:
```sql
select distinct category from school_auctions            -- ⊆ 생성된 어휘
select count(*) from firm_bids where valid is null        -- 0
select count(*) from school_auctions where category_src is null  -- 0  (출처 없는 값 금지)
select category_src, count(*) from school_auctions group by 1     -- baseline 대비 퇴행 시 실패
```
**그리고 "0행 적재는 자기를 성공으로 신고한다" — 이게 §1-0의 거울이다 (critic A25).**
자기검사에 **행 수 하한**이 없었다. 지금 상태를 실측으로 정리한다:

- ✅ **로더 쪽은 봉인됐다**(커밋 `6d91978`). 목록을 못 읽으면 건너뛰고, 0건이면 기존을 유지한다.
- ❌ **수집기 쪽은 그대로다.** `fetch_open.py:61`이 여전히 `open(OUT,"w")` — **바이트를 쓰기 전에 기존 파일을 0바이트로 자른다.**
  임시파일도 `os.replace`도 없다. **같은 리포 `src/eatbid/archive.py:40-43`은 이미 temp+rename을 쓴다** — 올바른 패턴이 옆에 있는데 여기만 안 쓴다.
- ❌ 그리고 봉인이 **부분 실패를 안 막는다.** `fetch_open.py:29-34`는 지역별 예외를, `:55-56`은 공고별 예외를
  삼키고 **종료 코드 0**으로 끝난다. 17개 지역 중 16개가 실패해도 "3건짜리 유효한 JSON"이 나온다.
  → `oj`가 비어 있지 않으므로 로더의 새 방어를 **통과**하고 `delete` 후 3건을 넣는다.
  **크론의 `set -e`·`&&`도 못 막는다 — 실패가 아니라 성공으로 끝나기 때문이다.**

처방 둘, 둘 다 이미 있는 패턴이다:
1. **원자적 쓰기**: temp + `os.replace` (`archive.py`와 같게). 반쪽 파일이 존재할 수 없게 만든다.
2. **급감 방어**: 로더가 직전 건수 대비 **급감(예: 50% 미만)이면 `delete`를 건너뛰고 사실을 남긴다.**
   0건만 막는 건 절반이다 — 위험한 건 0이 아니라 **3**이다.

그리고 **적재 요약(load report)** 을 매 실행 남긴다. 지금 아무 데도 안 남는 것들:
출처 분포 · 키 생성 실패로 **건너뛴 회차 수**(0-0 ③) · 시군구 코드 결측 수 · 신규 어휘 값 · **직전 대비 건수 변화**.
**"안 되는 건 안 도는 거다"의 올바른 구현은 조용한 `continue`가 아니라 카운트된 실패다.**

그리고 **관측 어휘 보고서**: 저카디널리티 컬럼마다 `distinct` 집합을 뽑아 지난 실행과 diff.
새 값이 나타나면 경고하고 기록한다.

> 우리가 두 번 실패한 이유는 "원본을 안 봐서"였다. 세 번째는 **"원본이 바뀐 걸 몰라서"** 날 수 있다.
> 이 장치가 그 방향을 막는 유일한 것이다.

hex 색 → oxlint 규칙 쪽이 맞다. `LEDGER-CHECKED` → **§4-c로 이동**(노드 grep이 아니라 파이썬 AST 대조).
`schema.sql` ≠ snapshot → §9로 이동(그 파일 자체가 사라진다).
`continue` 앞 카운터 → 정적 검사로 못 본다. **적재 요약의 숫자로 본다**(§1-4).

**allowlist는 `scripts/ssot-allow.json` 하나. 항목마다 `until` 날짜 필수. 연장은 1회, `# why:` 필수.**

### 2-b. 코드북 — **후보 교체는 철회한다. 미해결로 남는다**

앞 개정에서 나는 *"코드북 후보가 `sgg_nm`에서 `PDLC_NM`으로 바뀐다"* 고 썼다. **취소한다.**
data가 자기 제안을 스스로 반증했다.

**`PDLC_NM`은 참가 자격 지역 목록이지 공고 소재지가 아니다.**
결정적 증거: `전남광주/전체` 표기가 붙은 공고 **8건**의 실제 소재지가 **전북 군산시 4건 · 경기 4건**이었다.
다른 지역 공고가 광주·전남 업체에게 자격을 열어준 표기다. **"자격 지역 = 소재지"라는 가정이 틀렸다.**
(그리고 `27곳`이라던 앞선 수치도 재측정에서 **8건**이었다 — §6 실패4의 사례다.)

| | 축 | 쓸 수 있는 곳 |
|---|---|---|
| `PDLC_NM` | **자격 지역**(누가 응찰할 수 있나) | A11 자격 판정. **소재지 축에 쓰면 안 된다** |
| `SIDO_CD` + `SIGUNGU_CD` | **소재지**(어디 공고인가) | A2 지역 축. 둘 다 100% 채움 |

**따라서 A2는 원래 자리로 돌아간다: `SIDO_CD` + `SIGUNGU_CD`.**
그리고 **`SIGUNGU_CD` → 이름 코드북은 여전히 미해결 과제다** — 코드는 100% 있는데 이름표가 없다.
`_cb2.py`가 재던 것이 바로 그 이름표의 일관성이고, **§6 실패1의 폐기선(일관성 99%)은 그 측정에 그대로 걸려 있다.**

> **두 번 연속으로 "원본에 답이 있다"는 가설이 틀렸다**(PDLC_NM 품목 → PDLC_NM 소재지).
> 두 번 다 ⚠를 달아둔 덕에 피해가 0이었다. **가설을 세우는 것은 값싸고, 표시 없이 인용하는 것이 비싸다.**

### 2-0. 먼저: **"지역처럼 생긴 값"이 이 도메인에 네 축 있다**

우리 팀이 지역에서 **다섯 번 틀렸다** — 내가 셋(`PDLC_NM`을 품목으로 · `PDLC_NM`을 소재지로 ·
`_SGG_CANON`을 코드 증거로), critic이 둘(같은 인용 · 이름 개명을 코드 분열로).
**다섯 번 다 축을 뭉갠 것이고, 원인이 이 데이터의 성질이다:**

| 축 | 원본 필드 | 무엇에 붙는가 | 쓰는 곳 |
|---|---|---|---|
| **소재지** | `SIDO_CD` · `SIGUNGU_CD` | **공고**(어디서 열렸나) | 지역 필터·학교 키 |
| **응찰 자격** | `ds_areaList.PDLC_NM`·`SGG_CD` | **자격 조건**(누가 응찰 가능한가) | `eligibleFor` |
| **표시명** | `DOG_ADDR` 텍스트 | **그때의 이름**(사람이 읽는 것) | 화면 라벨 |
| **행정 코드** | `SIDO_CD` 값 자체 | **불변 정체성** | 조인·정렬 |

**넷이 전부 한글 지명으로 표기된다.** 채움률·형식·고유값 검사를 다 통과해도 축은 안 나온다 —
`PDLC_NM`은 **100% 채움 · 252종 · `시도/시군구` 형식**이 전부 맞았는데 축이 틀렸다.

> **형식 검사는 "이 값이 그럴듯한가"를 묻지 "이 값이 무엇의 속성인가"를 못 묻는다.**
> **추가 질문(자산 대장 칸): "이 필드가 붙어 있는 대상이 무엇인가 —
> 공고인가 · 발주처인가 · 응찰자격인가 · 표시명인가."**
>
> ⚠ critic 정정 수용: 이건 **§4-b 실행 대장(동사)이 아니라 자산 대장(명사) 쪽 질문**이다.
> 실행 대장은 *"언제 도나·누가 지우나"* 를 묻는다. **자리를 잘못 두면 또 안 물어보게 된다.**
>
> **축이 겹쳐 보이는 게 이 데이터의 성질이지 우리 부주의가 아니다** — 그래서 질문 한 줄이 실제로 막아준다.

### 2-c. 시도 — **확정됐다. 그리고 TS 쪽 선언은 0이다**

리더가 소스에 직접 물어 전 코드(0~20)를 탐침했다. **16개가 전부고 연속이 아니다.**
`5`·`13`·`0`·`19`·`20`은 실재하지 않는다. **`18` = `전남광주통합특별시`, 58,459건으로 서울 다음 최대 지역**이다.

그리고 **원본 주소 표기가 오염돼 있다는 게 원본에서 증명됐다**:
서울이 `서울특별시` 171 / `서울` 24로 갈리고, 전북은 `전라북도` 177 / `전북특별자치도` 19 / `전북` 2 /
**`익산시` 1**(시도 칸에 시군구가 들어감). **`_SIDO_MAP` 34줄을 걷어내야 하는 이유가 이걸로 끝났다.**

#### 결정 ①: 외부 행정구역 코드와 잇지 않는다 — **결론 유지, 근거 정정**

> ⚠ **정정**: 나는 *"`전남광주통합특별시`는 행안부 체계에 없는 eaT 자체 명칭이다"* 라고 썼다. **틀렸다.**
> **2026-07-01 출범한 실재하는 행정구역**이다(전남+광주 통합). 리더가 웹으로 독립 확인했다.
> 리더의 단정을 내가 검증 없이 받아 결정의 근거로 삼았다 — **§10-27b와 같은 실수를 또 했다.**

**결론은 유지된다. 근거가 바뀔 뿐이다.** 실측(리더): eaT 코드와 표준 행정코드는 **값이 완전히 다르다**
(서울 eaT `1` / 표준 `11`, 시군구 뒷자리 일치 **0**). 시도 집합만 **16↔16 대응**이고,
시군구는 **표준 목록에 화성·용인·고양·전주가 없어** 원인 확인 전까지 보류다.

**즉 외부 표준과 맞추려면 매핑표가 필요하고, 그게 §2가 지우는 중인 열한 개와 같은 물건이다.**
원본이 자기 세계의 이름을 정의한다. 우리는 그 이름을 쓴다.
(그리고 `전남광주통합특별시`가 실재하므로 §2-c 결정 ③의 "원본 그대로 표시"가 **더 강해진다** —
줄여 쓰면 실재하는 행정구역명을 우리가 임의로 바꾸는 것이 된다.)

#### 결정 ②: 시도 SSOT의 형태 — **파이썬 1곳, TS 0곳, 목록은 DB에서 관측**

리더가 물었다: *"품목에서 겪은 파이썬/TS 이중성이 여기도 있는가."*
**없다. 그리고 품목과 다른 이유가 정확히 리더가 짚은 그것이다 — 이건 원본이 주는 값이다.**

품목 어휘는 **우리가 만든 목록**이라 어딘가에 선언돼야 했다. 시도는 아니다:

| 소비자 | 필요한 것 | 어디서 |
|---|---|---|
| 수집기(py) | 코드 **목록**(순회용) | `config.py:REGION_CODES` — **이미 정확하다** |
| 로더(py) | 코드 → 이름 | 같은 곳 |
| 서버·웹(ts) | 표시할 지역 **목록과 순서** | **DB.** 선언 없음 |

**핵심: 로더가 `sido_cd`를 이름 옆에 컬럼으로 싣는다.** 그러면
- **이름**은 `schools.sido`에서 나온다(관측된 사실)
- **순서**는 `sido_cd`에서 나온다(원본이 정한 순서)
- **목록**은 `select distinct`에서 나온다 — `/wins/regions`가 이미 쓰는 패턴이고
  그 주석이 *"적재된 지역 목록(데이터 유도 — 거짓 '전국' 방지)"* 라고 이유까지 적어놨다

**부수 효과: 비연속 코드 문제가 통째로 사라진다.** 5·13을 "없다"고 선언할 필요가 없다 —
**선언을 안 하면 없는 건 그냥 안 나온다.** 목록을 손으로 적는 순간 `range(1,18)` 같은 버그가 생기고,
실제로 `fetch_open.py`가 그 버그를 갖고 있었다(리더가 `e19f880`로 고쳤다).

> **§1-2의 결론이 확장된다: 언어 경계를 넘는 어휘가 하나 더 줄었다.**
> 품목은 "우리가 만든 목록이라 선언이 필요하되 파이썬은 안 넘어간다",
> 시도는 **"원본이 준 값이라 선언 자체가 필요 없다"**. 후자가 더 강한 형태다.

#### 결정 ③: 표시 이름 — **원본 그대로. 단 검색 별칭은 둔다**

`전남광주통합특별시`를 `전남·광주`로 줄이는 안을 **기각한다.** 이유 셋:

1. **그건 분해를 주장하는 것이고, 우리는 그 분해를 검증하지 않았다.** 표본 200건에서
   187건이 그 표기이고 나머지가 전남 학교였다는 건 "전남이 포함된다"이지 "전남+광주가 전부다"가 아니다.
   **`축수산물`을 `축산`으로 읽어 수산을 잃은 것과 같은 모양이다.**
2. **그건 매핑 규칙이다.** §2가 지금 열한 개를 지우는 중이고, 이건 `_SIDO_MAP`을 새로 만드는 것이다.
3. **이름 안에 `전남`과 `광주`가 둘 다 들어 있다.** `서울특별시`를 `서울`로 줄이는 것과 달리
   여기서 줄이면 **정보가 준다.**

**리더가 짚은 UX 긴장은 실재한다. 처방은 표시가 아니라 검색이다:**
- **표시** = 원본 이름 그대로. 필요하면 보조문 `eaT 표기`
- **검색** = `광주`·`전남`을 쳐도 이 지역이 걸린다 (별칭 테이블)

**이 비대칭이 원칙이다: 별칭이 틀리면 검색 결과가 하나 더 걸릴 뿐이고,
표시가 틀리면 우리가 거짓을 단언한다.** 검색 별칭은 표시 규칙이 아니므로 §2의 삭제 대상이 아니다.

#### 남는 것: 시군구 코드북은 **미해결로 남긴다**

`SIGUNGU_CD`는 100% 채움인데 **코드→이름 매핑에 충돌 15조합**이 있고,
`PDLC_NM`은 자격 지역이라 못 쓴다(§2-b). **억지로 닫지 않는다.**

> ⚠ **가설(세 번째다. 표시하고 간다)**: 충돌 15조합이 실패1이 말하는 **시간축 분열**일 수 있다 —
> `_SGG_CANON`의 마산·진해·덕양구가 그 후보다. 맞다면 `(코드,연도)→이름`이 그대로 답이다.
> **나는 "원본에 답이 있다"를 두 번 연속 틀렸다**(§10-22). 검증 전에 이 문장을 인용하지 마라.
> 검증은 싸다 — **충돌 15조합의 이름 쌍이 행정구역 통합 관계인지 보면 된다.** n=15다.

**살아남는 규칙은 둘뿐이다: `_ATOM`(표기 변이)과 `region-coords`(좌표).**
전자는 TS에서 선언하고 파이썬으로 생성한다(§1-2). 후자는 값이 아니라 그림이라 웹에 남는다.
나머지 열한 개는 **원본 코드로 대체돼 사라진다.** 지우면 잃는 게 0이어야 한다 — 아니면 §5-3에서 멈춘다.

### 3-2. 의제 2(토스식 선언적 컴포넌트)와의 관계 — 충돌 아니라 전제

**순서: SSOT 정리 → 선언적 재작성.** 반대로 하면 로직을 품은 채로 예쁘게 감싸는 것이 되고,
중복은 컴포넌트 안으로 숨어 더 안 보이게 된다.

### 3-3. 의제 3(NestJS 철학 분리)과의 관계 — 중복 7곳은 서비스 계층 부재의 증상이다

`app.module.ts` 954줄에 전 컨트롤러가 인라인이다. 서비스가 없다.
그래서 `/results`·`/firms/record`·`/firms/bids`·`/rounds`·`/share`가 판정을 **각자 인라인**했다.
**중복은 게으름이 아니라 구조의 결과다.** 부를 곳이 없으면 복사한다.

**처방은 서비스 4개가 아니라 순수 함수 3개다 (critic 수정 수용).**
1차안에 `VerdictService`·`EligibilityService`·`MoneyService`·`CalendarService`를 적었는데 **과했다.**
`EligibilityService`는 **호출 지점이 `app.module.ts:189` 하나뿐**이다. 한 곳에서 부르는 걸 서비스로 만드는 건
의제 3을 명분으로 층을 하나 더 쌓는 것이다.

```
domain/verdict.ts   ← 판정 3분류 (0-3의 7곳이 여기 하나로)   ★ 순수
domain/money.ts     ← 하한금액·실효하한 (4곳)                ★ 순수
domain/time.ts      ← todayKST (4곳)                        ★ 순수
```
셋 다 **순수 함수라 테스트가 붙고, 서버·웹이 같은 것을 쓴다.** 자격 판정은 지금 자리에 둔다.
발주 예보는 서버 1곳으로 모으되(0-1) 서비스 클래스가 필요 없다.

**부채의 이유도 파일 크기가 아니다.** 954줄이라서가 아니라 —
**판정 3분류가 이 파일 안에서만 5번(`:223·443·531·693·896`) 다시 쓰였고
`:531`과 `:443`이 같은 화면 KPI에 다른 기준을 쓴다**는 것이 부채다.
**모듈 분할은 그 자체로 사고를 못 막는다.** 순수 함수 3개가 막는다.
의제 3의 값은 §8-5의 Swagger 생성이 성립하게 만드는 것 쪽에 더 크다.

### 4-b. 실행 대장 — 자산 대장이 구조적으로 못 담는 것

**§10-20에서 나는 *"나는 계약을 보고 경로를 안 본다"* 고 자기진단만 하고 교정을 못 찾았다.
critic이 원인을 짚었고, 그게 맞다.**

이번 주 A급 신규가 나온 자리를 되짚으면 전부 같은 종류다 —
A25는 **DELETE 다음 줄**, A31은 **`kind:` 필드**, A29는 **빠진 행 수**, A28은 **probe 경로**,
A23은 **`return` 다음에 뭘 *안* 하는지**.

**원인은 자산 대장의 정의 자체다.** §4는 자산을 *"두 곳 이상에서 쓰이는데 어긋나면 화면이 거짓말하는 것"*
으로 정의한다 — **값을 센다.** 실행 경로는 값이 아니라 **동사**라 이 대장에 들어올 자리가 없다.
그래서 다섯 번 놓친 건 부주의가 아니라 **정의의 귀결**이다.

**교정: 자산마다 세 가지를 더 묻는다.**

| # | 질문 | 이걸로 나온 것 |
|---|---|---|
| ① | 이 값을 **지우는** 코드는 어디 있고 **언제 도나** | A25(매일 07시 `delete`) · A30(문턱 7곳) |
| ② | 이 값을 쓰는 코드는 **실패를 어떻게 알리나 — 아니면 조용한가** | A23(`res.ok` 미검사) · `.catch(()=>{})` 24곳 |
| ③ | 이 **스키마를 적용하는 명령은 누가 언제 실행하나** | **A31** |

**단 문서로 만들지 않는다.** critic이 mw-auction의 `MODULE_MAP.md`를 기각한 이유(그쪽도 stale해졌다)가
여기 그대로 걸린다. 그리고 이 문서 자체가 §4-2에서 *"문서로 쓴 대장은 썩는다"* 고 이미 말했다.
**세 질문의 답은 적재 요약(§1-4)에 숫자로 싣는다 — 숫자는 매 실행 갱신되니까 썩지 않는다.**

> 이건 좌석이 둘인 이유의 실증이다. **§1-0(값,출처)은 critic이 못 냈고 내가 냈다.
> §4-b(경로)는 내가 못 냈고 critic이 냈다.** 편향이 반대 방향이라 서로의 사각지대를 덮는다.

**A29 — "공고당 학교 1개" 전제 (data 발견).**
`school_auctions`에서 빠진 10,770건 중 **공동구매가 5,966건(55.4%)**이고,
원본 `ds_SelectUnionPurceTgtListR`가 **대상교를 빠짐없이 준다(최대 18교)**. 우리가 안 읽을 뿐이다.
**나머지는 확정됐다: `len(opened) < 5` 문턱이 4,419건(누락의 41%), 시군구 빈칸이 6,067건(대부분 공동구매).
합쳐서 10,770건의 97.4%가 설명된다.**
탈락 학교의 회차 분포가 이 문턱의 성격을 말한다 — 1회 464 · 2회 1,218 · 3회 1,065 · **4회 1,796**.
**4회짜리가 가장 많다. 한 번만 더 열렸으면 통과했을 학교들이다.**
그리고 이 4,419건은 `firm_bids`에 **있다** → **"내 성적"엔 뜨고 학교 화면엔 없다.**
**맞다면 그건 "데이터를 임의로 버리기"이고 사용자 원칙과 정면으로 부딪힌다** —
표본이 적다는 사실은 화면이 말할 일이지 로더가 지울 일이 아니다(`floor_stats`의 P5 주석이 이미 그렇게 적혀 있다).
**§0-4의 정확한 반복이다: 원본이 주는데 우리가 안 읽고, 대신 규칙(문턱)으로 잘랐다.**

**그리고 이건 사고 6의 미발견분이다 (critic 판정 수용).**
사고 6은 `(userId, bidNo)` PK가 **사업자 축**을 못 담아 입력 46%가 저장 안 된 것이었다.
지금은 `bid_id` PK + `schoolId varchar NOT NULL` **단수**(`auctions.ts:46-47`)가 **학교 축**을 못 담아
5,966건이 적재 안 된다. **같은 모양이고, 그때 처방이 그대로 적용된다.**

**단 이번 주에 하지 않는다 (X17로 분리).** 스키마+적재+화면 동시 변경이라 §5-5에 걸리고,
**5,966건은 조용히 빠지는 게 아니라 처음부터 없던 것**이라 사용자가 지금 잃는 중인 값이 아니다.
→ 동결·관측창 뒤.

**이번 주에 할 수 있는 전부: 적재 요약에 제외 내역을 싣는다 (R21).**
`"10,770건 제외: 공동구매 5,966 · 표본 문턱 4,703 · 기타 281"`.
**다음에 이 숫자를 보는 사람이 원본을 다시 안 뒤져도 된다.** §4-b ①의 실행이다.
A30(문턱 제거)과 달리 A29는 **스키마를 고쳐야** 하므로 순서가 다르다.
이 중 A6·A8·A14는 **원본이 답을 갖고 있는데 안 실은 것** — 두 번의 실패와 같은 모양이다.

### 4-c. `FIELD-LEDGER` 검사 — **grep이 아니라 AST 집합 비교** (critic 제안 채택 → §10-21 해소)

원본 대장(`FIELD-LEDGER.md`)의 짝인 강제 장치다. §1-5에서 가드를 4개로 줄이며 이 검사를
"사람 리뷰"로 내렸었는데, **critic이 방법을 냈고 그게 맞다.**

**내가 못 찾았던 이유가 진단됐다: 틀린 접근은 코드를 grep하는 것이다.**
*"이 dict에 주석이 달렸나"* 는 구문 판정이라 파이썬의 모든 dict가 후보가 되고 오탐이 폭발한다.

**맞는 접근은 목록을 대조하는 것이다.** 질문을 바꾼다 —
*"주석이 있나"*(구문) 대신 ***"전에 없던 모듈 레벨 매핑 상수가 생겼나"*(집합 비교)**.

```python
# tools/serve/_ledger_check.py  (~25줄, 로더 시작 시)
names = {t.id for n in ast.parse(src).body if isinstance(n, ast.Assign)
         for t in n.targets if isinstance(t, ast.Name)
         and isinstance(n.value, (ast.Dict, ast.Tuple, ast.List, ast.Set))}
new = names - set(KNOWN[path])      # ledger-baseline.json — 커밋된 목록
if new: sys.exit(f"새 매핑 상수 {sorted(new)} — 원본에 대응 필드가 없음을 확인했으면 근거와 함께 baseline에 추가하라")
```

**오탐 0인 이유**: 정규식 추측이 아니라 **파서**가 이름을 정확히 준다.
기준이 "새로 생겼나"라 **기존 11개(`_ATOM`·`_SIDO_MAP`·`_SGG_CANON`·`CAT_KEYS`…)는
baseline에 그대로 커밋돼 한 번도 안 울린다.**

**새 개념이 아니다 — §1-0의 커버리지 baseline과 같은 메커니즘이다.**
나쁜 상태를 목록으로 박아두고 **변화만 고의로 만들게** 한다.

**붙는 자리도 더 낫다.** `ssot-guard.mjs`는 노드라 파이썬 AST를 못 읽는다. 이건 **로더 시작 시** 돈다.
그리고 그 슬롯이 지금 **비어 있다** — §1-2에서 `_contract.py` 해시 검증을 폐기하며 "로더 시작 5줄"이 났다.

**남는 한계(정직하게)**: 상수 이름을 안 바꾸고 **기존 dict에 항목만 추가**하면 안 걸린다
(`_ATOM`에 `"한우류"` 한 줄). 항목 해시까지 넣으면 정당한 확장마다 baseline을 고쳐야 해서
**실패2의 잔소리 죽음으로 간다. 거기서 멈추는 게 맞다** —
사고 1·2는 *"새 규칙 체계를 만들었다"* 였지 *"기존 표에 한 줄 더했다"* 가 아니었다.

## 6. 이 설계가 실패하는 시나리오 4개

### 실패 1 — ~~코드북이 원본에서 흔들린다~~ **폐기 조건이 소멸했다 (실측 통과)**

**폐기선을 통과했다.** 코드는 한 번도 안 흔들렸고 이름만 개명됐다(아래 실측).
`PURR_CD` 한 코드 → 두 기관명 **0 / 6,590**. **§2의 삭제 열한 개는 X20으로 확정 집행한다.**

> ⚠ **남는 한계 하나는 명시한다**: 표본 60,000 / 168,816(**36%**)이다.
> **폐교 후 재개교 같은 코드 재발급은 이 표본에서 안 보인다. 0/6,590은 강한 신호지 전수가 아니다.**
> 전수 재확인을 §5-3 착수 조건에 넣는다(8/30 이후).

아래는 이 결론에 이른 경과다 — **폐기선을 "비율"에서 "존재"로 바꾼 것이 결정적이었다.**

척추가 "원본 코드가 문자열 파싱보다 낫다"인데, 그게 틀릴 수 있다.
`SIGUNGU_CD`가 시점에 따라 다른 이름을 가리키면(2010 마산·진해→창원, 2023 강원·전북 특별자치도 개명),
"코드가 진실"은 파싱보다 나은 게 아니라 **다른 종류의 거짓**이 된다.
그 순간 우리는 `_SGG_CANON` 34줄을 **이미 지운 뒤**다 — 되돌릴 규칙이 없다.
`PURR_CD`도 같다. 통폐합·재발급되면 학교 정체성이 시간축에서 쪼개진다.

**개정 (critic §18-③): 폐기선을 비율에서 존재로 바꾼다. 그리고 답은 이미 나와 있다.**

1차안의 폐기선은 *"코드당 이름 다수결 일관성이 99%를 넘나"* 였다. **두 가지가 틀렸다.**

**(가) 지금 재면 위로 편향된다.** 백필이 넣는 건 옛 데이터이고, 옛 데이터가 마산시·진해시·덕양구가
사는 곳이다. 비율을 **낮추는 방향으로만** 움직인다. 지금 99.4%를 보고 규칙을 지우면
백필 완료 후 97%가 되는데 **되돌릴 규칙이 없다.** 이 시나리오가 스스로를 실현시킨다.

**(나) 99%든 97%든 처방이 같다.** 시간축 분열이 존재하는 순간 `코드→이름`은 **틀린 모델**이고,
비율은 "얼마나 자주 틀리나"를 말할 뿐이다. **처방을 안 바꾸는 측정은 판정선으로 쓸 값이 아니다.**

**→ 새 폐기선(존재·단조): *"한 코드가 시점에 따라 다른 이름을 가리키는 사례가 있나."***

**답은 예다. 그런데 처음에 든 증거가 틀렸다 — 정정한다.**

~~증거: `_SGG_CANON = {"마산시":"창원시", …}`. 저 표가 존재하는 이유가 정확히 그것이다.~~
**틀렸다. 그리고 이 오류는 내 것이다.**
`_SGG_CANON`은 **`이름 → 이름`** 매핑이다. **코드가 한 글자도 안 나온다.**
구조상 *"주소 문자열에 옛 지명이 섞인다"* 의 증거일 수는 있어도
*"코드가 의미를 바꾼다"* 의 증거는 **될 수가 없다.** 자료구조 모양만 봐도 알 수 있었다.
critic이 이 근거를 줬고 내가 검증 없이 받아 **"증거가 우리 코드에 박혀 있다"** 고 강조까지 붙였다(§10-27b).

그리고 `마산시`는 시간축도 아니다 — **2010 통합은 데이터 시작(2023)보다 13년 전**이라
통합 전 데이터가 이 데이터셋에 **아예 없다.** 2024~2026에 나오는 `마산시`는
**오늘 누가 주소 칸에 옛 지명을 친 것**이고 창원시와 연도 범위가 완전히 겹친다.

**그리고 인천 개편도 "코드 분열"이 아니었다 — 개명이었다. 내가 레이크에서 직접 쟀다:**
```
검단중학교  institution_code=144302  sigungu=서구    202606  5건
검단중학교  institution_code=144302  sigungu=검단구  202608  5건
```
**`PURR_CD`가 안 바뀌었다. `SIGUNGU_CD`도 안 바뀌었다(722 고정). `DOG_ADDR` 텍스트만 바뀌었다.**

**이게 실패 1의 폐기 조건을 사실상 없앤다.** 두 가지가 전혀 다른 것이었다:

| | |
|---|---|
| 실패 1의 공포 | 코드가 진실이 아니라 **다른 종류의 거짓** — 코드가 **다른 지역**을 가리키게 됨 |
| **실제** | 코드 722는 **한 번도 다른 지역을 가리킨 적이 없다.** 그 지역의 **이름**이 개명됐을 뿐 |

**정체성과 표시명이 분리된다.** 시간축이 필요한 건 `코드→표시이름` **하나뿐**이고 그건 **표시 계층**이다.
코드 자체는 안정적 정체성이다. → **`(코드, 개찰월)`은 유지하되 의미가 바뀐다**:
*"코드가 뭘 가리키는지가 시점마다 다르다"*(불안한 모델) 대신
***"그 지역을 그때 뭐라고 불렀나"***(단순한 표시 조회). §2-c 결정 ②가 그대로 적용된다.

**참고 — 아래는 critic이 처음 제시한 프레이밍이다. 사실은 맞고 해석이 틀렸다** (원시 20,000건):
```
코드 721:  중구    [2026-06만]  →  영종구   [2026-07~08]
코드 722:  서구    [2026-06만]  →  검단구   [2026-08만]
코드 723:  서구    [2026-06만]  →  서해구   [2026-07~08]
코드 720:  동구·중구 [2026-06]   →  제물포구 [2026-07~08]
```
**한 코드가 시점에 따라 다른 이름을 가리킨다.** 실패1이 두려워한 그것이 맞다.
다만 **2010 유산이 아니라 두 달 전 일이고, 우리 창 안이고, 또 일어난다.**

**따라서 결정한다: `코드→이름`이 아니라 `(코드, 개찰월)→이름`이다.**
**`(코드, 연도)`는 형태는 맞고 해상도가 부족하다** — 시행이 2026-07이라 2026을 하나로 묶으면
중구와 영종구가 같은 키에 남아 **여전히 충돌한다.** 월 단위여야 경계가 깨끗하다.

**그리고 선언 테이블로 만들지 않는다.** §2-c 결정 ②가 시도에 대해 이미 답을 냈다 —
*"원본이 준 값이라 선언 자체가 필요 없다. 목록은 DB에서 관측."*
**시군구도 같다: 이름을 `(코드, 개찰월)` 다수결로 관측한다.**
그러면 `_SGG_CANON`이 죽고 **새 매핑표가 그 자리를 대신하지 않는다.** 이게 §2의 목적이었다.

**그리고 이 측정이 폐기선 문제의 가장 깊은 판본을 드러냈다 — 순환이었다.**

critic 실측: 표본 19,984 · 조합 182 · 충돌 55 · **행 일관성 99.194%.**
**99.194%는 내 99% 폐기선을 넘는다. 그런데 그 숫자는 쓰레기다.**
충돌 소수파 182건의 정체가 이렇다:

| 갈래 | 건수 |
|---|---|
| **주소 파싱 잡음** (`급식실` 49 · `참고` 8 · `급식소` 7 · `중앙로` 3 · `식생활관` 2 …) | **100** |
| 계층 혼동 (창원시 vs 성산구·마산합포구, 전주시 vs 덕진구) | 다수 |
| 옛 지명 오타 (`마산시` 18 · `진해시` 1) | 20 |
| **진짜 시간축 분열** | **인천 4개뿐** |

**이 측정은 주소에서 뽑은 이름을 정답지로 삼아 코드북을 채점한다.**
**코드북이 대체하려는 대상이 곧 채점 기준이다. 순환이다.**
0.8%의 절반 이상이 코드북과 무관한데, 그 숫자로 §5-3의 존폐를 갈랐으면
**잘못된 대상을 재고 통과시킨 게 된다.**

> **비율이 문제가 아니라 그 비율이 무엇을 재고 있었는지가 문제였다.** → §10-26에 ③으로 추가.

- 남는 위험(변함없음): "지금 이름"을 골라야 하는 화면(지역 칩)에선 결국 하나를 고른다.
  그때 고르는 규칙은 **표기이지 진실이 아니다** — 화면이 "현재 행정구역 기준"이라고 말한다.
- **§5-3의 폐기 여부는 이제 이 측정에 안 걸려 있다.** 남은 건 `SIGUNGU_CD → 이름` 커버리지인데 —

**그 커버리지 폐기선(98%)도 같은 함정이었다 (critic이 §10-26의 검사를 대신 돌렸다).**

내가 *"§2-b에 같은 검사를 아직 안 해봤다"* 고 신고했고, critic이 해봤다. **걸린다.**

- *"96%든 99%든 처방이 달라지나"* → **안 달라진다.** §1-0②가 이미 못박았다 —
  코드 없으면 `sigungu: null`, 규칙으로 안 메움, 화면은 "지역 미상".
  **99%면 1%가 빈칸, 96%면 4%가 빈칸. 처방 동일, 개수만 변한다.** 임계값이 아무 결정도 안 가른다.
- **걸려 있는 것도 생각보다 적다.** §5-3-14가 *"`schools.id`는 그대로 — URL이 산다"* 이므로
  **school_id는 문자열 유래로 남는다.** 코드북 결측은 **표시·필터 축에만** 영향하고
  **학교 정체성은 안 건드린다.** "커버리지가 낮으면 학교가 사라진다"는 공포는 성립하지 않는다.

**→ 진짜 질문은 비율이 아니라 분포다:**

> ❌ *"행 커버리지가 98%를 넘나"* → ✅ ***"이름 없는 코드가 사장이 실제로 보는 지역 안에 있나"***

| 결측 2%가 어디 있나 | 처방 |
|---|---|
| 세종·제주 같은 꼬리 | **그대로 간다.** 아버지 화면에 안 나온다 |
| **김해시 안** | 아버지가 자기 지역 공고에서 "지역 미상"을 본다. §1-0②의 "빈칸을 보인다"가 아니라 **기능 상실**이고 폴백이 필요하다 |

**같은 2%인데 처방이 정반대다.** 그리고 이건 **스냅샷으로 지금 답하는 분포 질문**이다 —
백필 정지도 재파싱 완료도 필요 없다.

> 이 서비스의 판정 기준이 원래 그것이다 — **"전체의 몇 %"가 아니라 "아버지 화면에 뜨나"**.
> **나는 비율로 폐기선을 두 번 세웠고 두 번 다 그 기준을 안 썼다.**

### 실패 2 — 가드가 잔소리가 되어 죽는다 (§1-5 무력화)

1인 개발 + 에이전트 팀에서 **allowlist 추가는 언제나 수정보다 싸다.**
에이전트가 급할 때 가드에 막히면 고치는 대신 allowlist에 넣고 간다. 3개월 뒤 40줄이면 가드는 죽은 것이다.
`until` 만료를 걸었지만 **만료일을 미루는 것도 한 줄**이다.

- 조기 신호: allowlist 항목 수, 그리고 **연장 횟수**
- 완화: 연장 1회 제한 + `# why:` 필수. 2회째부터 빌드 실패
- 남는 위험: 규칙 만드는 사람과 지키는 사람이 같으면 어떤 자동화도 최종적으로 자발성에 기댄다.
  **이 설계는 그 사실을 없애지 못한다. 비용만 올린다.**

### 실패 3 — ~~생성이 오히려 새 이중성을 만든다~~ **(소멸. §1-2에서 생성기를 폐기했다)**

<details><summary>원문</summary>

`_contract.py`는 **커밋된 생성물**이다. 생성물을 리포에 두는 순간 "원본과 생성물" 두 파일이 생긴다.
지금 없던 이중성이다. 봉인(빌드 diff + 로더 해시)이 그걸 막지만, **봉인이 불편해지는 순간이 온다**:

- 완화: 생성물을 리포에 두지 않고 **로더 시작 시 DB에서 어휘를 읽는다**(서빙 DB에 `vocab` 테이블 1개).

- 남는 위험: 완화안은 "어휘의 진실이 DB"가 되어 §1-6에서 기각한 안("오타가 진실이 된다")에 가까워진다.
  **이 트레이드오프를 나는 아직 못 골랐다. critic 좌석의 판단을 받고 싶은 1순위 항목이다**

</details>

### 실패 4 — 측정 대상이 움직인다 (**이 팀의 방법 자체의 실패. 이미 일어나고 있다**)

앞의 셋은 설계가 틀리는 시나리오다. 이건 **설계를 검증하는 방법이 틀리는** 시나리오다.

이 문서는 거의 모든 결정을 측정에 걸어뒀다 — §5-0b의 여섯 항목, 실패1의 폐기선(일관성 99%),
§2-b의 행 커버리지 98%, §1-0의 커버리지 baseline 36.6%. **전부 숫자다.**
그런데 **백필 체인이 13시간째 레이크에 쓰고 있어 같은 질의가 실행할 때마다 다른 답을 준다.**
data가 같은 4개 id를 조회했는데 한 번은 3건, 다시 하니 1건이었다.
`전남광주 27곳`이 재측정에서 **8건**이 된 것도 같은 원인이다.

**"측정으로 설계를 검증한다"는 이 팀의 방식이, 측정 대상이 움직이면 성립하지 않는다.**
흔들리는 수치 위에 선 폐기선은 폐기선이 아니다 — 재실행하면 판정이 뒤집힌다.

**대응이 바뀌었다 (critic §18). "정지를 기다린다"는 선택지가 아니었다.**

**① 레이크가 스냅샷을 공짜로 준다.** `lake.py`를 직접 확인했다:
`write_batch`는 append-only·잠금 없음이고, 파일명이 `part-{time_ns:020d}-{uuid}`(`:75`) —
**20자리 제로패딩 단조 나노초**라 문자열 정렬이 곧 쓰기 순서다(`:72-74` 주석이 의도로 적어놨다).
그리고 `connect()`의 중복 제거가 `order by filename desc`(`:130-136`)다.

**따라서 파일명 접두 ns에 상한을 걸면 시각 T에 `connect()`가 돌려줬을 결과를 정확히 재현한다.**
백필이 계속 돌아도 같은 질의가 같은 답을 준다. 복사도 정지도 락도 없다.

> ⚠ **구현 함정**: 상한을 **뷰 바깥에 `where`로 걸면 안 된다.**
> `lake.py:126-141`이 `select * exclude (_rn)`이라 **`filename`이 뷰에 그대로 남아** 에러도 안 난다.
> 그런데 뷰 안에서 `row_number()` 중복 제거가 이미 끝나 있어서,
> **최신 버전이 T 이후인 행은 구 버전으로 대체되는 게 아니라 통째로 사라진다.**
> 그리고 **백필이 많이 건드린 행일수록 잘 사라져 하필 우리가 재려는 것에 편향이 걸린다.**
>
> **정확한 형태 — `read_parquet` 직후·`row_number()` 이전:**
> ```sql
> from read_parquet('…/**/*.parquet', hive_partitioning=true, filename=true, union_by_name=true)
> where regexp_extract(filename, 'part-(\d{20})-', 1) <= '<T의 ns 20자리>'
> ```
> 20자리 제로패딩이라 **문자열 비교가 곧 수치 비교**다.
> `filename`은 전체 경로이고 **윈도에선 역슬래시**(`data\parquet\auctions\year=2023\…`), 컨테이너에선 슬래시다 —
> `part-(\d{20})` 패턴은 **구분자 무관**이라 양쪽에서 같이 돈다.
> 전체 경로를 그냥 비교하면 안 되는 이유는 `year=`/`month=`를 먼저 비교하기 때문이다.
>
> **기존 dedupe 자체는 안전하다**(critic 재검증, 0건): `_partition(announced_at)`이 bid_id마다 고정이라
> 한 그룹은 같은 디렉터리를 공유하고, 전체 경로 비교가 basename 비교로 환원된다.

**이건 실패 4의 조기 신호도 된다** — 나중에 더 큰 상한으로 같은 질의를 돌려 답이 움직였는지 본다.
안 움직였으면 그 측정은 백필과 무관했던 것이다. "정지를 기다린다"는 이진 선택보다 싸고 정확하다.

**② 내 분류에 가운데가 빠졌다 — 단조 존재 질문.**
"코드로 확정" vs "비율이 판정선을 넘나든다" 둘로 갈랐는데, **백필이 반례를 추가만 하는 질문**이 따로 있다.
*"찾았다"가 즉시 확정*이고 *"못 찾았다"만 미확정*이라 데이터가 자라도 답이 안 뒤집힌다.

| 분류 | 백필 중 확정 가능? | 해당 |
|---|---|---|
| **코드로 확정** | ✅ 지금 | A30 문턱 7곳 · A23 두 겹 · A25 부분 실패 · A31 · 버려지는 *조건* |
| **단조 존재 질문** ← 빠졌던 칸 | ✅ **1건만 찾으면 확정** | **A6 정의**(n=1) · `PDLC_NM` 존재 · `PURR_CD` 분열 · `QLFC_LMT_YN` 대응 |
| **비율이 판정선을 넘나듦** | 🟡 스냅샷으로 재현 가능, 단 ③ 주의 | 커버리지 baseline · 문턱 삭제 손익 |

**③ 반대 방향 하나 — 실패 1의 99% 폐기선은 지금 재면 위로 편향된다. 스냅샷으로도 못 고친다.**

> **기전 정정 (critic §20 자기 정정)**: 처음엔 *"백필이 옛 데이터를 넣고 옛 데이터에 마산·진해가 산다"* 였는데
> **틀렸다.** 실측: 백필은 라이브 `data/parquet`에 쓰고 있고 **중복 bid_id 0건** —
> 재파싱이 아니라 **처음 보는 회차**를 넣는 중이다. 마산·진해는 경남(15), 덕양구는 경기(8)로 **이미 수집됐다.**
>
> **진짜 기전은 더 세다: 들어오는 게 코드 18 — `전남광주통합특별시` 전체다.**
> **58,459건, 현재 162,122건 대비 최종의 약 26%.** 그리고 하필 §2-c에 내가 방금
> *"행안부 체계에 없는 eaT 자체 명칭 · 두 시도를 합친 이름 · 서울 다음 최대"* 로 기록한 그 지역이다.
> **꼬리가 두꺼워지는 게 아니라 구성이 바뀐다.** 코드 18 전에 재면
> **가장 이상한 지역이 빠진 채로 재는 것**이라 숫자가 진실보다 **높게** 나온다.

즉 백필은 이 비율을 **낮추는 방향으로만** 움직인다.
함정이 성립한다: 지금 잰다 → 99.4% → 폐기선 통과 → §2의 규칙 열한 개 삭제 → 백필 완료 → 97% →
**되돌릴 규칙이 이미 없다.** 내가 실패 1에 *"그 순간 `_SGG_CANON` 34줄을 이미 지운 뒤다"* 라고 쓴
바로 그 시나리오이고, **백필이 지금 그 확률을 최대로 올려놓고 있다.**
스냅샷은 재현성을 주지 편향을 없애지 않는다 — 표본이 계통적으로 치우쳐 있다.

**→ 폐기선을 비율에서 존재로 바꾼다 (실패 1 개정).**

- 남는 진짜 정지 대기: **커버리지 baseline 하나뿐**이고, 그건 정의상 **재파싱 후**가 맞다(§5-0의 0-c).
- **사장·리더에게 넘겼던 결정을 회수한다.** 물어볼 것이 아니었다.

> **이 실패가 앞의 셋보다 나쁜 이유**: 실패 1~3은 틀렸다는 걸 나중에 알 수 있다.
> 실패 4는 **맞았는지 틀렸는지를 알 방법이 없다.** 측정이 재현되지 않으면 반증도 불가능하다.
>
> 그리고 이번 주에 이미 두 번 작동했다 — `PDLC_NM` 품목 가설(픽스처가 가짜)과
> `PDLC_NM` 소재지 가설(자격 지역을 소재지로 오독). **둘 다 ⚠를 달아둔 덕에 피해가 0이었다.**
> **⚠ 표기가 이 문서의 유일한 실패4 방어다.**

| `api-types.generated.ts` — **NestJS Swagger `/docs-json`에서 생성** | `pnpm generate:api-types` | ✅ **내가 §8-5에서 제안한 "API 대장"이 이미 있다** |
| `@tanstack/react-query-next-experimental` | 스트리밍 하이드레이션 | ❌ 보류 (§8-7) |

**우리와 안 맞는 것 하나를 먼저 지목한다: 폴링.**
mw-auction은 10초 스냅샷 주기라 `refetchInterval`이 구조의 축이다.
**우리는 하루 1회 갱신**이다(로더가 밤에 돈다). `create-polling-query.ts`는 우리에게 죽은 코드다.
대신 우리에겐 mw-auction에 없는 축이 있다 — **`fetchedAt`**(`open_auctions.fetched_at`).
서버가 이미 "이 데이터가 언제 것인지"를 내려주고 있다. 캐시 정책을 시계가 아니라 **그 값에 건다**(§8-2b).

### 8-1. 리더의 3층 구분 — 칸 수는 맞고 **경계가 틀렸다**

리더 안: 서버 상태→`react-query` / 클라이언트 상태→스토어 / UI 상태→`usePersistedState`.
칸 수는 맞다. 그런데 **가르는 축이 "서버냐 클라냐"인 게 문제다.** 이 문서가 내내 묻는 축은 하나다 —
**누가 진실인가.** 그 축으로 다시 그으면 경계가 달라진다.

상태마다 세 가지를 묻는다: ① 진실이 어디 있나 ② 잃으면 어떻게 되나 ③ 게스트에서 살아야 하나.

| 층 | 진실 | 잃으면 | 게스트 | 해당 | 도구 |
|---|---|---|---|---|---|
| **L1 원격 사실** | 서버 DB | 재조회하면 됨 | 무관 | 공고·회차·낙찰·예보·로스터·업체 | **react-query** |
| **L2 계정 데이터(이중 권위)** | **게스트=브라우저 / 로그인=서버** | **사용자 데이터 소실** | **살아야 함** | `bizNos`·`regions`·`marks` | **전용 스토어(현행 유지)** |
| **L3 화면 상태** | 이 브라우저 | 아무 일 없음 | 무관 | 렌즈·펼침·필터·`viewRegion` | **`usePersistedState`** |

**리더 안과의 차이는 L2다.** 리더는 이걸 "클라이언트 상태 → Zustand"로 뒀다.
나는 **L2는 상태 라이브러리로 안 풀린다**고 판정한다. 진실이 **로그인 여부에 따라 이동하는** 상태이고,
Zustand에도 react-query에도 "두 진실을 합친다"는 개념이 없다. `session.ts` 210줄 중 대부분이 그 일이다.

### 8-2. `marks` 판정 — **L2다. react-query mutation 아니다** (리더 안에 반대)

리더는 *"낙관적 업데이트가 필요한 서버 상태 = mutation 영역"*으로 봤다. 세 가지 근거로 반대한다.

1. **게스트에서 완전히 동작해야 한다.** "로그인 없이 전 기능"은 이 서비스의 제약이다(`auth.ts` 주석·`session.ts:5`).
   mutation은 서버가 있다는 전제 위에 선다. 게스트면 mutation 대상이 없다.
2. **`/api/me/marks`는 낙관적 업데이트의 대상이 아니다.** `app.module.ts:838`이 `delete` 후 `insert` —
   **전체 치환 PUT**이다. mutation+invalidate 패턴이면 값 하나 칠 때마다 전량 PUT + 전량 refetch가 된다.
   지금(로컬 즉시 + 백그라운드 PUT)이 더 낫다.
3. **리더가 든 사고 근거가 오히려 반대를 가리킨다.** 둘째 사업자 값이 지워진 건 mutation이 아니라
   **최초 로그인 1회 병합**에서 났다(`session.ts` boot의 `needMerge` 블록).
   `react-query`에는 그 개념 자체가 없다. 라이브러리를 넣어도 **그 코드는 한 줄도 안 준다.**

**다만 리더 지적의 알맹이는 맞다: 손으로 짠 병합이 사고를 냈다.**
처방은 라이브러리가 아니라 **이 문서의 원칙 그대로** — 규칙을 한 곳에, 그리고 순수하게:

```ts
// packages/shared/src/domain/merge.ts   ← 순수 함수, 서버·웹 공용, 테스트 가능
export function mergeAccountData(local: AccountData, server: AccountData): AccountData
```
지금 이 규칙은 `boot()` 안에 인라인이라 **재사용도 검증도 안 된다.**
이 프로젝트에서 사고를 낸 건 언제나 "한 곳에 없는 규칙"이었지 "라이브러리가 없어서"가 아니었다.

### 8-2b. `CACHE` 상수 — `packages/shared`에 둔다. 값은 **`fetchedAt`에 건다**

mw-auction처럼 shared에 둔다. 이유는 "그쪽이 그래서"가 아니라 **캐시 정책이 데이터의 갱신 리듬이고,
그 리듬을 아는 건 로더(파이프라인)지 화면이 아니기 때문**이다. 화면이 `staleTime: 60_000`을 손으로 쓰면
그건 §3-1의 "웹이 스스로 만드는 것"이 하나 더 느는 것이다.

```ts
// packages/shared/src/config/cache.ts
export const CACHE = {
  DAILY: hours(6),      // 로더가 하루 1회 — 6시간이면 같은 날 재조회 0
  OPEN: minutes(30),    // 열린 공고: 마감이 다가오므로 짧게
  ME: 0,                // 계정 데이터는 L2. 캐시 대상 아님
  LOOKUP: hours(24),    // 상호명 — 안 변한다
} as const;
```

**그리고 시계보다 나은 신호가 이미 있다.** `open_auctions.fetched_at`을 응답에 실어 보내면
화면이 *"몇 시 기준 자료"* 를 말할 수 있다 — **헌법의 "사실 + n 명시"가 캐시에도 적용된다.**
`staleTime`은 재조회 타이밍을 정할 뿐이고, **사용자에게 보이는 건 `fetchedAt`이어야 한다.**
지금은 데이터가 오래됐는지 화면이 말하지 않는다. 이건 캐시 도입의 부수효과가 아니라 **얻어야 할 것**이다.

> 로더가 `fetchedAt`을 이미 쓰고 있는데(`open_auctions` 기본값) **아무 화면도 안 읽는다.**
> §0-4("원본이 준 값을 버린다")와 같은 모양이 우리 API에서도 일어나고 있다.

### 8-3. Zustand — **L2를 대체하지 않는다. 다만 mw-auction 용법은 채택한다**

`session.ts` 210줄을 Zustand가 무엇으로 갚는지 세어봤다.

| Zustand가 **대체하는 것** | 줄 |
|---|---|
| `listeners` Set · `emit()` · `setState()` · `subscribe` · `getSnapshot` · `getServerSnapshot` | **약 15줄** |

| Zustand가 **대체 못 하는 것** | 줄 |
|---|---|
| `boot()` 이중 권위 병합(`needMerge`·회차별 rates 보존) | ~40 |
| `readLocal`/`writeLocal`/`put` 3중 쓰기 | ~35 |
| marks 손상 사본 보존(`marksUnreadable`·`MARKS_BACKUP_KEY`) | ~15 |
| `loadBizNames` 지연 조회 | ~12 |

**순비용: 의존성 +1, 없애는 줄 15, 그리고 잃는 안전장치 1개.**
`persist` 미들웨어를 쓰면 방금 만든 `use-persisted-state.ts`의 세 규칙 중 **3번(손상 사본 보존)을 잃는다** —
Zustand persist는 읽기 실패 시 조용히 초기값으로 간다. 우리는 그 조용함 때문에 고지 UI를 만들었다.
**정당화되지 않는다.** 방금 만든 걸 버리는 비용까지 더하면 더 그렇다.

**재검토 트리거(숫자로 못박는다)**: `session.ts`가 **300줄**을 넘거나 구독 훅이 **6개**를 넘으면 다시 본다.
그때는 L2가 진짜 스토어 규모가 된 것이다. 그 전엔 아니다.

**mw-auction 실측이 이 판정을 바꾸지 않는다 — 오히려 확인해 준다.**
그쪽 zustand는 **전역 앱 스토어가 아니라 feature-local 스토어**다:
`community/model/{identity,votes,reports}.store.ts` · `s/_lib/my-settlements.store.ts` · `server-online/model/jitter.store.ts`.
전부 **서버에 진실이 없는 값**(익명 신원·내 투표 기록·로컬 정산 메모)이고, **전부 `.spec.ts`가 붙어 있다.**
즉 mw-auction도 zustand를 **서버 캐시 대체재로 쓰지 않는다.** 우리 L2(이중 권위 + boot 병합)와는 층이 다르다.

**채택하는 것은 라이브러리가 아니라 그 용법이다**: *작고 · 순수하고 · 테스트가 붙은 모듈*.
그게 §8-2에서 내가 `mergeAccountData()`로 제안한 것과 같다. mw-auction은 그걸 zustand로 담았고,
우리는 이미 `useSyncExternalStore` 스토어가 있으니 **담을 그릇을 바꿀 이유가 없다.** 규칙만 꺼내면 된다.
새로 생기는 순수 클라 상태(서버에 진실이 없는 것)가 나오면 그때 zustand를 쓴다 —
단 **`persist` 미들웨어는 쓰지 않는다**(손상 사본 보존 규칙을 잃는다. §8-3 위).

### 8-4. react-query ↔ 계약 설계의 맞물림 (front가 기다리는 답)

**결정: 쿼리 선언은 계약의 *소비* 지점이다. 계약을 검증하지 않고, 계약에서 타입을 받는다.**

```
packages/shared/src/domain/*.ts     ← 계약 (zod 스키마)
        │  타입만 흐른다 (z.infer) — 런타임 파싱 없음
        ▼
apps/web/src/lib/queries/*.ts       ← queryKey + fetcher + 반환 타입
        ▼
화면                                 ← useQuery(roundsQuery(schoolId))
```

- **타입은 계약에서 파생된다.** 웹이 응답 타입을 선언하지 않는다 → **§0-5의 로컬 타입 23개가 여기서 죽는다.**
  react-query 전환과 계약 도입은 **별개 작업이 아니라 같은 작업**이다.
- **런타임 파싱은 한다. 이건 내 앞선 판단을 뒤집는 것이다.**
  1차안에서 나는 *"서버와 웹이 컴파일 타임에 같은 타입을 공유하므로 어긋날 경로는 배포 스큐뿐"* 이라고 썼다.
  **그 전제가 지금 우리에겐 거짓이다.** §0-6에서 내가 직접 확인했듯 **서버는 zod 계약을 응답에 적용하지 않는다** —
  `OpenAuction`·`SchoolSummary`·`FirmRecord`는 어디서도 응답에 안 걸린다. 즉 **서버가 계약과 다른 걸 보내는 게 지금 정상 상태**다.
  컴파일 타임 공유는 §5-2-9가 끝난 *뒤에* 생기는 성질이지, 지금 있는 게 아니다.
  **런타임 파싱은 그 괴리를 보이게 만드는 유일한 장치**이고, mw-auction의 `safeApiJson`이 정확히 그걸 한다
  (`z.safeDecode` → 실패 시 Sentry 보고 → 사용자에겐 "데이터를 불러올 수 없습니다"). 우리도 Sentry가 이미 붙어 있다.
- **기본은 파싱, 면제는 측정된 숫자로만.** `/firms/bids`(limit 5000)·`/wins/recent`(limit 1000)처럼
  큰 배열은 비용이 실재한다. **면제하려면 `scripts/ssot-allow.json`에 실측 ms를 적어야 한다** — 추측 금지.
  이 규칙이 없으면 "무거울 것 같아서" 전부 면제되고, 그러면 장치가 없는 것과 같다.
- **`/api/me`는 실패 시 게스트 폴백.** 다른 곳은 throw + ErrorBoundary. 계정 데이터는 못 읽는 것보다 게스트가 낫다.
- **덤으로 URL 조립이 한 곳이 된다.** 지금 55곳이 각자 `?bizNos=${bizNos.join(',')}` 를 만든다.
  `queries/`로 모으면 **키 조립을 한 곳으로 모으는 §1-3과 같은 계열의 이득**이다.
- **같은 queryKey를 공유하면 두 화면이 같은 데이터를 본다.** 지금 오늘 화면과 분석판이 각자 fetch한다.
  다만 **같은 데이터를 봐도 계산이 두 곳이면 답은 여전히 갈린다** → 8-5.

### 8-5. 0-1(예보 알고리즘 2벌)은 이 결정으로 **안 풀린다** — §1-3의 한계 자백

리더가 "§1-3이 이 경우에 실제로 작동하는지 구체적으로 보여라"고 했다. **작동하지 않는다.**

상태 라이브러리는 "누가 데이터를 갖고 있나"를 정리하지 **그 데이터로 무엇을 계산하나**를 정리하지 않는다.
react-query를 넣으면 웹이 `rounds`를 캐시하고 **여전히 자기가 예보를 계산한다.** 오히려 편해져서 늘 수도 있다.

**브랜디드 타입도 못 잡는다.** 이런 걸 시도할 수 있다:
```ts
declare const served: unique symbol;
type Served = { readonly [served]: true };
export type Forecast = { medGapDays: number; expected: string; dueInDays: number } & Served;
```
웹이 만든 객체를 `Forecast` 자리에 넣으면 컴파일이 깨진다. **그런데 웹이 자기 타입을 새로 선언하면 우회된다.**
그리고 지금 정확히 그렇게 돼 있다 — `analysis-board.tsx:504`의 `forecast` useMemo는 익명 객체를 만들어
`Forecast` 타입을 아예 안 거친다. **타입은 "안 쓰기로 한 사람"을 못 막는다.**

`Math.floor(gaps.length / 2)`는 그냥 숫자 계산이라 타입 시스템이 볼 게 없다.
**§1-3은 키(A3)에는 작동하고 알고리즘(0-1)에는 작동하지 않는다. 인정한다.**

실제로 잡는 건 둘뿐이고, 둘 다 타입보다 약하다:
1. **가드 grep** — `apps/web/**`의 `864e5` · `Math.floor(*.length / 2)`. 이미 §1-5 표에 있다. **이게 유일한 실효 장치다.**
2. **API 대장** — 내가 §8-5에서 손으로 쓰자고 제안했던 것을 **mw-auction이 이미 생성물로 갖고 있다**:
   `packages/shared/src/api-types.generated.ts`, **NestJS Swagger `/docs-json`에서 생성**(`pnpm generate:api-types`).
   우리도 같은 방식으로 간다 — `@nestjs/swagger`를 붙이고 `openapi-typescript`로 뽑는다.
   손으로 쓰는 `API-LEDGER.md` 안은 **폐기**한다(§4의 FIELD-LEDGER와 달리 이건 자동화가 되는 대상이다).
   웹이 뭘 계산하려 할 때 "서버가 이미 주고 있나"를 볼 곳이 지금 **없다** — 그래서 베꼈다.
   **다만 이건 의제 3(NestJS 모듈 분할)이 먼저 끝나야 값이 산다** — 지금처럼 954줄 인라인이면 Swagger 문서도 954줄이다.

> **0-1의 진짜 원인은 상태 관리도 타입도 아니다. "서버가 이미 준다"를 볼 방법이 없었던 것이다.**
> 원본을 못 봐서 규칙을 쌓은 것(§0-4)과 **똑같은 실패를 우리 API에 대해 한 것**이다.

### 8-6. `marks` 낙관적 업데이트 — `onMutate`/`setQueryData`/롤백으로 **안 풀린다** (리더 Q5)

낙관적 업데이트의 정의는 *"서버 응답을 기다리지 않고 캐시를 먼저 고치고, 실패하면 되돌린다"* 이다.
`marks`는 세 조건이 다 어긋난다.

| 낙관적 업데이트의 전제 | `marks`의 실제 |
|---|---|
| 캐시가 진실의 사본이다 | **게스트는 서버가 아예 없다.** 되돌릴 원본이 없다 |
| 실패하면 되돌리는 게 맞다 | **되돌리면 안 된다.** 사장이 방금 친 값이 사라진다 — 로컬에 남기는 게 맞다 |
| 서버 응답이 다음 진실이다 | `PUT /me/marks`는 **전체 치환**이고 응답은 `{ok, n}`뿐이다. 돌아올 진실이 없다 |

지금 구조(로컬 즉시 쓰기 → 백그라운드 PUT → 실패해도 로컬 생존)는 **낙관적 업데이트가 아니라

**리더가 든 사고(둘째 사업자 값 소실)는 여전히 실재하고, 처방은 §8-2 그대로다**:
`mergeAccountData()` 순수 함수 + `.spec.ts`. mw-auction의 store들이 전부 spec을 갖고 있는 것과 같은 규율이다.
**라이브러리는 이 사고를 못 막는다. 테스트가 막는다.**

## 9. drizzle 툴킷 — DDL 이중성(A16)을 없앤다

사용자 지시: *"그 드리즐 툴킷이나 이런 거 전부 다 써."*
**"전부 다"를 그대로 따르지 않는다.** 하나(`push`)는 우리 환경에서 §0-5 사고를 **되풀이할 도구**다.
안 쓸 것을 안 쓴다고 보고하는 게 이 지시에 맞는 답이다.

### 9-000. **먼저: DDL을 적용할 경로가 지금 없다 (A31 · critic A-6)**

내가 *"`schema.sql`은 매 배포가 아니라 Job의 initContainer에서 돈다"* 고 정정했더니
critic이 그 정정에서 **더 나쁜 걸 열었다.** 실물로 검증했다:

| 확인 | 결과 |
|---|---|
| `app.yaml:150` | `kind: Job` (`initial-load`) — **ArgoCD hook 어노테이션 없음**(전 파일에 `hook` 문자열 0건) |
| `kustomization.yaml:9` | `disableNameSuffixHash: true` → ConfigMap 내용이 바뀌어도 **이름이 같아 롤아웃 트리거가 없다** |
| Job `spec.template` | **immutable** — 명령을 고치면 sync가 `field is immutable`로 실패한다 |
| `daily-refresh` CronJob | psql을 **안 돈다** |

**결론: `schema.sql`에 ALTER를 추가해도 이미 도는 클러스터에는 영원히 적용되지 않는다.**
그 파일은 스스로 *"라이브 마이그레이션 병기"*(`:123`·`:193`)라고 선언하며 ALTER를 쌓고 있다 —
`account.issuer`(better-auth 콜백 실패를 고친 그 컬럼) · `user_mark` PK 교체(사고 6 수정분) ·
`categories`/`category_src`(사고 1 수정분) **전부**.

**재현**: `categories` 추가 커밋 → ConfigMap 갱신 → **아무것도 안 돎** → 로더가
`insert into school_auctions (…, categories, …)`(`load_postgres.py:282-283`) → `column does not exist`
→ 롤백 → **7개 테이블이 통째로 안 채워진다.** 크론이라 무인이다.

지금 안 터진 건 클러스터가 재생성됐거나 누가 손으로 psql을 돌렸기 때문인데 **리포에 기록이 없다.**
**그게 이 항목의 본질이다 — 스키마 적용이 사람 기억에 의존한다.**
사고 4의 재발 조건이다. 그때는 **틀린 SQL이 자동으로 돌았고**, 지금은 **맞는 SQL이 안 돈다.**

> **X16 (이 문서 전체에서 가장 급한 한 건): Job에 `argocd.argoproj.io/hook: PreSync` +
> `hook-delete-policy: BeforeHookCreation`.** `schema.sql:1-5`가 멱등을 보장하려고 쓰였으니 반복 안전하다.
>
> **그리고 이건 §9 전체의 선행 조건이다.** 내 베이스라인 B6은 "`migrate`를 한 번 돌린다"인데
> **지금 라이브 클러스터에 SQL을 돌릴 경로 자체가 없다.** 경로를 먼저 만들지 않으면 B6을 실행할 수 없다.
> critic 표현이 정확하다 — **"지금은 생성기가 없어서가 아니라 실행이 없어서 문제다."**
> A16(DDL 이중성)보다 **A31(DDL 무실행)이 먼저다.**

### 9-00. 실행 시점 — **이번 주에 하지 않는다** (critic 지적 수용, 사실 하나 정정)

critic이 *"§5-2-11을 이번 주에서 빼라"* 고 했다. **받는다.** 근거가 맞다:
`schema.sql`은 지금 **살아 있는 멱등 마이그레이션**이고, drizzle은 비멱등 CREATE + `__drizzle_migrations`를
전제하는데 **그 테이블이 이 DB에 없다.** 살아있는 DB의 마이그레이션 메커니즘 교체다.

**다만 사실 둘을 정정한다(실물 확인):**
1. `schema.sql`은 **매 배포가 아니라 `initial-load` Job의 initContainer**에서 돈다(`app.yaml:150-163`).
   교체 범위가 "배포 전체"가 아니라 **Job 하나의 명령**이라 critic이 본 것보다 좁다.
2. **`|| true`는 이미 제거됐다.** 커밋 `6d91978`이 걷어냈고 지금은 `psql -v ON_ERROR_STOP=1`이다.
   DEBT.md A-2는 그 커밋 이전 상태를 본 것으로 보인다. (주석이 사고 4의 1차 사료로 남아 있다.)

**새로 드러난 비용 하나**: 데이터플레인 이미지는 **파이썬**이다. `drizzle-kit migrate`는 노드가 필요하다.
마이그레이션 Job을 별도 이미지로 세우거나 노드를 얹어야 한다 — 1차안이 안 센 비용이다.

**결정: §9는 설계로 확정하되 실행은 §5-1(거짓말 멈추기) 완료 후.**
그 전에 할 수 있고 위험이 0인 것 하나는 **지금 한다 — `pull` + diff(B1·B2).**
DB에 한 글자도 안 쓰고, 리더가 막으라 한 사고 ①(*"스키마와 실제 DB가 어긋나도 아무도 모름"*)을
**즉시 드러낸다.** 나머지(B3~B7)는 그 diff를 보고 판단한다.

### 9-0. 위험도가 크게 낮다 — 같은 beta를 쓰는 형제 프로젝트가 있다

`drizzle-orm/drizzle-kit 1.0.0-beta.22`는 beta라 도입 전에 걸렸는데, **mw-auction이 정확히 같은 버전을
프로덕션에서 쓴다.** 그리고 그쪽엔 **손유지 `schema.sql`이 없다** — `generate`+`migrate`로 마이그레이션
18개(파티션·인덱스 교체 포함)를 운용한다. 우리가 하려는 것이 이미 검증돼 있다.
설치된 CLI 실측 명령: `generate · migrate · pull · push · studio · up · check · export`.

### 9-1. 도구별 판정

| 도구 | 판정 | 이유 |

| `migrate` | ✅ **핵심** | **유일한 DDL 적용 경로.** k8s Job으로 |

### 9-2. 베이스라인 — 사용자 데이터가 위험해지는 경로가 없음을 보인다

현 상태: 라이브 DB는 손유지 `schema.sql`로 만들어졌고, `packages/shared/drizzle/`엔 08-27자 마이그레이션이
**하나** 있는데 그 뒤 컬럼 추가는 전부 `schema.sql` ALTER 블록으로만 갔다.
즉 **마이그레이션 원장(`__drizzle_migrations`)이 라이브 DB에 없거나 현실과 안 맞는다.**

| 단계 | 명령 | DB에 쓰나 | 사용자 데이터 위험 |
|---|---|---|---|
| B1 | `pull` (라이브 대상) | **읽기만** | 없음 |
| B2 | 생성된 스키마 ↔ 손으로 쓴 drizzle 스키마 **diff** | 안 씀 | 없음 |
| B3 | diff를 근거로 TS 스키마 수정 (현실이 맞으면 TS를, TS가 맞으면 B5 마이그레이션에) | 안 씀 | 없음 |
| B4 | 낡은 `20260827064745_*` 삭제 후 `generate` — **베이스라인 1개** | 안 씀 | 없음 |
| B5 | 베이스라인 SQL을 **손으로 멱등화**(`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`) | 안 씀 | 없음 |
| B6 | `migrate` 1회 — 라이브에선 **전부 no-op**, 원장 행만 기록된다 | **원장 행 1개만** | **없음** |
| B7 | 이후 마이그레이션은 정상 생성·적용 | 씀 | 9-3의 방어 적용 |

**B2가 이 도입의 진짜 산출물이다.** *"drizzle 스키마와 실제 DB가 어긋나 있어도 아무도 모르는 것"* —
리더가 막으라고 한 사고 ①이 **B2 한 번으로 즉시 드러난다.** 코드 수정 0줄, 위험 0.
**B1~B5는 DB에 한 글자도 안 쓴다.** 위험은 B6 한 줄뿐이고, 멱등화했으므로 실행 결과는 원장 행 하나다.

> **왜 원장 행을 손으로 넣지 않고 멱등 마이그레이션을 실행하는가**: 해시를 위조해 원장에 넣는 방법도 있지만,
> 그건 "적용했다고 주장하지만 실제로 대조된 적 없는 상태"를 만든다. 멱등 SQL을 진짜로 실행하면
> **DB가 스스로 대조한다** — 컬럼이 없으면 그때 생기고, 있으면 아무 일도 안 난다. 검증 가능한 쪽을 고른다.

### 9-3. `push` 금지와 파괴 방어 (DB 전량 삭제 사고 재발 대비)

**`push`를 금지하는 이유.** `push`는 스키마와 DB를 직접 diff해 적용한다. **스키마에 없는 테이블·컬럼을
DROP하자고 제안**하고, 비대화형에서 `--force`면 그냥 지운다. 리더 지적대로 **우리는 k3d가 곧 프로덕션이라
dev/prod 경계가 없다** — 같은 명령이 어느 DB를 보는지 `DATABASE_URL` 하나에 달렸다.
`db:push`가 `package.json`에 있는 한, 그건 **한 줄 오타로 782만 행을 지우는 버튼**이다. 삭제한다.

**`generate`도 안전하지 않다.** 누가 TS 스키마에서 컬럼을 지우면 `generate`는 군말 없이
`DROP COLUMN`을 뱉고 `migrate`가 적용한다. 그리고 §5-5가 "절대 지우지 말라"고 한 것들이 정확히
지우고 싶어지는 것들이다 — `by_floor`(호환용) · `school_roster`(혼합) · `user_mark`의 구 형식.

방어 셋, 전부 이미 도는 게이트 위에:

1. **파괴 구문 가드** — `ssot-guard.mjs`가 새 마이그레이션 SQL에서 `DROP TABLE|DROP COLUMN|TRUNCATE`를 찾으면
   빌드 실패. 통과하려면 그 파일에 `-- DESTRUCTIVE-OK: <이유>` 줄이 있어야 한다. **조용한 파괴를 의도적 행위로 바꾼다.**
2. **보호 목록** — `user`·`session`·`account`·`verification`·`user_biz`·`user_region`·`user_mark`·`events`와
   호환 컬럼(`by_floor`·`school_roster`)은 **`DESTRUCTIVE-OK`가 있어도 빌드 실패.** 사람이 스키마를 고쳐야 통과한다.
3. **`migrate` 전 사용자 테이블만 덤프** — `db:migrate` 스크립트가 먼저 `pg_dump`로 위 8개 테이블을 뜬다.
   **핵심은 우리가 잃을 수 없는 것이 아주 작다는 사실이다**: 회차 147,633·투찰 782만은 **로더가 다시 만든다.**
   되돌릴 수 없는 건 계정·마크·이벤트뿐이고 그건 수 MB다. 재적재 가능성과 아닌 것을 가르면 **방어 비용이 급감한다.**

### 9-4. `drizzle-zod` — 어디까지 파생하고 어디부터 손으로 쓰나

mw-auction이 답을 갖고 있다: `createSelectSchema(table)`로 **테이블 모양만** 파생하고,
응답 봉투·계산 필드는 손으로 조립한다(`domain/{equip,keyword,listing,price,settlement}.ts`).

**규칙: 테이블 모양은 파생, 응답 모양은 조립.**
```ts
const OpenAuctionRow = createSelectSchema(openAuctions);   // ← 컬럼 추가가 자동 반영. 손 동기화 0
export const OpenAuctionResponse = OpenAuctionRow.extend({ // ← 계산 필드만 손으로
  categories: z.array(Category), anchorAmount: z.number().nullable(),
  band: FloorStat.nullable(), recent3: z.array(z.number()), usualN: z.number().nullable(),
  nSameFloor: z.number(), unrestricted: z.boolean(), allowedLabel: z.string(),
  qualificationBasis: z.literal('region-only'), countBasis: z.literal('inclusive'),
});
```
이게 front가 찾은 *"zod가 응답의 절반만 기술한다"* 를 정확히 고친다 —
**절반(테이블)은 자동이라 어긋날 수 없고, 나머지 절반(계산)은 작아서 손으로 유지된다.**

**품목 SSOT와의 관계 (§1-2와 충돌하지 않는다).** `createSelectSchema`는 `category`를 `varchar` →
`z.string()`으로 준다. 그대로 두면 어휘가 풀린다. **refine으로 좁힌다**:
```ts
createSelectSchema(schoolAuctions, { category: () => Category })   // Category = z.enum(CATEGORIES)
```
**`vocab/category.ts`가 여전히 어휘의 SSOT이고, drizzle 파생은 그 어휘를 주입받는다.**
`Sourced<T>`(§1-0)는 계산 필드이므로 `.extend()` 쪽에 들어간다 — 파생 쪽을 오염시키지 않는다.

**과잉 파생 금지선**: `createInsertSchema`는 **쓰지 않는다.** 우리 쓰기 경로는 로더(파이썬)와
`/me/*` PUT 셋뿐이고, 후자는 이미 손으로 쓴 좁은 zod가 맞다(사업자번호 정규식 등 DB 제약보다 강하다).

### 9-5. 파이프라인 — 파이썬이 DDL을 만드는 경로를 닫는다

**규칙: DDL은 drizzle만. 로더는 스키마를 요구할 수 있을 뿐 만들 수 없다.**

data가 최근 `ALTER ADD COLUMN`을 직접 적용한 경로가 있다. 그걸 닫는다 —
컬럼이 필요하면 **TS 스키마를 고치고 `generate`+`migrate`**다. 파이썬은 §5-2-12의 preflight로
*"내가 쓸 컬럼이 다 있는가"* 를 묻고 없으면 **적재 전에 죽는다.** 만들지 않는다.
이게 언어 경계에서 유일하게 필요한 계약이고, §1-1의 표와 같은 원리다 — **파이썬은 어휘와 스키마를 받기만 한다.**

그리고 이건 **로더 두 벌 문제(§0-5)를 더 급하게 만든다**: 낡은 `data-plane/load_postgres.py`가
마이그레이션된 스키마에 대고 돌면 preflight에서 죽거나, 더 나쁘게는 낡은 컬럼 집합으로 덮어쓴다.
**§5-1-6(사본 삭제)이 이 도입의 선행 조건이다.**

### 9-6. 이 도입이 막는 사고 (리더가 요구한 셋 + 하나)

| # | 사고 | 막는 장치 |
|---|---|---|
| ① | drizzle 스키마와 실제 DB가 어긋나도 아무도 모름 | **B2 diff** — 한 번으로 즉시 드러남. 이후 `check`가 계속 봄 |
| ② | zod가 응답을 절반만 기술해 화면이 자기 타입을 만듦 | `createSelectSchema` 파생 + §5-2-9 |
| ③ | 컬럼 추가 시 두 곳을 손으로 맞춤 | `schema.sql` **폐기**. `migrate`가 유일 경로 |
| ④ | *(추가)* 컬럼·테이블이 조용히 사라짐 | 9-3 파괴 가드 + 보호 목록. **`push` 삭제** |

   강조까지 붙여 실었다. §10-27에서 *"제안을 받을 때는 검증한다"* 고 썼는데 **그 바로 다음 라운드에 안 했다.**
   자료구조 모양만 봐도 알 수 있었다 — 남의 근거든 내 근거든 **안 보이는 건 마찬가지다**

   그리고 더 아픈 건 이거다 — **이 서비스의 판정 기준은 원래 "아버지 화면에 뜨나"인데,
   내가 세운 폐기선 둘 다 그 기준을 안 썼다.** 헌법을 설계에는 적용하고 내 판정선에는 안 적용했다
27. ~~제안은 검증하고 내 설계는 스스로 검증 안 한다 — 비대칭이 있다~~
   **정정(critic).** 이번 건이 그 진단의 반례다 — **내가 critic 제안의 함정을 찾았고,
   critic이 자기 근거의 오류를 그걸 검증하다 찾았다.** 비대칭이 있는 게 아니라 **자기 것은 원래 안 보인다.**
   §10-24b에서 내가 만난 벽과 같다. **체크리스트로는 안 뚫리고 서로 밟는 걸로만 뚫린다** —
   §4-b를 "서로에게 묻는 용도"로 쓰는 게 맞는 결론이다

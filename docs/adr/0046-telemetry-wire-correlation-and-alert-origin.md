# 0046 — 계측 규격, 상관 식별자, 진실·파생 경계와 알림 출처

- Status: Accepted
- Date: 2026-09-11
- Supersedes: [ADR 0012](0012-security-observability-and-recovery-baseline.md) Consequences의 "규모가 생기면 OTel/Prometheus/Grafana/Loki를 측정 근거로 추가한다" 조항. 0012의 나머지(구조화 로그 필드, 백업·복구 목표, 노출 금지)는 유지한다.
- 관련 작업: 2026-09-10 운영 사고 여섯, EAT-169

## Context

2026-09-10 하루에 운영 사고 여섯이 있었다. 그 분포가 설계를 정한다.

| 사고 | 지속 | 발견 경로 | 분류 |
|---|---|---|---|
| source semaphore 교착으로 수집 정지 | 2시간 | 사람이 조회하다 | 멈춤 |
| DB 백업 권한 실패 | 매시 반복 | 사람이 지켜보다 | 실패 |
| main `pnpm build` red | 14시간, 병합 13회 | 릴리스 준비 중 | 멈춤 |
| 백업 파드 로그 소실 | 즉시 | 읽으려다 없음 | 증거 소실 |
| 옛 VM 노드 사망 | 28시간 | 사용자가 물어서 | 멈춤 |
| 미발행 release 누적 | 5일, 14건 | 조회하다 | 멈춤 |

여섯 중 다섯이 예외가 아니라 **조용한 멈춤**이다. 프론트 오류는 0건이다. 멈춤은 로그에도 오류 추적기에도
남지 않는다. 자물쇠 교착은 아무것도 실패하지 않았고, release 누적은 세어보기 전에는 존재하지 않는 사실이다.

동시에 이 저장소는 앞으로 기능을 계속 얹는다. 계측 규격과 상관 식별자는 모든 모듈에 퍼지므로 나중에 바꾸면
전부 다시 만져야 한다. 반면 어떤 저장소에 담고 어떤 화면으로 보는지는 나중에 바꿔도 싸다. 이 ADR은 앞의
것만 고정하고 뒤의 것은 교체 가능한 자리로 남긴다.

## Decision

1. **계측 규격은 OpenTelemetry(OTLP)다.** web·server·dataplane과 브라우저는 OTel SDK로 계측하고 OTLP로
   내보낸다. 저장소 업체의 SDK를 애플리케이션 코드에 직접 심지 않는다. 예외는 결정 8이 정한 프론트 오류
   분류 도구 하나이며, 그것도 진단 보조일 뿐 업무 사실의 경로가 아니다. 규격을 고정하는 이유는 저장소를
   갈아끼울 때 코드를 고치지 않기 위해서다.

2. **환경별 차이는 내보낼 주소뿐이다.** 같은 코드가 local·dev·prod에서 같은 계측을 하고 collector endpoint만
   런타임 설정으로 다르다. dev에 별도 관측 스택을 세우지 않는다.

3. **상관 식별자는 W3C trace context다.** 프로세스 경계는 `traceparent`로 잇는다. 기존 `x-request-id`는
   사람이 읽고 옮겨 적는 용도로 유지하며 없애지 않는다. 모든 로그 줄은 `trace_id`와 `build_sha`를 단다.
   dataplane은 여기에 `run_id`와 `source_release_id`를 더 단다. 새 식별자 체계를 만들지 않는다.

4. **파이프라인의 진실은 PostgreSQL이고 관측 데이터는 파생물이다.** `ingest`·`core`가 권위이며 지표·로그는
   유실될 수 있는 사본이다(ADR 0004, AGENTS.md 1항·7항). 따라서 **업무 사실이 걸린 알림과 대시보드는 DB를
   읽는다.** 지표에서 내면 지표 수집이 멈췄을 때 조용히 정상으로 보인다. 지표를 업무 사실의 원천으로 쓰는
   것을 금지한다.

5. **멈춤은 기대 문장으로 잡는다.** 로그 수집이 아니라 명시된 기대를 주기적으로 평가한다. 각 기대는
   대상·판정 질의·임계·대응 문서를 갖는다. 최소 집합은 이렇다.

   | 기대 | 원천 |
   |---|---|
   | 실행 중 backfill이 임계 시간 안에 진행했다 | PostgreSQL |
   | 마지막 성공 백업이 임계 시간 안에 있다 | PostgreSQL·Workflow |
   | 임계 나이를 넘은 `planned` release가 없다 | PostgreSQL |
   | 수집 CronWorkflow가 예정 회차를 건너뛰지 않았다 | Workflow |
   | 노드와 Argo Application이 정상이다 | Kubernetes API |
   | 원격 `main`의 최신 CI가 초록이다 | GitHub |
   | 최신 release 발행이 끝까지 갔다 | GitHub |

   GitHub을 원천으로 쓰는 두 기대는 클러스터 **안에서** 공개 API에 묻는다. GitHub Actions 단계에서
   알림을 보내면 Actions가 도는 동안에만 말할 수 있고, 2026-09-13처럼 결제 한도로 회차가 시작조차 못
   하면 그 방식은 하루 종일 조용하다. 밖에서 물으면 "실패했다"와 "시작조차 못 했다"가 같은 자리에서
   보이고, 알림 봇 토큰을 GitHub 비밀값으로 한 벌 더 복제하지 않아도 된다. 대가는 최대 한 회차(15분)의
   지연이다.

   기대는 흩어진 코드가 아니라 하나의 목록으로 관리하고, 걸린 횟수를 남겨 분포를 다시 볼 수 있게 한다.

6. **알림의 출처는 둘, 도착지는 하나다.** 업무·파이프라인 기대는 클러스터 **안**에서 DB를 읽어 낸다. 생존
   확인은 클러스터 **밖**에 둔다. 안에 있는 감시는 기계가 죽을 때 함께 죽기 때문이다.

   생존 확인의 방향은 **미는 쪽**이다. 클러스터가 주기적으로 밖으로 신호를 보내고 그 신호가 끊기면 밖에서
   알린다. 밖에서 안으로 당겨 보는 방식은 쓰지 않는다. 그러려면 Kubernetes API나 내부 지표를 외부에 열어야
   하고 ADR 0012 Consequences의 "Argo UI, DB, metrics는 외부에 직접 공개하지 않는다"에 걸린다. 예외는 이미
   공개된 사이트의 응답 확인 하나이며, 그것만 밖에서 당긴다.

   두 출처 모두 하나의 텔레그램 대상으로 보내고, 문구에 대응 문서 위치를 포함한다. 한 원인이 여러 기대를
   동시에 위반시키므로(2026-09-10 자물쇠 교착 하나가 셋을 깨뜨렸다) 같은 창에서 발생한 위반은 묶어서 한 번
   보내고, 해소될 때까지 같은 위반을 반복해 보내지 않는다.

7. **증거는 파드보다 오래 산다.** `podGC`와 `ttlStrategy`가 파드를 지우므로 실행 로그는 지워지기 전에
   보관소로 나간다. Argo가 이미 가진 artifact repository와 workflow archive를 쓰고 새 구성요소를 만들지
   않는다. 보관소는 R2다.

8. **도구는 교체 가능한 자리로 적는다.** 아래는 이 시점의 선택이며 ADR을 바꾸지 않고 교체할 수 있다.
   교체 비용이 낮다는 사실 자체가 결정 1의 목적이다.

   | 자리 | 이 시점의 선택 | 켜는 조건 |
   |---|---|---|
   | 로그·지표·추적 저장 | OpenObserve(단일 바이너리, R2 backend, OTLP 수신, SQL API) | 결정 7로 안 되는 조회가 두 번 필요할 때 |
   | 대시보드 | Grafana(PostgreSQL을 직접 datasource로) | 결정 5·6이 동작한 뒤 |
   | 프론트 오류 분류 | Sentry SaaS | 운영자 아닌 사용자가 생길 때 |

   프론트 오류 도구는 유입 제어(세션당 상한, 동일 오류 병합, 알려진 잡음 제외)와 같은 변경에서 켠다.
   제어 없이 켜지 않는다.

## Consequences

- 계측을 한 번 심으면 저장소 교체가 설정 변경이 된다. 대신 OTel SDK 학습과 초기 배선 비용을 먼저 낸다.
- 대시보드는 감시가 아니다. 사람이 볼 때만 값을 하므로 결정 5·6이 없는 상태에서 대시보드부터 만들지 않는다.
- 결정 4 때문에 "지표로 빠르게 알림"이 막힌다. DB 질의는 지표 조회보다 느리고 무겁지만, 사고 여섯 중
  다섯이 조용한 멈춤이었으므로 정확성을 택한다.
- 결정 6의 밖 감시는 외부 의존을 하나 만든다. 그 의존이 죽으면 생존 확인이 멈추므로, 기능이 최소인 것을
  고르고 그 자체의 실패도 알림 대상에 넣는다.
- 결정 1과 결정 8을 함께 켜면 브라우저에 SDK가 둘 붙는다. 번들이 무거워지고 같은 오류가 두 곳에 남는다.
  프론트 오류 도구를 켜는 시점에 브라우저 OTel의 범위를 성능·사용자 흐름으로 좁혀 중복을 없앤다.
- `build_sha`는 dataplane에만 이미 있다. web·server는 이미지 빌드 시점에 주입해야 하므로 결정 3의 실행에
  빌드 파이프라인 변경이 따라온다.
- 근거는 하루치 분포이며 ADR 0012가 요구한 "측정 근거"의 기준을 아직 충분히 넘지 않는다. 그래서 이 ADR은
  스택 전개가 아니라 규격·경계·출처만 고정한다. 결정 5의 기대 목록에 적중 횟수를 남겨 한두 주 뒤 결정 8의
  선택과 순서를 다시 판단한다.

## 대안과 기각 이유

- **Prometheus + Loki + Tempo + Grafana 전개.** 표준이지만 구성요소가 넷이고 12GB 단일 노드에서 DB와 메모리를
  다툰다. 규모가 커져 각 신호를 따로 키워야 할 때 다시 본다.
- **관측 스택부터 세우고 알림은 그 위에서.** 사고 여섯 중 여섯이 스택 없이도 잡히는 종류였다. 순서를
  뒤집으면 잡을 수 있었던 멈춤을 스택 구축 기간 내내 놓친다.
- **지표를 파이프라인 사실의 원천으로.** 조회가 빠르지만 사본이 둘이 되고 어긋날 때 판정 근거가 사라진다.
  AGENTS.md 1항이 금지한다.
- **프론트 오류 수집기 자체 호스팅.** 한도 소진이 디스크 압박으로 바뀌고, 폭주 시 같은 노드의 운영 트래픽을
  죽인다. 눈이 머는 것보다 서비스가 멎는 쪽이 나쁘다.

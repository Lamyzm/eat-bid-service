# 0064 — 개찰 결과는 평일 오전 전용 수집 줄이 받는다

- Status: Accepted
- Date: 2026-10-11
- Supersedes: 없음.
- 보충: [ADR 0037](0037-poll-open-detail-refetch-policy.md)의 기준 release 선택을 모드별로 나눈다. 정시 수집(`poll-open`)과
  재대조(`daily-reconcile`)의 기준은 그대로이고, 새 모드 `poll-results`만 자기 release를 기준에 더한다.
- 관련 작업: EAT-335(EAT-329 후속), [PDR-0008](../product/decisions/0008-my-bids-market-pick-and-work-screen.md) 결정 6
- 승인: 총괄 Tech Lead 결정(사용자 위임, 2026-10-11)

## Context

아침 갱신(EAT-330)은 그날 앞서 끝난 공고의 명단을 보고 경쟁 업체들의 오늘 금액을 다시 맞춘다. 명단이 늦으면 할 수 있는
일이 없다. PDR-0008 결정 6은 "결과 전용 수집 줄이 붙기 전에는 아침 갱신을 켜지 않는다"고 정했다.

| 관측 (운영 DB 읽기) | 값 |
|---|---|
| 명단이 처음 보인 상태 | 2026-09 오전 개찰 3,086건 전부 `낙찰` 전이와 함께, `개찰` 상태의 명단 0건(runtime §2.6) |
| eaT 명단 공개 | 개찰 뒤 21~24분(가운데값) |
| 예정 개찰 → 명단이 우리 DB에 | 가운데값 159분, 40분 안 5.8%(2026-09) |
| 성수기 poll-open 회차 | 141~193분, 회차당 상세 5,774~7,139건(2026-09-21) |

명단은 소스가 낙찰 전이 때 처음 준다. 그 전이는 목록 상태 라벨 변화라 poll-open의 `signal-changed`가 곧바로 잡지만,
상세를 실제로 부르는 시점은 그 회차의 차례다. 성수기에 회차 하나가 몇 시간이면 명단도 몇 시간 뒤에 온다. EAT-329(v0.1.69)는
마감 뒤 창의 재호출을 줄이고 평일 08~11시에 백필이 소스를 비켜 주게 해 회차를 가볍게 했지만, 명단 도착은 여전히 "10분 주기 +
회차 크기"에 묶여 있다.

## Decision

1. **새 모드 `poll-results`를 같은 WorkflowTemplate의 새 DAG `results-pipeline`으로 돌린다(AGENTS 9).** CronWorkflow
   `eatbid-poll-results`는 평일 `*/5 9-11 * * 1-5`와 `0-25/5 12 * * 1-5` KST(09:00~12:25)이고 `concurrencyPolicy: Forbid`,
   `startingDeadlineSeconds: 300`이다. 오전 마감이 9~11시에 몰리고(runtime §2.6) 명단은 개찰 뒤 21~24분에 공개되므로 11시대
   마감분은 12시 25분까지 공개된다. 오후 개찰은 poll-open이 맡는다.
2. **목록은 다 읽고 상세는 상태 라벨이 바뀐 공고만 부른다(`status-changed`).** 목록 창은 poll-open과 같은 오늘 하루다. 새
   공고·투찰 수·마감 연장·정정·마감 뒤 창은 poll-open 몫으로 남긴다. 기준이 없으면 아무것도 부르지 않는다 — 전부 부르는
   것은 정시 수집의 일이고, 이 줄이 하면 5분마다 상세 수천 건을 부르게 된다.

   PDR-0008은 "낙찰 상태가 된 공고만"이라고 적었지만 여기서는 라벨의 **모든 변화**에 반응한다. 목록 행에는 상태 코드가 없고
   한글 라벨뿐이라, `낙찰` 문자열로 거르면 화면 라벨을 정체성으로 쓰게 된다(AGENTS 2). 변화 여부만 보는 비교는 라벨을
   해석하지 않는다. 마감·개찰 같은 중간 상태로 생기는 추가 호출은 공고당 몇 번이다. 상태 코드(`ETN_BID_STT`)를 목록 계약에
   들이면 그때 좁힌다.
3. **기준 release를 모드별로 고른다.** poll-open·daily-reconcile의 기준은 지금처럼 그 둘의 봉인 release다. 결과 줄 release는
   목록을 다 담지만 상세는 일부만 불렀으므로, 그 신호가 정시 수집 기준이 되면 투찰 수만 바뀐 공고를 정시 수집이
   unchanged로 보고 놓친다. 결과 줄의 기준은 그 둘에 자기 release를 더한다. 빼면 정시 수집이 새 기준을 봉인하기 전까지(성수기
   몇 시간) 이미 받은 낙찰 공고를 5분마다 다시 부른다.
4. **소스 semaphore key `eatbid-source-results`(1)를 따로 둔다.** live를 함께 쓰면 몇 시간짜리 poll-open 회차 뒤에 줄 선다.
   재대조(EAT-275)를 나눈 것과 같은 이유이며 같은 방법이다.
5. **marts를 잇지 않는다.** open_auction_snapshot 활성화는 마지막에 올린 build가 이긴다(ADR 0034). 결과 줄이 5분마다 새 목록으로
   build를 올리면, 그보다 오래된 목록으로 몇 시간 뒤 끝난 poll-open build가 나중에 올라와 화면이 뒤로 간다. 명단은 core에
   앉으면 맞춤 금액·공고 상세가 읽는다. core 투영 뒤 캐시 무효화는 project 단계가 한다.
6. **소스 보류를 존중한다.** 결과 줄도 예약 실행이라 `SCHEDULED_SOURCE_MODES`에 든다([ADR 0055](0055-source-hold-across-scheduled-runs.md)).

DB 마이그레이션은 없다. `ingest.run.mode`는 check 제약이 없는 `varchar(32)`다.

## 기각한 대안

- **poll-open 주기를 5분으로.** 늦음의 원인은 주기가 아니라 회차 크기다. runtime §2.5의 5분 조건(회차가 주기 절반 안에
  끝남)도 성수기에 성립하지 않는다.
- **"예정 개찰이 지났는데 결과가 없는 공고"를 core에서 골라 매 회차 다시 부르기(EAT-329 원안).** 후보가 결과를 받을 때까지
  매 회차 상세를 다시 불러 호출 수가 상태 신호 방식의 몇 배가 되고, 해석된 core 상태를 수집 판단의 입력으로 삼는다. 목록 상태
  신호는 이미 ADR 0037의 판단 근거이고 명단이 처음 보이는 관측과 함께 바뀐다(아래 실측).
- **기준을 공유하거나 결과 줄을 기준에서 아예 빼기.** 각각 정시 수집이 신호를 놓치거나, 결과 줄이 같은 낙찰 공고를 반복해
  부른다(결정 3).
- **결과 줄에도 marts를 잇기.** 활성화 순서가 뒤집힌다(결정 5).

## 결과와 측정

- **한 번만 부른다.** 라벨이 낙찰로 바뀐 관측에 명단이 아직 비어 있는 경우가 있다. 2026-08~10-10 운영 DB에서 `낙찰` 개정본
  131,363건 중 103건(9월 0.04%, 8월 0.33%)이 명단 0행이었고, 103건 모두 같은 공고의 더 늦은 관측에서 명단이 생겼다. 그 간격은
  가장 짧아도 8시간(가운데값 약 8일)으로, 다음 재대조·백필이 다시 부를 때였다. 결과 줄은 이런 공고를 다시 부르지 않지만 명단은
  지금과 같은 경로(poll-open의 마감 뒤 창, 다음 날 재대조)로 들어온다. 지금보다 나빠지지 않으므로 재시도를 두지 않는다.
- 비용: 하루 42회차. 목록은 평시 회차당 page 1~2장이지만 성수기에는 오늘 창 목록이 7천 행을 넘어 page_size 1000으로 8장
  안팎이다 — 성수기 오전 목록 약 300장과 그만큼의 기준 재읽기(R2)가 더해진다. 상세는 상태가 바뀐 공고뿐이다. 소스 동시
  호출은 live 1 + reconcile 2 + backfill 8에 1이 더해지지만, 평일 08~11시는 backfill이 비킨다(EAT-329).
- **중단 조건:** 결과 줄의 호출이 `SOURCE_THROTTLED`를 일으키면 소스 보류(ADR 0055)가 정시 수집까지 멈춘다. 결과 줄이 돈 시간대에
  보류가 한 번이라도 걸리면 `poll-results.yaml`을 `suspend: true`로 되돌린다(`infra/tests`의 `expected_suspend`를 함께 바꾼다).
  runtime §2.5가 목록 호출을 늘리는 전제로 둔 "소스가 늘어난 목록 호출을 제한 없이 받는다"를 이 줄이 처음 시험한다.
- 측정: 예정 개찰 → 명단의 첫 관측까지 시간대별 가운데값과 30·45·60분 안 비율. 2026-10-12(월) 오전에 v0.1.69 기준선을 재고,
  배포 뒤 다음 평일 오전에 같은 잣대로 잰다. PDR-0008의 "공개 뒤 5분 안이 평일 오전 절반 이상"을 못 지키면 아침 갱신을 켜지
  않는다.
- 남은 위험
  - 결과 줄의 project 단계는 `eatbid-core-publication` mutex를 poll-open·재대조(07시)·재처리 전진(08:25 등, release 전체를
    다시 앉히는 동안 쥔다)과 다툰다. 성수기에 그 project가 길면 결과 줄이 그만큼 기다린다. 측정에 project 대기 시간을 남긴다.
  - **공고 상세·명단 화면의 최신 개정본.** 서버의 공고·명단 조회가 최신 개정본을 개정본 번호(투영 순)로 고른다. 결과 줄이
    10시에 앉힌 낙찰 명단 뒤에, 그보다 먼저 관측했지만 늦게 끝난 poll-open 회차가 낙찰 전 관측을 더 큰 번호로 투영하면 화면이
    다음 투영까지 낙찰 전으로 돌아간다. 최신을 관측 순서로 고르는 EAT-333이 같은 릴리스에 들어가기 전에는 이 줄을 배포하지
    않는다. 맞춤 금액의 시장 조회는 이미 관측 순이다(EAT-324).
  - 결과 줄이 조용히 멈춰도 지금 감시는 poll-open만 센다. 아침 갱신(EAT-330)을 켜기 전에 결과 줄의 공백 기대(평일 오전 회차 부재)를
    감시에 더한다.
  - capture가 실패한 회차는 release를 `planned`로 남긴다. 5분 주기라 정시 수집보다 자주 쌓일 수 있으므로 `planned-release-age` 경보가
    울리면 runbook대로 `fail-release`한다.
- 되돌리기: `poll-results.yaml`의 `suspend: true`와 `infra/tests`의 `expected_suspend`를 함께 바꾸는 커밋 하나다. 결과 줄을 멈춰도
  poll-open이 같은 명단을 늦게라도 받는다.

# 선언과 사실이 갈리지 않게 한다 — 2026-09-17 사고 셋의 구조 설계

## 1. 무엇이 있었나

하루에 사고가 셋이었고 표면은 달랐지만 모양이 같았다. **기록된 상태가 실제 상태와 달랐고 우리가
그 기록을 믿고 움직였다.**

| 기록이 말한 것 | 실제 | 대가 |
|---|---|---|
| 수집 단계가 `Succeeded`, exit 0 | `ingest.run`에 행 0개 | 정시 수집 22시간 중단 |
| 격리 사유 "nonnegative KRW amount at scale 2" | 값은 양수, 소수 셋째 자리가 원인 | 잘못된 처방을 두 번 권함 |
| `drizzle` 기록 "29개 적용" | `ingest` 스키마에 표 0개 | 개발 작업 하루 정지 |

셋째는 2026-09-17에 EAT-271로 닫혔다(저장소와 다르면 고치지 않고 거부). 앞의 둘이 이 설계의 대상이다.

## 2. 이미 증명된 답이 저장소 안에 있다

`ingest.backfill_coverage`는 **오늘 한 번도 갈리지 않았다.** 창이 어디까지 됐는지, 몇 건이 발행됐는지가
늘 정확했고 그 값으로 전진 판단과 알림과 사람의 조회가 같은 답을 봤다.

이유는 하나다. 그것은 저장된 상태가 아니라 **사실에서 계산되는 뷰**다. ADR 0052 결정 2가 "진도는
저장하지 않고 파생한다"고 정했고, 그 결정이 지켜지는 자리에서는 사고가 없었다.

반대로 오늘 터진 둘은 전부 따로 적어 둔 상태에서 났다. 지금 `status` 열은 일곱이고 뷰는 하나다.

```
ingest.run.status              ingest.source_release.status
ingest.publication.status      ingest.request_unit.status
ingest.normalization_attempt.status   mart.build.status
core.code_mapping.status
```

## 3. 설계 원칙

**단계는 자기 상태를 선언하지 않는다. 사실만 남기고 상태는 사실에서 읽는다.**

선언을 없애면 갈릴 대상이 사라진다. 전부를 없앨 수는 없으므로 두 갈래로 나눈다.

1. **계산할 수 있는 상태는 뷰로 옮긴다.** 구성원 기록이 이미 있는데 요약을 따로 적어 두면 둘이
   갈린다.
2. **계산할 수 없는 것(우리가 내린 결정)은 저장하되 사실과 같은 저장 단위에 묶는다.** 소스 차단
   보류가 그 예다. 결정은 파생되지 않지만, 그 결정과 그것을 낳은 사실이 따로 살아남으면 안 된다.

## 4. 1단계 — 갈림을 즉시 시끄럽게 만든다 (작음, 먼저)

뷰로 옮기는 일은 크고 그 사이에도 사고는 난다. 그래서 **갈림이 조용히 지나가지 못하게 하는 것**을
먼저 넣는다. 둘 다 한 곳만 고치면 모든 명령에 적용된다.

### 4.1 저장되지 않은 채 끝나는 것을 금지한다

`Application.close()`가 연결을 닫기 전에 트랜잭션 상태를 본다. `IDLE`이 아니면 실패로 끝낸다.

```python
# composition.py Application.close()
status = self._connection.info.transaction_status
if status is not psycopg.pq.TransactionStatus.IDLE:
    failure = True  # 조용한 롤백을 성공으로 보고하지 않는다
```

**왜 이것이 근본에 가까운가.** 어제 저지른 실수가 무엇이었는지와 무관하게, 저장되지 않은 채 끝나는
모든 경로가 한 자리에서 막힌다. 새로운 종류의 실수도 같은 자리에서 걸린다. 실패를 잡는 감시가 아니라
**조용한 실패라는 범주를 없애는 것**이다.

`root-cause-discipline`의 요구대로 재현 시험을 먼저 쓴다. 읽기 메서드가 트랜잭션을 남긴 뒤 종료하면
exit code가 0이 아니어야 한다.

### 4.2 거부할 때 값과 조건을 함께 남긴다

`wire_text._canonical_decimal_text`와 `canonical_money_amount`가 계약 전문을 내보낸다. 무엇이 왜 걸렸는지,
실제 값이 무엇이었는지가 없다. 2026-09-17에 이것 때문에 두 번 틀린 처방을 권했다.

| 지금 | 바꾼 뒤 |
|---|---|
| `EFT_ALL_AMT must be a nonnegative KRW amount at scale 2` | `EFT_ALL_AMT: scale 3 (허용 2), 값 3978476.348` |

검증 함수가 한 곳이라 거기서 실패 조건과 값을 담으면 모든 필드에 적용된다. 값이 개인정보나 비밀이
아닌 것은 이 계층이 소스 수치만 다루기 때문이다.

## 5. 2단계 — 저장된 상태를 하나씩 뷰로 (큼, ADR 필요)

각 `status`를 다음 질문으로 판정한다. **"이 값을 지우고 구성원 기록에서 계산할 수 있는가."**

| 상태 | 판정 후보 | 근거 |
|---|---|---|
| `publication.status` | 뷰 후보 | `publication_record`와 `normalized_record`의 관계에서 계산 가능해 보인다. 확인 필요 |
| `source_release.status` | 저장 유지 | 봉인은 우리가 내린 결정이고 시점이 사실이다 |
| `run.status` | 저장 유지 | 실행의 시작·끝은 관측이 아니라 기록이다 |
| `request_unit.status` | 뷰 후보 | 예약·관측 여부에서 계산 가능해 보인다 |
| `normalization_attempt.status` | 저장 유지 | 시도의 결과 자체가 사실이다 |
| `mart.build.status` | 저장 유지 | 활성 포인터 교체가 원자여야 한다(ADR 0034) |

**이 표는 가설이다.** 각 항목은 실제 질의로 "뷰로 만들어도 같은 답이 나오는가"를 확인한 뒤에만
옮긴다. 옮기지 못하는 것은 4절의 장치로 보호한다.

옮기는 순서는 사고 빈도순이다. 오늘 문제가 된 것은 발행 상태였다.

## 6. 하지 않는 것

- **단계를 합쳐 장부 수를 줄이지 않는다.** 1만 6천 건을 한 트랜잭션에 넣을 수 없고, 나누는 이유가
  성능이 아니라 "부분 결과를 화면에 내보내지 않기"(AGENTS 변경 절차)라서 합치면 그 보호가 사라진다.
- **장부마다 대조 검사를 하나씩 붙이지 않는다.** 그것이 지금까지의 방식이고 구멍마다 패치가 쌓인다.
- **워크플로 엔진을 바꾸지 않는다.** 상태를 엔진에 맡기는 선택지가 있으나 단일 노드 12GB에서 Argo를
  대체할 근거가 없다(운영 신호 설계 §4에서 이미 기각).

## 7. 인수 기준

- [ ] 저장되지 않은 채 끝나는 명령이 exit 0으로 끝나지 않는다. 재현 시험이 그것을 고정한다.
- [ ] 계약 거부 메시지에 실패한 조건과 실제 값이 들어 있다. 원본을 열지 않고 판단할 수 있다.
- [ ] 2단계의 판정 표가 가설이 아니라 실측으로 채워진다.
- [ ] 뷰로 옮긴 상태는 옮기기 전후로 같은 답을 낸다.

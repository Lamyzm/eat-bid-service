# eaT 코드 어휘 층 설계 — 지역 이름과 품목 코드

## 1. 결정 요약

오늘 화면의 필터는 **어휘가 없어서** 막혀 있다. 지역은 코드가 있는데 이름이 없고, 품목은
이름이 있는데 코드가 없다. 정반대 결손이라 한 가지 처방으로는 안 되고, 축마다 다른 길로 간다.

```text
지역   코드 있음 · 이름 없음   → eaT 공통코드에서 이름을 관측한다
품목   이름 있음 · 코드 없음   → 닫힌 원자 어휘에 우리가 code_value를 발급한다
       그나마 67%만 채워짐     → 안 읽던 ds_itemList로 88%까지 관측으로 올리고(§4.7)
                               남는 12%만 제목에서 추정하되 관측과 갈라 둔다(§4.6)
```

두 축 모두 끝나면 조회가 **문자열이 아니라 `code_value_id`로** 걸린다(AGENTS 2). 그 전까지
화면 설계를 시작하지 않는다 — 계약이 바뀌면 화면을 두 번 만들기 때문이다.

## 2. 지금 무엇이 막혀 있나

`build 212`, 열린 공고 404건 기준 실측이다.

| 축 | 코드 | 이름 | 화면에서 |
| --- | --- | --- | --- |
| 공고지역 시도 | 404/404 있음 | **0개** | `코드 15`로밖에 못 부른다 |
| 공고지역 시군구 | 404/404 있음 | **0개** | 같다 |
| 품목 | **0/404** 없음 | 290/404 (72%) | `strpos(item_label, ...)` 문자열 부분일치 |

품목 조회는 EAT-206에서 조각 배열 부분일치로 만들어 동작은 하지만 **문자열을 정체성으로 쓰고
있다.** 합성 라벨(`육류 , 가금류`)을 쉼표로 쪼개 부분일치를 거는 구조이며, 원자에 id가 없다.

## 3. 지역 — eaT가 자기 코드의 이름을 준다

### 3.1 발견

원천 필드 사전(`docs/audit-source/SOURCE-FIELDS.md` T1)은 "학교 위치축에는 이름 필드가 없다.
`SIDO_NM`·`SIGUNGU_NM`은 상세 응답에 아예 오지 않는다"고 적고 있고 그것은 **상세 응답에 한해
맞다.** 이름은 다른 호출에 온다.

```text
POST https://ns.eat.co.kr/cmmn/code/selectCodeListEhcache.do
  ds_Param.CMNS_GRP_CD = "SC066,SC067"
  ds_Param.RETV_DIV    = "N"
→ CMNS_GRP_CD · CMNS_CD · CMNS_CD_NM · ITM_VL2
  · SRTNG_SEQN · VLD_BGNG_YMD · VLD_END_YMD · USE_YN
```

- `SC066` = 공고지역 시도 19개. `15=경남`, `8=경기`, `1=서울`, `0=기타`
- `SC067` = 공고지역 시군구 235개. 코드가 **전역 유일**이고 `ITM_VL2`가 부모 시도 코드다
  (`653=김해시`, `ITM_VL2=15`)
- 로그인 불필요. 유효기간·사용여부가 함께 온다

### 3.2 커버리지 검증

우리가 관측한 코드가 이 목록에 전부 있는지 대조했다.

| 축 | 우리 DB | eaT 목록 | 이름이 붙는 수 |
| --- | --- | --- | --- |
| `eat:auction-location-sido` | 15 | 19 | **15 (전부)** |
| `eat:auction-location-sigungu` | 201 | 235 | **201 (전부)** |

미매칭 0이다.

### 3.3 행안부 매핑은 하지 않는다

eaT 지역 코드는 1~3자리 내부 일련번호이고 행안부 행정구역은 10자리 법정동 코드다. 코드로 조인하면
0건이며 `core.code_mapping`은 지금 0행이다. **eaT가 자기 이름을 주므로 매핑이 필요 없다.**
ADR 0035의 행안부 canonical 전환은 별개 가치로 남지만 지역 필터의 선행 조건이 아니다.

`mart/region_axis.py`의 번역 CTE도 건드리지 않는다. 선언 체계에 code release가 없으면 관측 코드를
그대로 싣는 경로가 이미 있다.

### 3.4 무엇을 만드나

1. **코드목록 endpoint를 검토된 전송 경계에 추가한다.** `apps/dataplane/src/eatbid/source/eat/`의
   `registry.py`에 세 번째 endpoint로 등록하고, 요청 payload와 응답 dataset을
   `schema_contract`로 고정한다. 기존 둘(`bid-list`·`bid-detail`)과 같은 규율을 따른다.
2. **raw를 먼저 저장한다.** 코드목록도 관측이므로 R2 raw 객체 → `raw_observation` →
   `normalized_record` 순서를 지킨다(AGENTS 3, "raw 저장 성공 전에 canonical 행을 공개하지 마라").
3. **`core.code_label_observation`에 라벨을 싣는다.** `observation_id`는 그 코드목록 관측을
   가리킨다 — 공고 관측을 빌려 쓰지 않는다.
4. **유효기간을 `core.code_value`의 `valid_from`·`valid_to`에 반영한다.** eaT가 준 값을 쓰고
   우리가 정하지 않는다.
5. **`USE_YN='N'`인 코드는 라벨을 싣되 `active`를 내린다.** 과거 공고가 그 코드를 참조할 수 있으므로
   지우지 않는다.

### 3.4.1 구현에서 갈라진 자리 (EAT-187, 2026-09-16 적재까지 완료)

설계가 `normalized_record`를 적었지만 구현은 **release 봉인까지만** 간다. `ingest.normalized_record`는
공고 발행 corpus의 단위이고(record type별 발행·검증·replay가 그 표에 매여 있다), 코드목록에는 발행
corpus도 건별 격리 단위도 없다. 정부 코드 파일 실행(`pipeline/reference.py`)이 같은 이유로 이미
raw → release 봉인 → core 투영 셋으로 돌고 있어 그 선례를 따랐다. 순서 규칙(raw가 먼저, 봉인되지 않은
입력으로 canonical 행을 공개하지 않음)은 그대로다.

**`code_release`를 만들지 않는다.** 만들 수 있었지만 만들면 안 된다. `mart/region_axis.py`는 선언한
지역 체계에 `core.code_release`가 **있는지 없는지**를 축 전환 신호로 읽고, 기본 지역 체계가
`eat:auction-location-sigungu`다. 시도와 시군구는 서로 다른 체계라 어느 한쪽에 release가 생기는 순간
`open_auction_snapshot`의 다른 쪽 열이 전부 "체계 밖 코드"가 되어 mart 빌드가 멈춘다. 이름을 채우는
일이 지역 축 전환을 촉발하면 안 되므로 어휘는 `code_value`와 `code_label_observation`에만 앉힌다.
`tests/integration/test_code_vocabulary_pipeline.py`가 이 사실을 시험으로 고정한다.

**`SC067`의 `ITM_VL2`(부모 시도 코드)는 싣지 않는다.** 관측된 사실이지만 담을 자리가 없다.
`core.code_release_member.parent_code_value_id`의 복합 FK는 상위가 **같은 release 안의 member**일 것을
요구하는데 시도와 시군구는 서로 다른 체계라 같은 release에 들어갈 수 없고, `core.code_mapping`은
포함 관계가 아니라 등가 주장을 담는 표다. 담을 자리를 만드는 것은 스키마 결정이므로 별도 작업으로
남긴다. 화면의 시도↔시군구 묶음은 `mart.open_auction_snapshot`이 두 열을 함께 갖고 있어 막히지 않는다.

**유효기간 sentinel을 번역하지 않는다.** `VLD_END_YMD`가 `99991231`·`29991231`로 오지만 null로 바꾸지
않는다. 바꾸는 순간 "소스가 끝을 말하지 않았다"와 "소스가 먼 끝을 말했다"가 한 값이 되고 그 차이를
우리가 지운 사실이 어디에도 남지 않는다. 날짜는 다른 eaT 시각과 같은 규칙으로 서울 벽시각을 거쳐
instant가 된다.

### 3.5 이 실행으로 함께 채워지는 것

같은 endpoint에서 다른 그룹도 온다. 이번 범위에 넣는다.

| 그룹 | 뜻 | 우리 결손 | 판정 |
| --- | --- | --- | --- |
| `EP049` | 공고 진행상태 12개 | `eat:attempt-status` 9개 전부 이름 없음 | **9/9 덮임** — 넣는다 |
| `BC016` | 기관 유형 16개 | 화면이 `school`·`unknown`으로만 구분 | 넣는다(AGENTS 5) |

`eat:award-method`(9) · `eat:planned-price-type`(2)의 그룹 번호는 아직 못 찾았다. 공고 상세
화면에서 같은 방식으로 잡으면 되고, **이번 범위 밖**이다(EAT-200).

## 4. 품목 — 닫힌 원자 어휘에 코드를 발급한다

### 4.1 원천에 코드가 없다는 것은 확정된 사실이다

`SOURCE-FIELDS.md` T6:

> `MLFD_CLASS_CD`는 `_CD`로 끝나지만 코드가 아니다. 실제 정체는 공고 안 품목 줄의 **순번**이다.
> 공고의 품목군은 `MAIN_ITEM_NM`/`MAIN_ITEMS`/`ITEM_GB_NM`의 **닫힌 원자 어휘이며 코드가 없다.**
> 식재료 표준코드 API로 갈아타는 것도 안 된다 — 계층이 어긋나 함수 대응이 성립하지 않는다.

### 4.2 어휘가 정말 닫혀 있다

과거 전체 89,576 revision 중 품목 라벨이 있는 59,766건을 콤마로 쪼갠 결과다.

| 원자 | 건수 |
| --- | --- |
| 가공식품 | 15,149 |
| 육류 | 13,886 |
| 농산물 | 12,091 |
| 수산물 | 11,423 |
| 가금류 | 10,489 |
| 김치류 | 7,032 |
| 곡류 | 4,571 |
| 우유류 | 1,921 |

**정확히 8개로 닫힌다.** 오타 변형도, 안 쪼개진 합성도 없다. `육가금류` 같은 값은 존재하지 않는다.

### 4.3 왜 우리가 코드를 발급해도 되나

근거 둘이다.

1. **콤마가 구분자라는 것은 원천 조사로 확인된 사실이다.** `SOURCE-FIELDS.md` T11이
   "두 필드의 진짜 불일치는 없고 차이는 전부 콤마 앞뒤 공백이다. 공백을 정규화하라"고 적고 있다.
   쪼개기 규칙은 우리의 발명이 아니다.
2. **쪼갠 결과가 8개로 깨끗이 닫힌다.** 규칙이 틀렸다면 쓰레기 원자가 나왔을 것이다.

그래도 **라벨 → code_value 매핑은 우리가 소유하는 결정**이다. 그래서 위험을 이렇게 가둔다.

- 9번째 원자가 나타나면 **조용히 섞이지 않고 격리**한다(AGENTS 3). 격리된 라벨은 세어서 드러내고,
  사람이 보고 나서 code_value를 발급한다.
- 발급한 코드는 `source_system`이 우리라는 사실을 숨기지 않는다. eaT가 준 코드가 아니다.

**`unknown`이라는 아홉째 코드는 발급하지 않는다.** 발급하면 *"미상을 관측했다"*와 *"아무것도 관측하지
못했다"*가 같은 모양이 되어 둘을 다시 가를 수 없다. 없음은 행이 없는 것으로 두고 수는 세면 나온다.

대신 **서로 다른 두 없음을 갈라 센다.**

| | 무엇인가 | 어떻게 남나 |
| --- | --- | --- |
| 원천 결손 | eaT가 `MAIN_ITEMS`를 비워 보냈다. 학교가 안 채운 것이다 | 품목 code 행이 없다 |
| 매핑 실패 | 라벨은 왔는데 우리가 원자로 못 읽었다 | 격리 기록에 남고 빌드가 수를 드러낸다 |

두 번째가 0이 아니면 그것은 우리 어휘가 원천을 못 따라갔다는 신호이고, 첫 번째와 섞으면 그 신호가
사라진다. 화면에는 둘 다 `품목 미상` 한 낱말로 보여도 좋지만(사용자 결정) 저장에서는 갈라야 한다.

### 4.4 무엇을 만드나

1. **`eatbid:auction-item` 코드 체계를 선언한다.**

   | 항목 | 값 | 이유 |
   | --- | --- | --- |
   | `namespace` | `eatbid:auction-item` | 기존 체계는 접두사가 곧 소유자다(`mois:`→MOIS, `neis:`→KERIS, `eat:`→aT). 코드를 발급·폐기하는 주체가 우리인데 `eat:`를 쓰면 aT가 코드를 준 것처럼 보인다 |
   | `owner` | `eatbid` | eaT가 코드를 주지 않으므로 9번째 용어가 나타날 때 코드를 발급할 주체는 우리다 |
   | `versionPolicy` | `product-managed` | 기존 열셋은 전부 `source-managed`이고 그것은 원천이 코드를 줄 때 쓰는 값이라 그대로 쓰면 거짓말이 된다 |
   | `validTimePolicy` | `effective-dated` | 기존과 같다 |

   용어(`육류`·`가금류`)는 eaT의 것이라 그대로 싣고, **체계가 우리 것이라는 사실만 이름이 말한다.**
2. **원자 8개에 `core.code_value`를 발급한다.**
3. **라벨을 `code_label_observation`에 싣는다.** 관측 출처는 그 라벨이 온 공고 관측이다.
4. **`mart.open_auction_snapshot.item_code_value_id`를 채운다.** 지금 0/404인 열이다.
   한 공고가 여러 원자를 가지므로 **단일 열로는 담기지 않는다** — 자식 표나 배열 열이 필요하다.
   이 선택은 구현 계획에서 정한다.
5. **조회를 `strpos` 부분일치에서 `code_value_id` 대조로 바꾼다.** `open-auction-queries.ts`의
   `itemLabelPredicate`가 사라지고 id 배열 교집합이 들어온다.
6. **격리 수를 센다.** 어느 원자에도 안 붙은 라벨 수를 마트 빌드가 세고, 0이 아니면 드러낸다.

> **2026-09-16 2차 구현(EAT-230 2차).** 4는 단일 열이 아니라 다리표 `mart.open_auction_snapshot_item`으로 정했고
> (`mart-r5`), 빌더가 core 코드 행이 아니라 `item_label`을 `read_item_label`로 읽어 채운다 — replay 없이 다음
> build부터 동작하며 규칙의 권위는 그 함수 하나다. 5는 목록·요약·조합 건수 셋에서 `itemAtomPredicate`(다리표
> `exists` 조인)로 바꿨고 `strpos(item_label` 술어는 서버에 남아 있지 않다. 계약의 `items`는 원자 enum으로 좁혔고
> 저장 조합(`app.workspace_filter_combination_item`)도 `item_code_value_id`를 가리킨다. 6은 EAT-255로 닫았다 — 빌더가
> 어휘 밖 조각과 행 수를 `mart.build_vocabulary_gap(build_id, scheme_namespace, fragment, row_count)`에 남기고 운영 기대
> `item-vocabulary-gap`이 활성 스냅샷 build에 행이 있으면 조각마다 알린다(대응은 `collection-runbook.md` §4.8).
> `org_round_summary.item_code_value_id`(단일 열)와 결정 화면 코호트는 EAT-256, 제목 추정은 EAT-257이다.

### 4.5 관측률 72%는 원천 결손이 맞다 — 그러나 "왜 없는지"는 받을 수 있다

품목 라벨은 290/404(72%)만 관측되고 시도별 미상은 25~49%다(경기 49%). 우리 정규화가
`ds_info.MAIN_ITEMS` 한 필드만 읽고 있어서 "다른 자리에 있는데 우리가 안 읽는 것 아닌가"를 의심했고,
**2026-09-16 실제 상세 응답을 두 건 불러 확인한 결과 아니었다.**

| | `5797214` (품목 없음) | `5797206` (품목 = 육류) |
| --- | --- | --- |
| 기관 | 제1군수지원여단 | 반송중학교 |
| `ds_info.MAIN_ITEMS` | 없음 | `육류` |
| `ds_mainItemlist` | **빈 데이터셋** | — |
| `ds_itemList` | **빈 데이터셋** | 컬럼 있음 |
| `ds_SelectUnionPurceTgtListR` | **빈 데이터셋** | 빈 데이터셋 |
| `ds_mlsrItemInfo.MLSR_ITEM_YN` | **`N`** | **`Y`** |
| `ds_info.MN_TRMT_LMT_YN` | **`N`** | **`Y`** |

> **[2026-09-16 정정] 위 문단의 결론은 틀렸다.** 공고 두 건만 보고 "응답 전체 어디에도 없다"고
> 일반화했는데, 표본을 늘리자 뒤집혔다. §4.7이 대체한다.

~~**품목이 없는 공고는 응답 전체 어디에도 품목이 없다.** 다른 데이터셋을 읽어도 안 나온다. 원천 결손이
맞고 재파싱으로 채울 수 없다.~~

그래도 **왜 없는지는 받을 수 있다.** `MLSR_ITEM_YN`이 품목 유무와 정확히 갈리는데 우리는 이 필드를
읽지 않는다. 읽으면 `미상`을 "우리가 못 읽은 것"이 아니라 **"원천이 품목을 주지 않는 공고"**로 부를 수
있다. 이는 관측과 해석을 가르는 일이고(AGENTS 3), 그 값 자체가 사용자에게 의미가 있다.

미상이 누구의 것인지도 다시 쟀다. 아래 표는 **열린 공고 404건이 아니라 전체 89,576 revision**이고,
기관 이름은 payload의 `buyer.organizationName` 관측을 쓴다(`core.organization.canonical_name`은
비어 있고 `type`은 전부 `unknown`이다).

| 기관 유형(이름으로 추정) | 전체 | 관측률 | 미상 | 전체 미상 중 비중 |
| --- | --- | --- | --- | --- |
| 학교·유치원 | 87,736 | 67.1% | 28,852 | **96.8%** |
| 복지·보육 | 751 | 37.0% | 473 | 1.6% |
| 교육청·교육원 | 446 | 54.7% | 202 | 0.7% |
| 군부대 | **265** | 46.0% | 143 | **0.5%** |

> **[2026-09-16 정정]** 이 문단은 원래 "군부대가 82% 품목 없음"을 미상의 주된 설명으로 적었다.
> 그것은 열린 공고 404건만 본 수치였다. 전체에서 군부대는 265건, 0.3%다. **미상의 96.8%는 학교이며
> 군부대는 각주다.** 마감 연도별로도 2025년 64.6%, 2026년 66.8%로 일정해 시스템이 바뀐 것도 아니다.

그리고 우리는 **기관 유형을 관측한 적이 없다** — `core.organization.type`이 전부 `unknown`이라 이
구분을 화면에 쓸 수 없다. §3.5의 `BC016`(기관 유형 16개)이 필요한 이유가 여기 있다(AGENTS 5).

이 작업 범위에 넣는 것:

1. **`ds_mlsrItemInfo.MLSR_ITEM_YN`과 `ds_info.MN_TRMT_LMT_YN`을 수집 계약에 추가한다.** 새 parser
   version이며 기존 발행물의 canonical 바이트를 흔들지 않는다(ADR 0025 sealed membership).
   raw는 응답 전체를 저장하므로(`http_client.outcome.body` → `raw_blob`) 재수집이 아니라 재파싱이다.
2. **`MLSR_ITEM_YN`의 뜻을 단정하지 않는다.** `SOURCE-FIELDS.md` T7이 "뜻 자체는 모른다"고 적어 뒀다.
   품목 유무와 동치라는 **관계만** 기록하고, 화면 문구는 그 관계에서만 파생한다.
3. **품목 미상을 두 상태로 가른다.** `원천이 품목을 주지 않음`과 `우리가 아직 못 읽음`. 후자가 0이
   되는 것이 목표다.

### 4.7 `ds_itemList`가 미상의 3분의 2를 메운다 — §4.5를 대체한다

§4.5는 공고 두 건을 보고 "품목이 없는 공고는 응답 어디에도 품목이 없다"고 썼다. **표본을 늘리자
뒤집혔다.**

우리 DB에서 품목 미상인 공고 30건을 골라 eaT 상세를 다시 불렀다(2026-09-16).

| | 30건 중 |
| --- | --- |
| `ds_info.MAIN_ITEMS` 있음 | **0** |
| `ds_itemList.MLFD_CLASS_NM` 있음 | **19 (63%)** |

즉 **우리가 "품목 미상"이라 부르는 공고의 63%가 원천에 품목 이름을 갖고 있다.** 우리가 그 데이터셋을
읽지 않았을 뿐이다. 관측률이 66.7% → 약 **87.7%**가 된다. 추정 한 글자 없이.

#### 그 값의 성질 — 코드가 아니라 사람이 적은 글자다

라벨이 있는 공고 30건에서 두 필드를 나란히 봤다. 겹친 10건이다.

| `MAIN_ITEMS` | `MLFD_CLASS_NM` |
| --- | --- |
| 육류 | 축산물업체 |
| 육류 , 가금류 | 육류 |
| 농산물 , 가공식품 , 김치류 | 식품류 |
| 육류 | 축산물 / 축산 |
| 가공식품 | 공산품 / 공산 |
| 수산물 | 수산 |
| 농산물 | 농산 |

**그룹 수준 모순은 0이지만 자유 텍스트이고 세밀도가 낮다.** `육류 , 가금류`가 `육류` 하나로 줄고,
셋이 `식품류`로 뭉친다. 어휘도 제각각이다(`공산품`/`공산물`/`공산`/`공산품업체`).

같이 오는 `MLFD_CLASS_CD`는 코드가 아니다. 같은 `공산품`에 `04`와 `03`이 따로 붙는다 —
`SOURCE-FIELDS.md` T6의 "`MLFD_CLASS_CD`는 공고 안 품목 줄의 순번"이 맞다.

#### 그래서 어디에 저장하나

`MLFD_CLASS_NM`은 **관측이되 원자가 아니다.** `MAIN_ITEMS`와 같은 자리에 넣으면 8원자 어휘가
`축산물업체`·`식품류`로 오염된다. 별도 관측으로 싣고, 8원자로 접는 매핑은 우리가 소유하되 근거를
eaT 자신의 식재료 표준코드에 둔다.

```text
POST /nm/mp/150/selectBcCmnsFoodCdList.do   ds_param.GUBUN = LCLSF | MCLSF | SCLSF | SDVS

대분류   1 농산물 · 2 수산물 · 3 축산물 · 4 가공식품
축산물 중분류   난류 · 닭고기 · 돼지고기 · 부산물 · 수입소고기 · 오리고기 · 육우 · 한우
```

**`축산물 = 육류 + 가금류`가 우리 추측이 아니라 eaT 체계다.** 다만 표준코드는 곡류를 농산물 아래,
우유류를 가공식품(유가공품류) 아래 두므로 8원자와 층이 어긋난다. 표준코드로 **갈아탈 수는 없고**
매핑 근거로만 쓴다. `SOURCE-FIELDS.md` T6의 "계층이 어긋나 함수 대응이 성립하지 않는다"가 맞다.

### 4.8 품목 말고도 안 읽던 축이 다섯 더 있다

상세 응답 `ds_info`는 **116열이고 86열에 값이 있는데 우리 계약은 16열만 읽는다.** 품목을 파다가
전수 대조를 했고, 아래는 같은 30건 표본에서 **관측률 100%**인데 우리가 안 읽는 것들이다.

| 축 | 필드 | 실측 | 왜 필요한가 |
| --- | --- | --- | --- |
| **투찰 성립** | `SGNS_BID_PRCS_MTHD_CD_NM` | 단독입찰 허용안함 **29/30** | 혼자 들어오면 유찰이다. **우리가 이미 보여주는 `참여 0곳`의 뜻이 바뀐다** |
| **납품** | `DLVRY_STRT_DT`·`DLVRY_END_DT`·`DLVRY_TIME`·`DLVRY_END_TIME`·`DOG_ADDR` | 30/30, 납품시각 06:00~08:30 | 그 시간에 그곳까지 갈 수 있는지가 품목만큼 큰 투찰 조건이다 |
| **자격제한** | `QLFC_LMT_YN`·`QLFC_LMT_ITM_CD_NM` | 30/30, HACCP 제한 **3/30** | 낼 수 없는 공고를 열어 보기 전에 거른다 |
| **제한조건 유형** | `LMT_CNDTN_CD`·`LIMIT_CONDITION_NM` | 지역제한경쟁 28 · 일반경쟁 2 | 제한지역 *목록*은 읽으면서 제한의 *종류*를 안 읽는다 |
| **금액 해석** | `VAT_INCL_YN`·`BGNG_PRC_RLS_YN`·`MRKT_EXMN_PRC_RLS_YN` | 30/30 | 기초금액을 보여주면서 부가세 포함인지 모른다 |

그 밖에 `CHG_TP_NM`(일반공고 29 · 재입찰 1)은 화면이 요구하던 정정·재입찰 배지의 출처이고,
`ds_areaList`의 `CTPV_NM`·`SGG_NM`은 참가제한지역의 **이름**인데 우리는 코드만 읽는다.
`ATCHFL_ID`가 가리키는 현품설명서에는 품목 명세가 더 있으나 이번 범위 밖이다.

**이 축들은 품목 작업과 같은 재파싱 한 번에 들어온다.** raw가 응답 전체를 보존하므로 재수집이 아니다.

원천이 주는 품목을 다 읽고도 남는 미상은 약 12%다. 거기에만 §4.6을 쓴다.

### 4.6 제목에서 품목을 추정한다 — 정답지가 있어 정확도를 잴 수 있다

품목이 `주취급품목`에 없어도 **제목에는 거의 항상 있다.** 2026-09-16 eaT 상세 화면에서 확인한
`이일여자고등학교` 공고가 그 전형이다.

| 항목 | 값 |
| --- | --- |
| 공고건명 | `2026년 10월분 이일여자고등학교 식재료(축산물류) 소액수의` |
| 주취급품목 | **비어 있음** |
| 자격제한 | `HACCP인증업체로 참가자격을 제한합니다.(품목 : 선택안함)` |

eaT 자신도 품목 드롭다운이 없고 **사용자가 `공고건명`으로 찾는다.** 우리가 발명하는 방식이 아니다.

#### 왜 이것이 추측이 아닌가

**정답지가 있다.** 품목이 관측된 50,751건으로 규칙의 정밀도·재현율을 잴 수 있다. 규칙 v3 실측이다.

| 품목 | 정밀도 | 재현율 |
| --- | --- | --- |
| 육류 | **98%** | 95% |
| 농산물 | **99%** | 74% |
| 우유류 | **99%** | 40% |
| 가금류 | **98%** | 47% |
| 김치류 | **98%** | 54% |
| 수산물 | 97% | 81% |
| 가공식품 | 96% | 83% |
| 곡류 | **81%** | 29% |

**정밀도가 높고 재현율이 낮다** — 틀린 것을 붙이는 게 아니라 못 붙인다. 안전한 방향으로 틀린다.

> **[2026-09-16 재측정]** 위 표는 규칙 v3의 수치이고 이 문서가 옮겨 적은 것이다. 같은 날 전체
> revision(라벨 있는 59,766건)에 단순 낱말 규칙으로 다시 재니 축 셋은 이렇다.
>
> | 규칙 | 제목 단서 | 맞음 | 정밀도 | 재현율 |
> | --- | --- | --- | --- | --- |
> | 축산(축산·육류·가금·돈육·우육·한우·계육) → 육류·가금류 | 20,423 | 20,395 | **99.9%** | **92.0%** |
> | 수산 → 수산물 | 9,065 | 8,946 | 98.7% | 65.5% |
> | 김치 → 김치류 | 4,659 | 4,547 | 97.6% | 53.8% |
>
> **축산은 거의 완벽하다.** 제목에 축산 단서가 있으면 1,000건 중 999건이 실제로 육류·가금류다.
>
> 다만 회수량은 이 문서가 적은 것보다 작다. 미상 29,810건 중 축산 단서를 가진 것은 **6,554건**이고,
> 품목 낱말을 하나라도 가진 것이 20,443건(68.6%)이다. `부식`·`식재료`는 품목 단서가 아니라 제외했다.

§4.7이 나온 뒤 이 층의 몫이 줄었다. 원천의 `ds_itemList`까지 읽으면 관측만으로 약 87.7%가 되고,
**제목 추정은 남는 12%에만 쓴다.** 추정 99.9%보다 관측 100%가 먼저다.

규칙을 만들며 드러난 원천의 관행이다. 추측이 아니라 실측으로 확인했다.

- **`축산물A` = 소·돼지, `축산물B` = 닭·오리.** 학교가 관행적으로 나눈다.
- **`축산물` 단독(A/B 표시 없음)은 육류다.** 육류만 3,253 · 육류+가금류 2,455 · 가금류만 161이라
  육류는 97% 확실하고 가금류는 42%뿐이다. 그래서 단독 표기에 가금류를 붙이지 않는다.
- **`농수공`·`농공수산`·`농공산품`** 같은 줄임말이 여러 원자를 한 번에 가리킨다.
- `계육`은 `육류`라는 글자를 품지만 가금류다.

#### 무엇을 만드나

1. **관측과 추정을 절대 같은 열에 두지 않는다**(AGENTS 3).

   ```text
   item_code_value_id           원천이 준 품목. 관측.
   inferred_item_code_value_id  제목에서 추정. 해석.
   title_rule_version           어느 규칙으로 추정했는지
   ```

2. **정밀도 기준선을 둔다.** 기준 미만인 품목은 추정을 붙이지 않는다. v3에서는 곡류(81%)가 여기
   걸린다. 기준선 값은 구현 계획에서 정한다.
3. **빌드마다 정답지로 다시 잰다.** 정답지는 계속 늘어나므로 규칙이 조용히 썩지 않는다. 새 표기가
   나타나 정밀도가 떨어지면 그 사실이 드러난다. **문자열 매칭의 위험을 측정 가능한 것으로 바꾸는
   장치이며 이 설계의 핵심이다.**
4. **규칙 버전을 바꾸면 새 `calc_version`의 새 build다**(ADR 0034). 과거 추정이 조용히 바뀌지 않는다.

#### 화면에는 적지 않는다

**어느 필드에서 읽었는지는 우리 사정이지 사용자의 관심사가 아니다.** `apps/web/AGENTS.md`가
"화면 문구는 사용자가 할 일과 실패만 말한다. 내부 결정과 구현 사정을 설명하지 않는다"고 한 그대로다.
화면은 품목을 그냥 품목으로 보여 준다. 관측과 추정의 구분은 **데이터 층에만** 남는다.

대신 **제목을 행에 보여 준다.** `축산물A(소,돼지)`가 화면에 있으면 근거가 이미 거기 있고, 우리가
확신도를 주석으로 달 필요가 없다.

그래도 남는 5%는 미상이다. 화면은 **`품목 미상`을 기본으로 포함**해야 한다 — 끄면 낼 수 있는 판이
조용히 사라진다. 이것은 3층(화면) 설계의 입력이다.

## 5. 범위 밖

- 화면 설계(필터 UI·검색·목록 구조). 이 문서가 끝나고 계약이 바뀐 뒤에 한다.
- `eat:award-method`·`eat:planned-price-type` 이름. 그룹 번호를 아직 못 찾았다(EAT-200).
- 참가제한지역(`eat:eligibility-area`). 다른 축이고 사용자 결정으로 뒤로 미뤘다.
- 행안부 canonical 전환(ADR 0035). 별개 가치이며 선행 조건이 아니다.
- NEIS 학교 코드 연결. `neis:school`은 코드 0개이고 검색에는 필요 없다.

## 6. 검증 기준

- 코드목록 endpoint가 검토된 전송 계약으로 등록돼 있고 raw → 관측 → canonical 순서를 지킨다.
- `eat:auction-location-sido` 15개, `eat:auction-location-sigungu` 201개에 이름이 붙는다.
  미매칭이 0임을 재현 가능한 질의로 보인다.
- `eat:attempt-status` 9개에 이름이 붙는다.
- `eatbid:auction-item` 원자 8개에 code_value가 있고 `mart`의 품목 열이 채워진다.
- 품목 조회가 `code_value_id`로 걸리고 `strpos` 부분일치가 남아 있지 않다.
- `MLSR_ITEM_YN`이 계약에 들어가 있고, 품목 미상이 `원천이 주지 않음`과 `못 읽음` 두 상태로 갈린다.
  후자가 0이다.
- 제목 추정이 관측과 **다른 열**에 저장되고 규칙 버전이 함께 남는다.
- 빌드가 정답지로 품목별 정밀도·재현율을 재고 그 수치가 기록된다. 기준선 미만인 품목에는 추정을
  붙이지 않는다.
- 규칙 버전을 바꾼 build가 새 `calc_version`을 갖는다.
- 어느 원자에도 안 붙은 라벨 수를 빌드가 세고, 그 수가 관측 가능하다.
- 9번째 원자를 넣은 fixture가 격리되고 빌드가 그 수를 드러내는 시험이 있다.
- 원천 결손과 매핑 실패가 저장에서 갈라지고, 각각의 수를 따로 셀 수 있다.
- 테스트명 한국어. `pnpm architecture:check -- --changed` 통과.

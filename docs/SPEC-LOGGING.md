## 0. 먼저 — 무엇을 기록하나 (질문 7이 나머지를 정한다)

**"다 기록한다"는 답이 아니다.** 우리가 겪은 사고 다섯에서 역산했다.

| 사고 | 그때 로그에 무엇이 있었으면 3초에 끝났나 |
|---|---|
| 로더가 `a[15]`로 죽고 7개 테이블이 빌 뻔함 | **단계 이름 + 그때까지 처리 건수 + "롤백됨"** |
| `fetch_open`이 `/app/data`에 쓰고 로더가 `/lake`를 읽어 매일 exit 0 | **읽은 절대경로 · 쓴 절대경로 두 줄** |
| 시도코드 18을 한 번도 안 받음 | **요청한 코드 목록 vs 코드별 수신 건수** |
| `n >= 20` 문턱이 신설 지역을 잘라냄 | **버린 수 + 버린 이유** |
| 배포 안 됐는데 지도 버블만 60개 빔 | **`BUILD_SHA` + 렌더 건수** |
| **어제 17:34부터 로더 100% 실패 — 오늘 우연히 발견** | **"마지막 성공이 언제인가"** — 이건 로그가 아니라 **탐지**의 일이다(§0-c) |

**다섯 개의 공통점: 전부 "무엇을 했는가"가 아니라 "무엇을 안 했는가"다.**
성공 로그는 한 건도 도움이 안 됐다. 도움이 됐을 것은 전부 **경계의 수지(收支)**다.

> ## 결정 0 — 로그는 서사가 아니라 **경계의 수지**다
> **들어온 것 · 나간 것 · 버린 것 · 못 한 것.** 이 넷이면 위 다섯이 전부 3초다.
> 나머지(진행 상황·성공 알림)는 **stdout에 흘리고 사라져도 된다.**

## 0-b. mw-auction 로깅의 전제 — 따져보니 **우리한테 더 맞는다. 그리고 그것만으론 부족하다**

리더가 밝힌 전제: **소비자가 사람 대시보드가 아니라 에이전트다.**

| 전제의 귀결 | 우리에게 | |
|---|---|---|
| 예쁜 출력·색상·알림 피로가 덜 중요 | ✅ | 사용자 1명. 대시보드를 볼 사람이 없다 |
| **자기설명적이어야 한다** | ✅✅ | **§0의 결론과 같은 문장이다.** `저장 실패`가 아니라 `open_auctions 116건 중 0건 저장 · 경로 /app/data · 로더는 /lake 읽음` |
| **검색 가능성 > 형식** | ✅✅ | **파일이 아니라 테이블이어야 하는 근거**가 여기서 나온다(§2) |

**전제는 우리한테 더 강하게 맞는다** — mw-auction은 그래도 사람이 볼 여지가 있지만 우리는 사실상 에이전트뿐이다.

**그런데 전제가 맞아도 부족한 지점이 셋 있다.** 리더가 하나(탐지)를 짚었고, 나머지 둘은 내가 찾았다.

**(가) 에이전트는 맥락이 없는 게 아니라 "틀린 맥락"을 갖는다.**
사흘 뒤 읽는 에이전트는 **무맥락이 아니라 그동안 코드가 바뀐 상태**에서 읽는다.
로그가 `load_postgres.py:217`을 가리키는데 그 줄이 이미 다른 코드면 **오독한다.**
→ **로그에 파일·줄 번호를 적으면 썩는다.** 안정된 **행위 이름**(`threshold_school`·`clean_inst_none`)을 적는다.
줄 번호가 필요하면 `build_sha`로 되짚을 수 있으니, 로그가 그 짐을 질 이유가 없다.

**(나) 에이전트는 "정상"을 모른다.**
사람은 *"어제도 이랬나?"* 를 어렴풋이 기억하는데 에이전트는 못 한다.
`open_auctions: 0`만 있으면 판단이 안 되고 `직전 116 → 이번 0`이어야 판단이 된다.
→ **로그가 절대값이 아니라 직전 대비를 함께 담아야 한다.**

**(다) — 리더 반론. 이게 제일 크다.**

## 0-c. 탐지와 재구성은 **다른 일이다** (리더 반론 수용 · 내 설계 정정)

> *"아무도 안 보는 로그는 조용한 실패와 같다."* 에이전트가 **누가 물을 때만** 읽으면,
> 무언가 조용히 깨진 채 **아무도 안 물을 때까지** 앉아 있는다.

**어제 17:34부터 로더가 100% 실패한 걸 오늘 우연히 발견한 게 정확히 그 형태다.**
그리고 더 나쁜 건 — **아무도 "로더 괜찮나?"를 물을 이유가 없었다는 것**이다.
"누가 물을 때만"이 아니라 **"물어볼 생각이 들 때만"**이다.

| | 무엇 | 우리 상태 |
|---|---|---|
| **탐지** | 뭔가 깨졌다고 **먼저 말한다** | `drift.py` · `crawl-guard` · `fetch_open` X13 — **이미 있다** |
| **재구성** | 깨진 뒤 **무슨 일이었는지 되짚는다** | **없다. 이게 로깅이 채울 자리** |

> ### 🔴 내 §1 "결정 1"이 틀렸다 — 정정한다
> 1차안은 *"다음 실행이 직전 실행을 읽어 대조하고 급감이면 비영 종료"* 였다.
> **그건 탐지를 로깅 안에 다시 구현하는 것이다.** X13이 이미 그걸 하고 있고, 두 번 만들면 안 된다.
>
> **바른 경계: 로깅은 사실을 남기고, 탐지는 그 사실을 읽어 판정한다.**
> - `run_log` = **사실 저장소**. 판정 로직 없음
> - 탐지 3종 = **판정자**. 지금은 각자 파일을 읽어 각자 판정하는데, **읽는 곳만 `run_log`로 바꾼다**
> - **로깅이 탐지의 데이터 소스가 되고, 탐지 로직은 아니다**
>
> 지금 X13은 직전 JSON을 자기가 읽어 자기가 판정한다(둘을 겸함).
> `run_log`가 생기면 **데이터는 `run_log`에서, 판정은 X13에서.** 그게 두 번 구현 안 하는 선이다.

### 완료 판정 — **경로가 실제로 이어지는가**

리더 요구: *"탐지가 깨졌다고 말한 뒤 에이전트가 로그로 원인까지 가는 경로."*
**어제 17:34 사고를 재현 시나리오로 고정한다.**

```
탐지: "로더 마지막 성공 = 어제 17:34"
  ↓ SQL 1회   select * from run_log where job='load' order by started_at desc limit 5
결과: ok=null 4건(시작하고 안 끝남) · paths.read=/lake · io.received=0
  ↓ SQL 1회   (필요하면) notes 조회
원인 확정
```
**목표: SQL 2회 안에 원인.** 이걸 못 하면 이 설계는 실패다.
**그리고 "마지막 성공이 언제인가"는 `run_log`가 답을 갖고 있어야 탐지가 물을 수 있다** — 지금은 그 질문 자체가 불가능하다.

**그리고 이건 새 개념이 아니다.** 우리는 이미 네 곳에서 이걸 하고 있다 —
`fetch_open` X13(지역별 성공/실패·급감), 적재 요약(제외 내역·분열/합침),
`crawl-guard.json`, `source-drift.json`. **흩어져 있을 뿐이다.**
**이 문서는 그 넷을 한 모양으로 모으는 것이지 층을 하나 더 얹는 게 아니다.**

## 1. 무엇을 남기나 — `run_log` 한 테이블

```
run_log(
  run_id, started_at, ended_at, ok,
  job,            -- 'crawl' | 'fetch_open' | 'load' | 'reparse' | 'migrate'
  build_sha,      -- 배포 대조용
  paths jsonb,    -- {read: [...], write: [...]}  ← 절대경로. 사고 2가 이걸로 3초
  io jsonb,       -- {requested: {...}, received: {...}, wrote: {...}}
  dropped jsonb,  -- {threshold_school: 1877, clean_inst_none: 412, ...}  ← 이유별
  notes jsonb     -- 급감·드리프트·게이트 결과
)
```

| 필드 | 답하는 질문 | 대응 사고 |
|---|---|---|
| `paths` | *"어디서 읽고 어디에 썼나"* | `/app/data` vs `/lake` |
| `io.requested` vs `io.received` | *"부른 만큼 받았나"* | 시도코드 18 |
| `dropped` | *"무엇을 왜 버렸나"* | `n>=20` 문턱 · `len(opened)<5` |
| `ok` + `notes` | *"끝났나, 중간에 죽었나"* | `a[15]` |
| `build_sha` | *"도는 코드가 방금 만든 코드인가"* | 지도 버블 60개 |

> **`dropped`가 이 설계의 핵심이다.** `failing-loudly.md` F2가 *"표본이 적다는 사실은 화면이 말한다"* 인데,
> **로더가 무엇을 버렸는지는 화면이 아니라 여기에 말한다.** 그리고 §4-b 실행 대장 ①
> (*"이 값을 지우는 코드는 어디 있고 언제 도나"*)의 답이 매 실행 자동으로 채워진다.

### 결정 1 — **write-ahead. 시작할 때 먼저 쓴다**

가장 중요한 디테일이고, 안 하면 `a[15]` 같은 사고가 **아무 흔적도 안 남긴다.**

```
시작:  insert run_log(run_id, job, started_at, build_sha, paths, ok=null)
끝:    update  run_log set ended_at=…, ok=true/false, io=…, dropped=…, notes=…
```

- **프로세스가 죽어도 `ok=null` 행이 남는다** = *"시작했는데 안 끝났다"*.
  지금은 죽으면 **아무것도 안 남는다** — 그게 어제 17:34를 오늘까지 모른 이유다.
- **`ok=null`이 곧 탐지 신호다.** 탐지가 물을 질문이 *"마지막 `ok=true`가 언제인가"* 하나로 줄어든다.
- `paths`를 **시작 시점에** 쓴다 — 경로 불일치(`/app/data` vs `/lake`)는 죽기 전에 이미 확정돼 있다.

> **판정은 여기서 하지 않는다**(§0-c). `run_log`는 `ok=null`을 남길 뿐이고,
> *"몇 건 연속이면 문제인가"* 는 탐지 3종이 정한다.

## 2. 어디에 남기나 (질문 3)

**CronJob 파드가 사라지면 로그도 사라진다** — 지금 제일 큰 구멍이다. 둘로 가른다.

| | 어디 | 왜 |
|---|---|---|
| **수지**(`run_log`) | **Postgres 테이블** | 작다(실행당 1행 · 연 ~1,500행). **비교가 목적이라 시계열이어야 한다.** 사라지면 안 되는 건 이것뿐 |
| **서사**(진행·스택트레이스) | stdout → `kubectl logs` | 사라져도 된다. **크론이 매일 도니 다시 나온다** |

> **사라지면 안 되는 건 "그날 무엇이 들어오고 나갔나"이지 스택트레이스가 아니다.**

- `events` 테이블 옆에 두고 **재적재 보존 대상**(`user-data.ts`와 같은 취급)
- **저장·전달 인프라는 `ARCH-DATA` 참조.** 이 문서는 **무엇을 어떤 모양으로 남기는가**만 정한다

**기각: OpenTelemetry · Loki · Grafana.**
서비스 1개 · 크론 1개 · 사용자 1명이다. 수지 테이블 하나와 stdout이면 위 다섯 사고가 전부 잡힌다.
**관측 인프라를 세우는 비용이 그 값을 못 넘는다.** 트래픽이 생기거나 서비스가 둘이 되면 그때 다시 본다.

## 2-b. 🔴 파이썬을 어디에 둘 것인가 — **(c) 지지. 단 둘로 가른다**

리더 초안 (c)에 동의한다. **근거를 하나 더 대고, 그다음 (c)를 쪼갠다.**

**(b) 긴 수명 파이썬 서버를 기각하는 결정적 이유는 단일 실패점이 아니라 스케줄러다.**
(b)는 스케줄러를 우리가 만들어야 하는데, **k8s CronJob이 이미 검증된 걸 다시 만드는 것**이다.
그리고 우리는 **그 함정들을 이미 밟고 고쳤다** — `app.yaml` 주석이 왜 넣었는지 적어놨다:
`concurrencyPolicy: Forbid`(로더 둘이 790만 행을 동시에 지워 락이 엉킴) ·
`activeDeadlineSeconds`(매달린 Job이 다음 회차를 조용히 스킵) · `startingDeadlineSeconds`(100회 놓치면 스케줄링 정지).
**자체 스케줄러는 이 셋을 처음부터 다시 밟는다.**
그리고 "밖에서 물어볼 창구"는 리더 말대로 **NestJS 엔드포인트 하나**면 된다 — 파이썬 서버를 세울 이유가 아니다.

### 그런데 (c)를 그대로 쓰면 안 된다 — **크롤러와 로더는 처지가 다르다**

| | DB 접근 | 판정 |
|---|---|---|
| **로더·서버** | DB가 곧 작업 대상 | ✅ **`run_log`에 직접 쓴다** |
| **크롤러**(`backfill`·`update_lake`·`fetch_open`) | 레이크(파일)에만 쓴다 | ❌ **직접 쓰지 않는다. JSONL 사이드카 → 로더가 흡수** |

**크롤러에 DB 의존성을 새로 만들지 않는 이유 셋:**
1. **DB 장애를 수집에 전파하지 않는다.** 수집은 DB가 죽어도 계속 돌아야 한다 — 원본은 지나가면 못 받는다
2. **백필은 몇 시간 돈다.** 그동안 DB 커넥션을 붙들 이유가 없다
3. **부트스트랩 공백이 사라진다**(리더 반박 4). 크롤러가 DB를 아예 안 보면 "DB 없을 때"라는 상태가 없다

로더가 적재하면서 사이드카를 읽어 `run_log`에 넣는다. **크롤 로그가 로더보다 늦게 DB에 도착하지만,
재구성에는 문제가 없다** — `run_id`와 시각이 그 안에 있다.

### 리더 반박 4개에 답한다

| 반박 | 답 |
|---|---|
| **DB 쓰기가 실패하면?** | **로깅 실패가 작업을 죽이면 안 된다.** `run_log` 쓰기는 감싸고, 실패하면 **그 내용을 stdout에 그대로 뱉는다**(`run_log 기록 실패: <이유> + 페이로드 전문`). **stdout이 최종 안전망**이다. 작업 종료 코드는 유지한다 — 작업은 성공했고 기록만 실패한 것이다 |
| **로더가 `delete`로 시작하는데 로그도 지워지면?** | `run_log`는 **`user-data.ts` 계열**(재적재 보존). `reset-dev.sql` 제외 · 로더 `delete` 목록에 안 들어간다 · **§5-5 "삭제 금지" 목록에 올린다.** 그리고 `db-migrate`(PreSync)가 만드니 로더보다 먼저 산다 |
| **백필 시간당 9,700건 — 행 단위면 폭발** | **행 단위로 안 쓴다.** `run_log`는 **실행당 1행**이고 9,700은 `io.received` **숫자 하나**로 들어간다. 개별 실패는 **이유별 카운트 + 대표 샘플 3건**만. → **규칙: `run_log`에 들어가는 것은 O(1)이지 O(n)이 아니다.** "수지"의 자연스러운 귀결이다 |
| **부트스트랩 — DB 없을 때** | 크롤러는 위 분리로 **애초에 DB를 안 본다.** 로더는 `initial-load`의 initContainer가 스키마를 만든 뒤 도니 DB가 이미 있다. **공백이 없다** |

**추가 반박 — 내가 찾은 것**: **`run_log`가 커지면 `select *`가 느려진다.**
연 ~1,500행이라 당장은 무의미하지만, `notes`·`dropped`가 jsonb라 **행 크기가 예측 불가**다.
→ **`notes`에 O(n) 데이터를 넣는 순간 이 설계가 깨진다.** 위 O(1) 규칙이 크기 방어이자 성능 방어다.

## 3. 파이썬 (질문 1) — **여기가 제일 급하다**

무인으로 24시간 도는 게 크롤러다. 리더 원문: *"정책 바뀌어서 뭔가 깨진 걸 로깅 인지 가능해야."*

**결정: 표준 `logging` + JSON 포매터 ~20줄. 새 의존성 0.**

```python
log = domain_logger("load")          # pino의 createDomainLogger 대응
log.info("적재 시작", read=str(lake), write=DB_URL_masked)
run.drop("threshold_school", 1877)   # 수지에 누적
run.finish(ok=True)                  # run_log 1행 + 직전 대조
```

- **CLS(비동기 컨텍스트) 대응물은 필요 없다.** 크롤러는 **단일 프로세스 순차 실행**이라
  correlationId가 곧 **`run_id` 하나**다. 프로세스 시작 시 만들어 전 로그에 붙인다.
  mw-auction의 `nestjs-cls`는 동시 요청을 가르려는 것이고 **우리 파이썬엔 동시 요청이 없다.**
- `print()`는 그대로 둬도 된다(stdout으로 간다). **새로 쓰는 것만 `log`를 쓴다.**

## 4. 두 언어의 로그 모양 (질문 2) — **필드 3개만 맞춘다**

**결정: `ts` · `run_id`/`correlationId` · `domain` 셋만 통일하고 그 이상은 안 맞춘다.**

**근거:** `SPEC-CODEBOOK §5`가 *"언어 경계를 넘는 어휘를 0으로"* 만드는 중이다.
로그 스키마를 공유하면 **또 하나의 손 동기화 어휘**가 생기고, 그건 품목에서 김치가 빠졌던 그 구조다.
**필드 3개는 사람이 눈으로 맞출 수 있고, 그 이상은 문서가 필요해진다 — 비용이 값을 넘는 지점이 거기다.**

수지(`run_log`)는 **DB 스키마 하나**라 애초에 공유된다. 그게 진짜 통일이 필요한 자리고, 이미 답이 있다.

## 5. 이미 있는 것과의 관계 (질문 4) — **합친다**

| 지금 | 무엇 | 판정 |
|---|---|---|
| `crawl-guard.json` | 크롤 건전성 | **`run_log.notes`로 흡수** |
| `source-drift.json`(`drift.py`) | 원본 필드 변화 감지 | **`run_log.notes`로 흡수** |

> 병행 기간은 두되, `run_log`가 답을 주기 시작하면 파일은 지운다.

## 6. 서버 (질문 5) — **로깅이 모듈 분리보다 먼저다**

**결정: 로깅만 먼저 넣을 수 있고, 먼저 넣는 게 낫다.**

954줄 인라인에 로깅을 끼우면 더러워진다는 우려는 **인터셉터·필터에는 해당하지 않는다** —
`providers`에 등록하는 것이라 **컨트롤러를 한 줄도 안 건드린다.**

```
apps/server/src/common/
  logger.ts                    도메인 로거
  global-exception.filter.ts   ← 지금 없다. 500이 그냥 나간다(7-2가 그 사례)
  interceptors/logging.ts      요청·응답·소요시간
```

**그리고 이게 R17(모듈 분리)의 안전망이 된다** — 954줄을 8파일로 쪼갤 때
**무엇이 깨졌는지 보이는 상태에서** 쪼개는 것과 아닌 것은 다르다.
`/api/firms/bids?summary=1`이 **100% HTTP 500인데 호출처가 0곳이라 아무도 못 봤다**(A5).
전역 필터가 있었으면 그 500이 로그에 쌓였다.

**업무 코드가 쓰는 건 한 줄이다** — mw-auction 패턴 그대로:
```ts
const log = createDomainLogger('open');
log.info({ bidNo }, '자격 판정');   // correlationId·domain 자동
```
**리스너(이벤트→알림) 패턴은 채택하지 않는다.** mw-auction은 텔레그램·메트릭 등 소비자가 여럿이라 값하지만,
우리는 소비자가 `run_log` 하나다. **이벤트버스를 놓는 건 없는 문제를 푸는 것이다.**

## 7. 웹 (질문 6) — **선언은 마크업에, 수집은 한 곳에**

리더 지정: *"`data` 태그로 되게 하고, Sentry 처럼 컴포넌트 하나 감싼 걸로 추상화."*

> **완료 판정: 컴포넌트를 읽었을 때 로깅이 안 보인다.**
> `logEvent(...)`가 컴포넌트 안에 **한 줄이라도** 있으면 그 설계는 실패다.

### 7-1. 두 장치, 같은 성질

| | 잡는 것 | 형태 | 호출부 |
|---|---|---|---|
| **`data-*` 위임** | 사용자가 **뭘 눌렀나** | `<button data-track="bid-save">` + 루트 리스너 1개 | **없음** |
| **`LoadError`** | **조회가 실패했나** | 이미 있는 컴포넌트가 렌더될 때 기록 | **없음** |

**둘 다 "호출부가 없다"가 핵심이다.** `data-*`가 상호작용에 대해 하는 일을 `LoadError`가 실패에 대해 한다.
`ErrorBoundary`(렌더 예외)가 셋째이고, 이것도 감싸는 것이라 호출부가 없다.

### 7-2. 🔴 그런데 **리더의 전제가 아직 사실이 아니다** — 실측

리더: *"모든 실패가 그 한 컴포넌트를 지난다. 거기가 유일한 지점이다."*
**확인했고, 아직 아니다.**

| | 실측 |
|---|---|
| `LoadError` 정의 | `components/load-error.tsx:25` ✅ |
| **`LoadError`를 쓰는 파일** | **5개** |
| **`.catch(() => {})`로 삼키는 자리** | **24개** |

**그리고 우회 방식이 나쁜 쪽이다.** 24곳은 *"다른 에러 UI를 그린다"* 가 아니라
**상태를 초기값(`[]`·`null`)에 두고 끝난다.** 그러면 화면은 에러가 아니라 **빈 상태**를 그린다.

```ts
// analysis-board.tsx:360
fetch(`/api/schools/${id}/roster`).then(r => r.json()).then(setRoster).catch(() => {});
//                                                                    ^^^^^^^^^^^^^^^ roster = []
// → 화면: "이 학교는 아직 참여 기록이 없습니다"   ← 사실이 아닌 문장을 단언한다
```
`failing-loudly.md`가 이미 이 사례를 적어놨다. **삼켜진 실패는 `LoadError`에 애초에 도달하지 않는다.**

> **판정: `LoadError`에 로깅을 붙이면 "표시된 실패"만 잡힌다.
> `.catch(() => {})` 24곳을 `LoadError` 경로로 모으는 것이 선행이고, 그게 웹 로깅 작업의 90%다.**
> 로깅 배선은 그 뒤에 **한 곳**만 건드리면 끝난다 — 순서를 바꾸면 24곳에 로깅을 흩게 된다.

### 7-3. 클릭 추적의 값 — **틀은 만들되 처음엔 거의 안 붙인다**

리더가 *"흐지부지 넘기지 마라"* 고 했으니 분명히 적는다.

**우리는 광고도 퍼널 최적화도 안 한다.** 그리고 **이 제품의 유일한 전환(사장이 값을 정해 저장하는 것)은
이미 `user_mark`에 남는다** — 클릭 이벤트가 아니라 **결과가** 남는다. 화면 열람도 `useTrack`이 이미 보낸다.
**→ `data-track`을 만들어놓고 아무도 안 보면 그게 죽은 배선이다.**

| | 판정 |
|---|---|
| **틀**(`data-*` + 루트 위임 리스너) | ✅ **만든다.** 나중에 붙일 때 컴포넌트를 안 고치게 하는 게 목적이다 |
| **처음 붙일 자리** | **0~2곳.** 아래 조건을 만족하는 것만 |

**붙일 조건: *"화면을 바꿨는데 사장이 그 기능을 쓰는지 모를 때."***
지금 그에 해당하는 후보는 **하나**다 — **`LoadError`의 "다시 시도"**.
실패를 봤을 때 사장이 다시 시도하는지 그냥 나가는지는 **결과로 안 남고**, 그 답이 재시도 UI의 존재 이유를 정한다.

**그 외에는 붙이지 않는다.** 필요해지는 순간 `data-track` 한 글자면 되고, **틀이 있으니 그때 컴포넌트를 안 고친다.**

### 7-4. 어디로 보내나 — **새 엔드포인트 없음**

`/api/events`가 이미 있고 배치 전송한다(`useTrack`). **세 장치가 같은 경로를 쓴다.**
`sendBeacon`으로 보낸다 — 페이지를 떠나며 나는 실패도 잡힌다.

> **⚠ 자기참조 구멍과 그 값싼 답 (§9-4 부분 해소)**
> events 경로가 죽으면 **그 사실도 못 남긴다.** 재전송 큐를 만들 수도 있지만 **안 만든다**(복잡도).
> 대신 **`useTrack`의 화면 열람이 대조군이 된다**:
> **화면 열람은 오는데 에러가 0 → 진짜 0. 화면 열람도 0 → 경로가 죽은 것.**
> 두 신호가 같은 경로를 타므로 **한쪽만 0일 수는 없다.** 공짜로 얻는 구분이다.

**Sentry를 쓰자는 게 아니다** — 외부 SaaS는 없다(스택은 Windows·CF·ArgoCD·GitHub·Docker 다섯).
**빌린 것은 `<ErrorBoundary>`라는 추상의 모양이지 서비스가 아니다.**

## 8. 비용과 순서

| # | 무엇 | 비용 | 안 하면 뭐가 깨지나 |
|---|---|---|---|
| 1 | 파이썬 `domain_logger` + `run_log` 적재 | ~60줄 | **무인 크론이 깨져도 다음 날 아침까지 모른다.** 이미 두 번 그랬다 |
| 2 | 직전 실행 대조 → 비영 종료 | ~20줄 | *"open_auctions: 1"로 하루가 지나가고 아무도 아무 말을 안 했다"* 가 재발 |
| 3 | 기존 JSON 산출물 4개 이관 | ~40줄 | 같은 걸 두 곳에 쓰는 상태가 굳는다 |
| 4 | 서버 `GlobalExceptionFilter` + 로거 | ~80줄 | **500이 조용히 나간다**(A5가 그 사례) |
| 5a | **웹 `.catch(()=>{})` 24곳 → `LoadError` 경로로** | 24곳 | 서버 죽음이 **"참여 기록이 없습니다"**로 보인다. **5b의 선행** |
| 5b | `LoadError`·`ErrorBoundary`·`data-*` 위임에 기록 배선 | **3곳** | 사장 브라우저에서 조회가 깨진 걸 알 방법이 없다 |

> **5a와 5b의 순서를 바꾸면 안 된다.** 지금 `LoadError`는 5파일이고 우회가 24곳이라,
> 먼저 배선하면 **24곳에 로깅을 흩게 된다.** 모은 뒤에 한 곳만 건드린다.

**순서: 1 → 2 → 4 → 3 → 5.**
1·2가 먼저인 이유는 **무인으로 도는 것이 크롤러뿐**이기 때문이다. 서버·웹은 사람이 보고 있다.

## 9. 이 설계가 못 하는 것

1. **`run_log`는 "무엇이 틀렸나"를 말하지 "왜"를 말하지 않는다.** 스택트레이스는 stdout에 있고
   **파드가 사라지면 없다.** 재현하려면 다시 돌려야 한다 — 크론은 하루 뒤다.
   (`ok=null` + `paths` + `dropped`로 **어디까지 갔는지**는 알 수 있다. 예외 자체는 못 남는다.)
2. **직전 대비 비교는 "천천히 나빠지는 것"을 못 본다.** 매일 3%씩 줄면 임계에 안 걸린다.
   급감만 잡는다 — X13의 한계 그대로다. **그리고 이건 탐지의 한계지 로깅의 한계가 아니다**(§0-c) —
   `run_log`에 시계열이 쌓이므로 **나중에 추세 탐지를 붙일 재료는 생긴다.** 지금 안 붙일 뿐이다.
2b. **에이전트가 "물어볼 생각"을 하게 만드는 건 이 설계 밖이다.** `ok=null`이 쌓여도
   **누군가 조회해야 보인다.** 탐지 3종이 그 자리를 메우지만, **탐지가 안 걸리는 종류의 고장은
   여전히 아무도 안 물을 때까지 앉아 있는다.** 어제 17:34가 그 형태였고, 이 설계는 그걸 **줄이지 없애지 못한다.**
3. **`dropped` 이유는 우리가 붙이는 라벨이다.** 새로 생긴 버림 경로는 **아무도 안 적으면 안 나타난다.**
   `_ledger_check.py`(§4-c)가 새 매핑 상수를 잡듯 **새 `continue`를 잡는 장치는 없다.**
4. ~~웹 에러가 `/api/events`로 가는데 그 경로가 죽으면 그 사실도 못 남긴다~~
   **부분 해소(§7-4)**: 화면 열람과 에러가 같은 경로를 타므로 **한쪽만 0일 수 없다** —
   `열람>0 & 에러=0`이면 진짜 0이고 `둘 다 0`이면 경로가 죽은 것이다.
   **완전 해소는 아니다** — 사장이 그날 앱을 안 열어도 `둘 다 0`이라 **구분이 안 된다.**
5. **로그를 사람이 보는 습관은 이 설계가 못 만든다.** 2번(자동 대조)이 그 의존을 줄일 뿐이고,
   **`notes`에 쌓이는 것은 여전히 아무도 안 볼 수 있다.**

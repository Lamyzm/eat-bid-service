# PDR-0001 — 업체 활동 지역은 사용자가 직접 설정한다

- Status: Active
- Date: 2026-09-05
- Supersedes: 없음
- Superseded-by: 없음
- Linear: EAT-54

## 결정

업체의 활동 지역은 **사용자가 직접 설정한다.** 사업자등록번호나 참여 이력으로 유추하지 않으며,
제안값으로도 만들지 않는다.

지역의 진실 원천은 `core`의 코드 테이블 한 곳이다 — `core.code_scheme`, `core.code_value`,
`core.code_mapping`(`packages/db/src/schema/core/codes.ts`에 이미 있다). canonical 지역은 **대한민국
정부(행정안전부) 행정구역 코드**(`mois:administrative-region`)다.

eaT 참가제한지역(`PDLC_CD`)은 별개 `CodeScheme`(`eat:eligibility-area`)으로 수신하고
`core.code_mapping`으로 행안부 코드에 **명시 매핑**한다. 두 체계를 같다고 보고 직접 조인하지
않는다(규칙 6).

사용자 설정은 `app` 스키마에 둔다(사용자 작성 상태, 규칙 1). 지역은 문자열이 아니라
`core.code_value`의 숫자 id로 참조한다(규칙 2). 코드 체계 문자열과 지역 목록을 여러 모듈·문서·
프론트 상수에 중복 선언하지 않는다. 선언은 `CodeScheme` 등록 한 곳(EAT-43이 만들 `code_schemes.py`)이고 나머지는 전부 참조다.

설정 주체는 사람(사용자) 단위이며 복수 선택이 가능하고, **미설정이 기본이자 유효한 상태**다.

공고와 대조하는 상대는 참가제한지역(`location.eligibilityCodes`)이지 학교 소재지(`location.sidoCode`)가
아니다. 대조 경로는 사용자의 행안부 지역 → 매핑된 eaT 코드 집합 → 공고 코드 순이다.

## 배경

지역을 자동으로 채우고 싶은 유혹은 크다. 온보딩이 사업자등록번호 하나만 받고 그 번호로 과거
전적이 통째로 뜨기 때문에, 같은 재료에서 지역까지 뽑아 입력 단계를 없애자는 안이 자연스럽게 나온다.

**원본에 업체 지역이 없다.** 2026-09-05 전수 census(`docs/audit-source/census-detail.txt`, `ds_bidList`
명단 8,605,417행)에서 업체 축에 실린 값은 넷뿐이다.

| 컬럼 | 뜻 |
| --- | --- |
| `BIZ_NO` · `SHIPPER_BRNO` | 사업자등록번호 |
| `SHIPPER_CD` | 업체 코드 |
| `SHIPPER_NM` | 업체명 |
| `NARA_BIZ_NO` | 부정당 여부(코드가 아니라 문장) |

업체 소재지나 활동 지역을 담은 컬럼은 없다. 유추 말고는 채울 방법이 없다는 뜻이다.

**사업자등록번호 앞자리는 지역이 아니라 세무서 코드다.** 등록 당시 관할 세무서를 가리키므로
사무소 소재지와 체계적으로 어긋나고, 사무소를 옮겨도 번호는 바뀌지 않는다.

**참여 이력 유추는 실제로 오염된 값을 냈다.** 레거시가 이력에서 지역을 뽑았을 때 `급식소(경상남도`,
`기해시` 같은 후보가 나왔다. 문자열에서 지역을 긁어내는 방식은 조용히 틀리고, 틀린 값이 자격
판정의 뿌리에 앉는다.

**대조 상대를 잘못 고른 실측도 있다.** 레거시는 사용자 지역을 학교 소재지와 대조해서 김해 밖에
있지만 김해 업체가 참가할 수 있는 자격 공고를 놓쳤다. 참가자격은 공고의 참가제한지역이 정하지
학교가 어디 있는지가 정하지 않는다.

행안부 코드는 아직 적재 0건이다. 그래서 이 결정의 실행에는 정부 코드 release 수집(EAT-20)과 eaT
참가제한지역 189종(census `PDLC_CD`, 327,168행에서 고유 189)의 매핑이 선행한다. 그때까지 미설정은
정상 상태이며 추측으로 메우지 않는다(규칙 3).

## 대안과 기각 이유

- **(a) 사업자등록번호에서 지역을 유추한다.** 기각. 앞자리는 세무서 코드라 지역이 아니다. 지역처럼
  보이는 값을 지역으로 쓰는 것이 규칙 2가 금지하는 문자열 정체성이다.
- **(b) 참여 이력의 지역 합집합을 제안값으로 준다.** 기각. 이력은 증거이지 정의가 아니고, 위의
  오염 후보가 실측으로 나왔다. 제안값이라도 화면에 뜨는 순간 사용자는 확인 없이 넘긴다. 유추를
  완전히 없애는 쪽이 안전하다.
- **(c) eaT 참가제한지역 코드를 canonical로 삼는다.** 기각. 데이터는 이미 있지만 소스 종속 코드가
  제품의 지역 정체성이 되면 다른 소스나 정부 코드와 정합이 되지 않고, 화면·문서마다 코드가
  재선언될 위험이 생긴다. canonical 대신 **매핑 대상**으로 둔다.
- **(d) 지역 전용 테이블을 새로 만든다.** 기각. 이미 있는 `core` 코드 테이블과 권위가 둘이 된다(규칙 1).

## 되돌리기 조건

- **eaT가 업체 소재지·활동지역 필드를 응답에 싣기 시작하거나, 설정률이 낮아 미설정 사용자에게
  공고가 전혀 보이지 않는 것이 실측되면** "제안값"만 재검토한다. 그 경우에도 **자동 확정은 여전히
  금지**이며, 제안을 도입하려면 새 PDR이 필요하다. 점검 지점은 전수 census를 다시 돌릴 때의
  `ds_bidList` 업체 축 컬럼 목록과 설정 화면의 설정률이다.
- **eaT 189종 중 행안부 코드로 매핑되지 않는 코드가 실측되면** `CodeScheme`의 유효기간과 매핑
  정책을 재검토한다.
- **ADR 0032가 워크스페이스를 업체 단위로 확정하면** 설정 주체를 사람에서 업체로 옮길지 재검토한다.

## 영향

- EAT-54: `app` 계약과 지역 설정 화면. 지역은 `core.code_value` 숫자 id로 참조한다.
- EAT-20: 정부(행정안전부) 코드 release 수집. 이 결정의 canonical 축을 채우는 선행 작업이다.
- EAT-43: `CodeScheme` 등록 지점 `code_schemes.py`가 코드 체계 선언의 유일한 자리다. 지금 등록은
  `packages/db/src/seeds/code-schemes.ts`에 있고 `eat:eligibility-area`가 이미 들어 있다. 자리가
  옮겨지더라도 **선언은 한 곳**이라는 규칙은 그대로다.
- EAT-57: 지역·코드 중복 선언 제거. 행안부 행정구역 코드를 `core.code_value`로 적재하고 web의 지역
  이름 문자열과 좌표 변이표를 코드 id 참조로 바꾼다. 이 PDR이 그 작업의 근거다.
  그 적재의 canonical 파일·grain·좌표·매핑 정책은
  [ADR 0035](../../adr/0035-administrative-region-canonical-and-mapping.md)가 소유한다. 매핑 자동
  생성은 정규화 라벨이 양쪽에서 유일할 때로만 제한되므로 이 PDR이 기각한 유사도 병합은 열리지 않는다.
- EAT-39 오늘 화면 필터: 대조 상대는 `location.eligibilityCodes`이며 `location.sidoCode`가 아니다.
- ADR 0032(인증·인가 경계)와 [도메인·데이터](../../architecture/domain-and-data.md) §4.2의 scheme
  분리표. 이 PDR은 그 분리를 제품 설정 축으로 확장한 것이며 데이터 권위를 대체하지 않는다.
- [결정 화면 v2](../decision-screen-v2/README.md)를 포함한 화면 문서의 지역 축 문구.

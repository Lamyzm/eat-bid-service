# 외과적 변경

바꾸는 모든 줄은 요청으로 곧장 연결되어야 한다. 리뷰어가 "이거 왜 바뀌었지?"라고 묻는 순간 리뷰 비용이 배로 뛴다.

## 하지 않는다

- 요청 범위 밖의 코드, 주석, 포맷을 건드리지 않는다
- 눈에 띄었다는 이유만으로 "온 김에 정리"하지 않는다 — **요청받은 리팩터링은 좋지만, 지나가다 하는 정리는 아니다**
- 깨지지 않은 것을 리팩터링하지 않는다
- 자기 취향이 아니어도 기존 스타일을 따른다

## 죽은 코드

- 관련 없는 죽은 코드는 **언급만 하고 지우지 않는다.** 정말 죽었는지는 대개 외부 확인이 필요하다
- 자신의 변경이 만들어낸 **고아만** 정리한다

## 기록에 덧붙인다, 덮어쓰지 않는다

옛 접근, 실험 history, docstring history는 모두 기준선으로서 가치가 있다. 덧붙이고, 덮어쓰지 않는다. 왜 어떤 접근을 택하지 않았는지의 기록을 잃으면 다음 사람이 같은 막다른 길로 다시 걸어간다.

## 재구조화가 **작업 자체**일 때

module 분리, 파일 이동, README 재작성은 그것이 요청된 작업이라면 얼마든지 좋다. 위 규칙은 그것을 금지하는 게 아니라 — 관련 없는 변경에 그것을 **몰래 끼워 넣는 것**을 금지하는 것이다.

## 건드리기 전에: Chesterton's Fence

기존 코드를 지우거나 단순화하기 전에 **왜 그렇게 쓰여 있는지** 먼저 확인한다. 전체 절차는 `chestertons-fence`를 본다 — 핵심은: 이해하지 못한 것을 부수지 않는다.

## 변경 크기

작은 변경은 리뷰하기 쉽고, 병합이 빠르고, 더 안전하게 나간다.

| 크기 | 판정 |
|---|---|
| ~100줄 | 좋음. 한 번에 리뷰 가능 |
| ~300줄 | 하나의 논리적 단위라면 괜찮음 |
| ~1000줄 | 너무 크다. 나눈다 |

**diff 크기만이 아니라 파일 크기를 본다.** 작은 diff라도 이미 큰 파일을 더 키운다면 그것도 신호다 — helper나 submodule을 먼저 추출할지 물어본다. 먼저 나누고, 그다음 추가한다.

**리팩터링과 기능 작업을 분리한다.** 새 동작을 추가하면서 기존 코드를 다듬는 것은 사실 두 개의 변경이다 — 따로 낸다. rename 같은 자잘한 정리는 리뷰어 판단에 맡길 수 있다.

## 이 diff를 넘는 파급

- 변경이 공유 interface, config 형식, 다른 팀이 의존하는 library를 건드린다면, "외과적"이라는 말은 이 저장소 안이 아니라 **그 interface** 안에서 경계 지어진다는 뜻이다 — 병합 후가 아니라 병합 전에 외부 호출자를 확인한다.
- 여기 놓인 패턴은 다른 엔지니어가 근거를 다시 따지지 않고 그대로 베끼는 패턴이 된다. 여기서 택한 지름길이 조용히 조직 전체의 관행이 될 수 있다 — 공유 코드는 일회성 스크립트보다 높은 기준으로 대한다.
- 몇 년에 걸쳐 조직 전체가 베낄 만한 패턴이라면, diff에서 우연히 발견되고 흉내 내기보다 RFC나 문서화된 관행으로 의도적으로 제안한다 — 우발적 교리는 리뷰 코멘트보다 되돌리기 어렵다.
- 조용히 조직 전체의 관행이 되는 패턴은 vendor, license, 채용 모델을 몇 년간 고정시킬 수 있다 — 퍼지기 전에 headcount와 비용 면에서 표준화할 만큼 싼지 물어본다.

## 심각도 표시

Required와 Optional을 구분해 표시한다. 표시를 안 하면 minor한 지적도 blocker로 취급된다.

| 표시 | 의미 |
|---|---|
| (없음) | Required — 병합 전 반드시 해결 |
| **Critical:** | 병합을 막음 — 보안 취약점, 데이터 손실, 기능 파손 |
| **Nit:** | 소소함, optional — 무시해도 안전 (포맷, 스타일 취향) |
| **Optional:** / **Consider:** | 제안 — 고민해볼 만하지만 필수는 아님 |
| **FYI** | 정보 제공 — 조치 불필요 |

**중요한 것을 먼저 말한다.** correctness와 보안이 먼저, 구조적 회귀와 놓친 단순화가 다음, 나머지는 그 뒤다. 실질적 문제 하나를 열 개의 nitpick 밑에 묻지 않는다 — 구조적 문제 하나가 **곧** 그 리뷰다.

## "나중에 정리할게요"를 받아들이지 않는다

실무에서 미뤄진 정리는 대개 일어나지 않는다. 이번 변경에 포함시키거나, 정말 급하다면 **담당자를 지정한** 별도 issue로 남긴다.

## 이 저장소에서

`AGENTS.md` 정언명령 20의 "하나의 work item에는 한 명의 writing owner만 둔다"와 `.agents/skills/eatbid-supervised-delivery`의 위임·인계 절차는 이 스킬의 "변경 크기"·"파급" 판단을 소유권 단위로 강제한다. 변경 절차의 "테스트 이름만 바꿀 때 assertion·fixture·실행 순서를 함께 고치지 마라"는 "리팩터링과 기능 작업을 분리한다"를 명세 번역 대 동작 변경의 구체적 사례로 못 박은 것이다. 커밋마다 도는 `pnpm architecture:check -- --changed`는 병합 전 검사를 변경된 경로로 좁혀 이 스킬의 "외과적" 원칙과 같은 방향을 향하지만, 최종 판정은 pull request의 전체 CI가 한다.

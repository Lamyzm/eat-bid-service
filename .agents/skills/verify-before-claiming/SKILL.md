# 주장하기 전에 검증한다

**주장보다 증거가 먼저다. 예외는 없다.**

## 철칙

```
방금 검증 명령을 실행하지 않았다면, 통과한다고 말할 수 없다.
```

"아까 통과했다"는 검증이 아니다. 코드가 바뀌었다면 다시 돌린다.

## 게이트 함수

무언가의 상태를 주장하기 **바로 전에**:

1. **식별** — 이 주장을 증명하는 명령은 무엇인가?
2. **실행** — 그 명령을 **처음부터 전부** 실행한다(부분 실행은 아무것도 증명하지 않는다)
3. **읽기** — 출력 전체를 읽는다. 종료 코드를 확인한다. 실패 개수를 센다.
4. **대조** — 출력이 주장을 지지하는가?
   - 아니다 → 실제 상태를 증거와 함께 말한다
   - 그렇다 → 주장을 증거와 함께 말한다
5. **그다음에야** 주장한다

한 단계라도 건너뛰면 검증이 아니라 추측이다.

## 주장별 필요 증거

| 주장 | 필요한 것 | 부족한 것 |
|---|---|---|
| 테스트 통과 | 테스트 명령 출력: 실패 0건 | 이전 실행, "통과할 것" |
| lint 깨끗 | 린터 출력: 오류 0건 | 부분 확인, 추정 |
| 빌드 성공 | 빌드 명령: exit 0 | lint 통과(린터는 컴파일하지 않는다) |
| 버그 수정됨 | 원래 증상을 다시 재현: 이제 통과 | "코드를 고쳤으니 당연히 됐을 것" |
| 회귀 테스트 동작함 | 수정을 되돌려 **실패 확인** → 복원 → 통과 | 한 번 통과한 테스트 |
| 요구사항 충족 | 요구사항 대조 줄 단위 체크리스트 | 테스트 통과 |
| 하위 작업 완료 | diff가 실제 변경을 보여줌 | 도구·에이전트의 "성공" 보고 |
| 공유 인터페이스/API 변경 | 소비자 쪽도 새 계약으로 실행해 검증, 자기 호출부만이 아니라 | 자기 테스트만 통과 |

## 위험 신호 — 멈춰야 할 때

- "될 것 같다", "아마", "~인 듯하다"
- 검증 전에 만족을 표현("좋아!", "됐다!", "이제 된다!")
- 검증 없이 commit/push/PR로 넘어가려는 시도
- 도구나 서브에이전트의 성공 보고를 그대로 받아들임
- 일부만 확인하고 전체를 가정함
- "이번 한 번만"
- 지쳐서 마무리하고 싶음

## 합리화 차단

| 변명 | 실제 |
|---|---|
| "이제 될 것 같은데" | 그럼 **실행**해서 확인 |
| "확신한다" | 확신은 증거가 아니다 |
| "이번 한 번만" | 예외는 없다 |
| "lint는 통과했다" | 린터는 컴파일러가 아니다 |
| "에이전트가 성공했다고 했다" | 독립적으로 검증한다 |
| "지쳤다" | 피로는 면제 사유가 아니다 |
| "부분 확인이면 충분하다" | 부분은 아무것도 증명하지 않는다 |
| "말을 다르게 했으니 규칙이 적용 안 된다" | 문구가 아니라 취지를 따른다 |

## 적용 범위

성공이나 완료를 **암시하는 모든 표현**에 적용된다 — 정확한 단어뿐 아니라 표현을 바꾼 문장, 함의까지.
이 주장에 의존할 소비자·팀이 많을수록 검증이 실제로 커버해야 할 범위도 커진다 — 로컬 스위트가
초록인 것은 자기 코드가 동작함을 증명할 뿐, 하위의 모든 호출자가 여전히 동작함을 증명하지 않는다.
Distinguished/Fellow 관점: 이 주장이 여러 해에 걸친 회사 전체의 판단을 뒷받침한다면, 증거는 오늘의
맥락을 모르는 사람도 처음부터 재현할 수 있어야 한다 — 실행한 사람이 아직 있어서 보증해주는 것으로
충분하지 않다. Executive 관점(CTO/VP-Eng): 이사회·규제기관·고객에게 하는 주장("우리는 준수한다",
"사고는 격리됐다", "이 SLA를 지킬 수 있다")은 기술적 진술이 아니라 계약·법적 진술이 된다 — 말하기
전에 그 기준으로 검증한다. 말을 되돌리는 비용은 revert가 아니라 계약이나 기사 제목이다. 검증을
실행할 수 없다면 그렇다고 말한다 — "아직 테스트를 안 돌렸다"가 "될 것 같다"보다 낫다.

## 이 저장소에서

- 이 스킬의 철칙은 `pnpm architecture:check`, `pnpm contracts:check`, `pnpm contracts:python:check`처럼
  이 저장소가 이미 갖춘 결정적 gate와 정확히 같은 방향이다. 명령은 개별로, 작업 경로가 분명하게
  실행하고 pipe로 축약한 성공을 원래 검사의 exit code로 쓰지 않는다는 규칙은
  `.agents/skills/eatbid-supervised-delivery`가 구현자 절차로 이미 명시한다.
- 정언명령 22에 따라 `pnpm review:ai`의 AI finding은 결정적 gate 뒤의 읽기 전용 advisory일 뿐이며
  lint·typecheck·test·contract·architecture 실패를 덮을 수 없다 — "AI가 통과라고 했다"는 이 표의
  "에이전트가 성공했다고 했다"와 같은 함정이다.
- push 전 무엇을 돌려야 하는지는 push 게이트가 로컬 `main` 기준인지 `origin/main` 기준인지에 따라
  달라진다. 두 층위를 혼동하면 통과했다고 믿었지만 실제로는 좁은 범위만 본 것이 된다.

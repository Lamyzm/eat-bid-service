# 트레이드오프와 결정의 무게

## 먼저: 이 결정이 얼마나 무거운가

모든 결정이 같은 시간을 들일 자격은 없다.

- **쉽게 되돌릴 수 있는 결정**(함수 내부 구현, 파일 위치, 변수 이름) → 만들고, 고민하지 말고,
  나중에 고친다.
- **되돌리기 어려운 결정**(DB 스키마, 공개 API, 데이터 형식, 핵심 의존성, 이미 배포된 인터페이스)
  → 시간을 더 쓰고 대안을 진지하게 따진다.

확인 절차도 같은 등급을 따른다: 되돌릴 수 있으면 → 그냥 한다, 되돌릴 수 없으면 → 먼저 확인받는다.
**모든 것을 같은 무게로 게이트하면 게이트 자체가 무시당한다.**

## 어떻게 비교하는가

- 실제 대안 2~3개의 장단점을 **한 줄씩** 나열한다: 속도 대 복잡성, 유연성 대 학습 곡선, 지금 편함
  대 나중에 편함, 성능 대 가독성.
- 익숙하다는 이유만으로 반사적으로 고르지 않는다. 익숙함은 정당한 장점이지만, **명시된** 장점이어야
  한다.
- 각 대안이 틀렸을 때의 비용을 본다. 비용이 비대칭적이면(하나는 되돌리기 쉽고 다른 하나는 아니면)
  그것이 대개 결정적 요인이다.
- Principal 관점: 다른 팀이 그 위에 무언가를 쌓을 결정(공유 스키마, 공개 API, 다른 팀도 채택할
  의존성)이라면 조직 차원의 비용도 함께 잰다 — 소비자 전체의 마이그레이션 비용, 앞으로 몇 분기
  동안 다른 팀이 이 방향으로 기본값을 삼길 원하는가.
- Distinguished/Fellow 관점: 여러 해에 걸친 회사 전체의 판단(다른 회사도 함께 수렴할 수 있는
  프로토콜·형식)이라면, 오늘의 맥락이 전혀 없는 5년 후 신규 합류자에게도 여전히 말이 되는지,
  설명이 지금 있는 사람에게 의존하는지를 잰다.
- Executive 관점(CTO/VP-Eng): 엔지니어링 노력만이 아니라 총소유비용을 올려놓는다 — 라이선스
  비용, 인프라 지출, 만들고 유지할 팀의 기회비용은 기술적 장점보다 먼저 CFO나 이사회가 묻는 것이다.

## 이유를 기록한다

- 왜 이것을 골랐는지 **한두 문장**을 코드 주석, 커밋 메시지, 설계 노트에 남긴다.
- 6개월 후 "왜 이렇게 했지?"에 답할 수 있어야 한다. 답할 수 없으면 다음 사람이 그냥 뜯어낸다.
- **기각한 대안도 함께 기록한다.** 왜 쓰지 않았는지 모르면 다음 사람이 같은 길을 다시 걷는다.

## 이 저장소에서

- "판단 경계에는 한국어로 이유를 남긴다"는 정언명령 13이 이미 범위를 정해 두었다: 공개 port/계약,
  도메인 불변식, 인증·권한·transaction·수명주기, BigInt 무손실 변환처럼 잘못 바꾸면 사고가 되는
  선택에 TSDoc 또는 why 주석을 둔다. "이유를 기록한다" 절은 이 범위 안에서만 적용하고, 코드를
  문장으로 반복하거나 현재 숫자를 복사하는 장식적 설명은 만들지 않는다.
- 되돌리기 어려운 결정(스키마, 공개 API 등)에서 아키텍처 경계를 바꾼다면 "변경 절차" 절이 요구하는
  대로 관련 ADR을 새로 쓰거나 대체 ADR로 갱신한다 — 기각한 대안을 코드 주석에만 남기지 않고
  ADR에도 남긴다.
- 데이터 모델·API·시스템 경계 변경은 각각 `domain-and-data.md`, `runtime-and-deployment.md`,
  `c4.md`/`arc42.md`를 같은 변경에서 갱신해야 한다 — 트레이드오프 기록이 코드 주석에만 머물면
  이 요구를 충족하지 못한다.

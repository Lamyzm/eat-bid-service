# 먼저 측정한다

증거 없이 최적화하지 않는다. "이거 느린 것 같다"는 추측이고, 추측에서 시작한 최적화는 대개 느껴지는 개선 없이 복잡도만 더한다.

## 순서: 측정 → 특정 → 수정 → 재측정

- **재현 가능한 측정**(profiler, timing log, Lighthouse, real-user metric)부터 시작한다 — 직감으로 "이게 문제다"라고 짚지 않는다
- 병목을 **정확히 하나만** 특정한다: N+1 query, cache miss, bundle size. 여러 개를 한 번에 고치면 무엇이 실제로 도움이 됐는지 알 수 없다
- 수정 후 **같은 방식으로 재측정**한다. 개선이 측정 잡음(noise)을 이겨야 진짜다
- 재측정 없이 "이제 빨라졌다"고 말하지 않는다

## 흔한 함정

- profiling 전에 memoization이나 cache부터 손대는 것 — cache는 새로운 비용(invalidation 버그)을 산다
- 여러 최적화를 한 커밋에 묶어서 아무도 무엇이 효과 있었는지 모르게 만드는 것
- "중립적인 변경이니 일단 남겨두자" — 도움이 안 됐으면 되돌린다; 정당화되지 않은 코드를 쌓지 않는다
- 회귀를 막을 안전망(모니터링, 벤치마크 테스트) 없이 "이제 빠르다"고 선언하는 것

## 최적화할 가치가 있는가

측정했는데 병목이 전체 경로에 비해 무시할 만하면, 그건 최적화 대상이 아니라 **건너뛸** 대상이다. 성능은 예산이다: 실제로 느껴진다는 증거가 있는 곳에만 쓴다.

- hot path가 다른 팀도 호출하는 공유 library나 service 안에 있다면, 자기 호출 지점만이 아니라 **그들의** 트래픽 프로파일까지 저울질한다 — 내 호출자를 돕는 변경이 남의 호출자를 조용히 퇴보시킬 수 있다.
- 조직 전체의 기본값이 될 만한 기법(외부에 발표하거나 오픈소스로 낼 만한 것)이라면, 한 워크로드의 benchmark만으로 여러 해에 걸친 결정을 내리지 않는다 — 그것이 거짓 최적화가 교리가 되는 경로다.
- infra를 늘리는 수정(더 큰 인스턴스, caching layer, 새 managed service)이 기본값으로 나가기 전에, 반복되는 비용과 그것이 아끼는 엔지니어-시간을 저울질한다.
